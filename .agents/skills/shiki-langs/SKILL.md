# Shiki languages

Importing `codeToHtml` from `"shiki"` pulls `bundledLanguages`, a static map of every grammar (~250 lazy `import()`s). Even on a prerendered server component, Next's output-file-tracing follows that whole graph, so all ~250 grammars (~10 MB) trace into `.next/standalone` even though highlighting runs only at build. The fix is a custom shiki bundle over a content-derived language map, so only the grammars the site uses trace in.

Docs and blog code blocks are highlighted by fumadocs-mdx at build and baked to static HTML, so they ship zero grammars at runtime. The only runtime highlighter is the marketing landing page; that is the one place a bundle is built.

## Layout

- `.github/scripts/shiki-langs.ts`, scans `web/next/content/**` code fences, resolves aliases via shiki's `bundledLanguagesInfo`, writes the generated map
- `web/next/src/lib/shiki-languages.ts`, generated and git-ignored, `bundledLanguages` keyed by id and every alias (`bash`/`sh`/`zsh` -> shellscript, `ts` -> typescript), each value `() => import("@shikijs/langs/<id>")`
- `web/next/src/app/(marketing)/page.tsx`, builds the bundle with `createBundledHighlighter` + `createSingletonShorthands` from `shiki/core`, over `bundledLanguages` plus the two themes and the oniguruma engine
- `@shikijs/langs` and `@shikijs/themes`, direct deps (catalog) so the generated `import()` targets resolve
- wiring: the script runs before `next build`, `next dev`, and `tsc` (web/next `build`, `dev`, `check-types` scripts)

## How it works

- The generated map's keys are the string a caller passes (`highlight(code, "bash")`), so `codeToHtml`'s `lang` is type-checked against the content-derived set: a language not used anywhere is a compile error, not dead weight.
- Keys cover id and aliases because `createBundledHighlighter` looks up the requested lang in the map to decide which grammar to lazy-load; an alias that is not a key would not resolve. `langAlias` does not resolve through `createSingletonShorthands`, so alias keys (not `langAlias`) are what the map ships.
- The set is a superset by construction: the script scans every content fence, so any language a code block uses is available, and adding a code block in a new language just works after the script reruns.

## Add or change a highlighted language

1. Nothing manual for content: write the code fence (```lang) anywhere under `web/next/content`, then rerun the script (or start dev) so the map picks it up: `bun .github/scripts/shiki-langs.ts`.
2. To highlight a language on the landing page that no doc uses, add a code fence for it in content (the map is content-driven), or the `lang` argument will be a type error.
3. To change the themes, edit the `themes` map in `page.tsx` (`github-light`/`github-dark`); themes are a design choice, not content-derived.
4. Regenerate and type-check: `bun --cwd web/next run check-types` (runs the script, then `tsc`).

## Verify

1. Build: `bun --cwd web/next run build`.
2. The `@shikijs/langs` package must NOT appear under `.next/standalone/node_modules` (grammars are inlined into the marketing server chunk instead): `du -sh web/next/.next/standalone`.
3. No full-bundle leak: an unused grammar's scope (e.g. `source.python`) should appear in at most the markdown grammar chunk (as an embedded-scope string, not real patterns), never as its own grammar. `grep -rl source.rust web/next/.next/standalone` should be empty.
4. Render: the four hero code blocks highlight (dual-theme `--shiki-light`/`--shiki-dark` spans). Same grammars, themes, and options as before, so output is byte-identical.

## Notes

- Do NOT route the landing page through `DynamicCodeBlock` (`fumadocs-ui/components/dynamic-codeblock`): it highlights in the browser and ships shiki plus grammars to the client bundle, with a Suspense flash. It is for code not known at build (API responses, user input), not static literals.
- Do NOT use fumadocs `ServerCodeBlock` or `fumadocs-core/highlight` for the landing page either: both pull `shiki/full`, which re-traces the whole ~250-grammar bundle.
- The generated file is git-ignored (like `content/**/meta.json`) and regenerated by the dev, build, and check-types scripts; a fresh clone that opens `page.tsx` before running one of those will see an unresolved import, same as fumadocs `.source`.
- The scan is safe on the over-collection side: a superset only adds a small grammar; missing a used language would fail at runtime, so the regex favors matching (indented and `~~~` fences included).
