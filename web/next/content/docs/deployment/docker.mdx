Package `web/next` and `api/hono` as two images from their multi-stage Dockerfiles, then bring the whole stack up with one command:

```bash
docker compose up
```

That builds and starts **web** on [localhost:3000](http://localhost:3000) and **api** on [localhost:4000](http://localhost:4000) from `docker-compose.yml` at the repo root and a root `.env` you provide. Two things set the images apart from the Vercel build: they never migrate the database, and they read `.env` through a build secret, so a value the build bakes in (the web's `NEXT_PUBLIC_*`, the cookie scope from `HONO_APP_URL`) changes only on a rebuild.

## When you need this

Reach for this page when you self-host on any Docker host, or want the production build running locally before a release. For the serverless path, where the build migrates for you, see [Deploy to Vercel](/docs/deployment/vercel).

## Prerequisites

- Docker with BuildKit and Compose v2 (`docker compose`): the Dockerfiles mount a build secret.
- A root `.env`: both builds validate the full env and fail without it ([Environment Variables](/docs/manage/environment)).
- A Postgres the containers can reach, already migrated; a `localhost` URL is rewritten for you (below).

<Callout type="warn" title="A deploy's .env is not the one init wrote">

The `.env` that `init` writes sets `NODE_ENV=local` and `AGENT_SIGNIN_ENABLED=true`, which together mount `POST /api/agents/sign-in-as` ([Local sign-in](/docs/getting-started/working-with-agents#local-sign-in)), and Compose publishes both ports on every interface. That route's only check is the `Origin` header, which a client outside a browser sets to anything it likes, so on a host others can reach it signs anyone in as `LocalAgent`, an `owner` when that call creates the account. Anywhere but your own machine, set `NODE_ENV=production` (or `staging`) and leave `AGENT_SIGNIN_ENABLED` blank. Either one alone unmounts the route; the stage also hides raw error messages and closes `/headers`, which echoes every request header, cookies included.

</Callout>

## How the containers talk

Inside the Compose network the web container cannot reach the api at `localhost`: that address is its own container. `INTERNAL_API_URL=http://api:4000`, set on both services in `docker-compose.yml` and baked into the web image by `web/next/Dockerfile`, is the one Docker-specific knob, with three jobs:

- **web, build time**: the Next rewrite in `next.config.ts` sends `/api/*` to `http://api:4000`.
- **web, runtime**: server-side calls (`src/lib/config.ts`) hit the api container directly.
- **api, runtime**: its presence flips a `localhost` `POSTGRES_URL` to `host.docker.internal` (`dockerHostUrl` in `packages/env/src/lib/postgres-url.ts`), so the container reaches a database on your host.

External clients keep the mapped ports. You never set it by hand, and it belongs to no other topology.

## The images

Both Dockerfiles share one shape on `oven/bun:1.4.3-alpine`:

```txt
base → prepare → builder → runner
```

`prepare` runs `turbo prune <workspace> --docker` to carve a workspace-only context, so each image builds only its own dependencies, and `runner` runs as the non-root `USER bun`.

- The **web** image uses Next's `output: "standalone"`: the builder copies `.next/static` and `public` into it and the runner starts `bun server.js`. `next.config.ts` sets standalone for every build except Vercel's, and prunes the other-libc `sharp` and `@takumi-rs` binaries (alpine is musl), so one libc stack ships.
- The **api** image copies `bundle/` and runs `bun --no-install bundle/index.mjs`: no `node_modules`, and with auto-install off a bare specifier the bundle lacks fails at once instead of being fetched from npm.

### The .env build secret

Both builds need `.env` at build time but never bake it into a layer: it is mounted as a BuildKit secret for the build step only:

```txt
--mount=type=secret,id=dotenv,target=/app/.env,required=true
```

Compose wires it from `secrets: dotenv`; a plain `docker build` passes `--secret id=dotenv,src=.env`. The secret never enters the build context, and `.dockerignore` excludes every `.env*` file and lets only `.env.example` in. At runtime, compose's `env_file` hands the same `.env` to the containers.

The api bundle bakes no `NODE_ENV` either: it is built with `bun build --env disable`, so the stage is whatever `.env` says at runtime and `/api/health` reports it as `environment`. Without the flag Bun would inline the build shell's value, never what the mounted file says.

<Callout type="warn" title="Rebuild with --no-cache after editing .env">

Secret contents are not part of BuildKit's cache key, so a plain rebuild can replay the cached step and ship stale baked values. Run `docker compose build --no-cache`.

</Callout>

## Migrations: you run them

The images never run migrations. Apply them yourself with `bun run db:migrate` from a checkout, before or alongside a rollout, against the same `POSTGRES_URL` the containers read; only the [Vercel](/docs/deployment/vercel) build migrates on deploy. Without a reachable database, `/api/health` still passes and a route answers 500 only once it queries: a signed-in `/api/v1/user` after its five-minute cookie cache lapses, or `GET /api/waitlist` with the waitlist on. An anonymous `/api/v1/user` answers 401 before it reaches the database, so it proves nothing about the connection.

## Checking the images

The `docker-test` skill ([AI Skills](/docs/resources/ai-skills)) holds the checks: one service at a time while iterating (its first step), the offline run that proves the api bundle resolves every import, the single-libc assertion on the web image, and the golden end-to-end suite under `tests/` against the running stack (canonical starter only, since that directory is fork-excluded). Its `.env` section builds a dummy `.env` for a clean checkout and names the traps around it, among them the inline comments a direct `docker run --env-file` keeps where compose strips them. Compose names images after the checkout directory, so every command there goes through compose.

## Common questions

**Why does the api run with `--no-install`?**

Better Auth carries a guarded `@opentelemetry/api` import that fires inside its first span, the first auth call of any kind rather than boot, since every auth endpoint and every database adapter call opens one. With auto-install on, Bun fetches it from npm at that moment, which stalls a container with no network; with the flag the import fails at once and the guard falls back. A `Cannot find package 'X'` in the api logs names an import the bundle genuinely lacks.

**Why does `bun run db:migrate` ask for a `pg` or `postgres` driver, or fail to find `@packages/env/dist`?**

Drizzle Kit does not speak Bun's SQL driver, so `packages/db` carries `postgres` as a dev dependency for the CLI alone, and `drizzle.config.ts` imports the built `@packages/env`, which the script builds first. Either error means the install never ran: `bun install`, then the script.

## It's working if

- `curl localhost:4000/api/health` answers with `"environment"` set to the `NODE_ENV` your `.env` names.
- `docker compose config --images` lists two images, named after the checkout directory.
- `curl localhost:3000/api/health` answers the same body, which is the web container's rewrite reaching `http://api:4000`.
- With a deploy's `.env`, `curl -X POST localhost:4000/api/agents/sign-in-as` answers `404`.
