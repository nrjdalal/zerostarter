Deploy `web/next` and `api/hono` as two Vercel projects on the same repository. Each ships a `vercel.json` naming its install command, build command, framework preset and function runtime, so a project needs two things from you: its **Root Directory** and its variables.

One Postgres ties the two together, and the api build migrates it: production and `canary` deploys apply pending migrations before they bundle, and every other deploy, a PR preview included, skips the step, so an unmerged migration never reaches the shared database.

## When you need this

Reach for this page when you first put the starter on Vercel, or add a custom domain to a pair that already runs. For the same stack in containers, where nothing migrates for you, see [Deploy with Docker](/docs/deployment/docker).

## Prerequisites

- A Postgres reachable from Vercel's build, not only at runtime: production and `canary` builds run `db:migrate` before they bundle. A preview skips it and needs no database to build.

## Two projects, one runtime

| Project  | Root Directory | Framework | Function runtime   |
| -------- | -------------- | --------- | ------------------ |
| Backend  | `api/hono`     | Hono      | Bun (`bunVersion`) |
| Frontend | `web/next`     | Next.js   | Bun (`bunVersion`) |

Both projects pin `"bunVersion": "1.4.x"` (Vercel accepts only `1.4.x` or `1.x` and manages patch versions itself); the [Bun runtime](https://vercel.com/docs/functions/runtimes/bun) is in beta. Both install from the repo root with `bun install --ignore-scripts`, so `postinstall` never runs there. Why each app is on Bun differs:

- **The api** runs a bundle built with `bun build --target bun`. Its `build:vercel` writes it to `vercel-bundle/` with `--external hono`, because Vercel's Hono preset finds the entrypoint by a literal `hono` import; the Docker bundle stays self-contained.
- **The web** has to build under Bun as well as run under it: its `build:vercel` is `bun run --bun build`, which shims `node` to Bun for every binary the build spawns, `next build` included. The build command also sets `SKIP_ENV_VALIDATION_SERVER=true`, which validates only the `NEXT_PUBLIC_*` values the build inlines ([Skipping validation](/docs/manage/environment#skipping-validation)).

<Callout type="warn" title="Bun at runtime needs Bun at build">

Pin the web functions to Bun while building for Node and every function crashes on `next/dist/compiled/next-server`; only prerendered output keeps serving, which hides the break until a dynamic route is hit. Docker and local builds keep the plain `build` script.

</Callout>

## The api build migrates

`api/hono/vercel.json` puts the migration ahead of the build:

```json
"buildCommand": "cd ../.. && bun .github/scripts/migrate-on-deploy.ts && turbo build:vercel --filter=@api/hono"
```

`.github/scripts/migrate-on-deploy.ts` reads `VERCEL_ENV` and `VERCEL_GIT_COMMIT_REF`: on `production` or the ref `canary` it runs `bun run db:migrate`, otherwise it logs a skip and exits. `main` and `canary` are the two branches allowed to change the shared schema; a feature branch previews without touching it.

## Deploy the api first

The web needs the api's URL, so the backend goes up first.

1. **Add New Project**, select the repository, and set **Root Directory** to `api/hono`; Vercel reads the rest from its `vercel.json`.
2. Add the variables. `.env.example` is the full list; at minimum:

   ```
   NODE_ENV=production
   HONO_APP_URL=https://your-api.vercel.app
   HONO_TRUSTED_ORIGINS=https://your-web.vercel.app
   BETTER_AUTH_SECRET=your_secret_key
   POSTGRES_URL=your_postgres_connection_string
   GITHUB_CLIENT_ID=your_github_client_id
   GITHUB_CLIENT_SECRET=your_github_client_secret
   GOOGLE_CLIENT_ID=your_google_client_id
   GOOGLE_CLIENT_SECRET=your_google_client_secret
   ```

   The OAuth pairs are optional. `HONO_PORT` (default `4000`) stays unset: the api binds the `PORT` the platform injects.

3. Deploy. The build log prints the migration line, then the bundle, and the deployment URL answers `/api/health`. Copy that URL for the web.

## Then the web

1. **Add New Project**, select the **same** repository, and set **Root Directory** to `web/next`.
2. Add the variables, with the api URL as `NEXT_PUBLIC_API_URL`:

   ```
   NODE_ENV=production
   NEXT_PUBLIC_APP_URL=https://your-web.vercel.app
   NEXT_PUBLIC_API_URL=https://your-api.vercel.app
   NEXT_PUBLIC_POSTHOG_HOST=https://eu.i.posthog.com
   NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN=your_posthog_key
   NEXT_PUBLIC_USERJOT_URL=your_userjot_url
   ```

   The last three are optional. `NEXT_PUBLIC_NODE_ENV` is derived from `NODE_ENV` (`packages/env/src/web-next.ts`), so you never set it, and `INTERNAL_API_URL` is Docker's and stays unset.

3. Deploy. The landing page renders with its API status badge green, and Core Web Vitals arrive under the project's **Speed Insights** tab with nothing to enable: the root layout renders the beacon only when `process.env.VERCEL` is set ([Vercel Speed Insights](/docs/manage/analytics#vercel-speed-insights)).

Variables never propagate between the projects: a custom domain means updating the URL variables on both, and the OAuth callbacks to match.

## Public suffix

`vercel.app` is a public suffix, where the browser refuses a `Domain` cookie shared between sibling sites, so two `*.vercel.app` projects cannot share a session the way subdomains of one custom domain do. The build detects the shape (`packages/scripts/src/generate-env.ts` runs the Public Suffix List once over the api URL, never in a shipped bundle) and the client routes sign-in **same-origin through the web's `/api` proxy**, so the session cookie lands first-party on the web. It follows that:

- **OAuth registers at the web origin.** Sign-in completes on the web, so the app origin and the callback are both the web, not the api:

  ```txt
  https://your-web.vercel.app
  https://your-web.vercel.app/api/auth/callback/github
  https://your-web.vercel.app/api/auth/callback/google
  ```

  A custom domain, where web and api share a parent, switches back on its next build, with the callback on the api host.

- **The api infers the web origin** as the first `HONO_TRUSTED_ORIGINS` entry that is not itself. Set `HONO_WEB_URL` on the api project when that will not do: more than one trusted origin, or none that differs from the api, where the log warns `[auth] HONO_APP_URL is a public-suffix host` and sign-in cannot complete until you set it.
- **The rate limiter sees a Vercel hop** behind the rewrite, so proxied visitors share one anonymous bucket ([Rate Limiting](/docs/manage/rate-limiting)).

## WebSockets

The api serves WebSockets on Vercel through [Vercel's native support](https://vercel.com/docs/functions/websockets) (in beta), which needs [Fluid compute](https://vercel.com/docs/fluid-compute). It switches to the Node adapter (`@hono/node-server` + `ws`) when `VERCEL` is set (`api/hono/src/lib/server.ts`) and keeps `Bun.serve()` everywhere else; [Realtime](/docs/getting-started/realtime#one-route-two-hosts) says why the split stays. On Vercel:

- **On a public suffix the socket falls back to REST.** A Next rewrite does not forward the upgrade, so the `/api/health/ws` example runs on its REST heartbeat there (green, without the live pulse). A custom domain keeps the socket.
- **A connection is pinned to one function instance** and closes at its [max duration](https://vercel.com/docs/functions/limitations#max-duration), 300 seconds by default under Fluid compute, so keep shared socket state external and let clients reconnect.

## Common questions

**Sign-in ends in `state_mismatch` between two `*.vercel.app` projects.**

Either the OAuth app is registered at the api origin (it belongs at the web, above), or `NEXT_PUBLIC_API_URL` points at the web. It stays the api's URL even though the browser never calls it directly: it is the target of the web's `/api` rewrite, so pointing it at the web makes the rewrite call itself and every `/api/*` request answers `508 Loop Detected`. `INTERNAL_API_URL` is not the fix; it is Docker's and stays unset here.

**Is there a deploy mode to set?**

No. `generate-env.ts` runs tldts over `HONO_APP_URL` for the api and `NEXT_PUBLIC_API_URL` for the web and bakes the breakdown, so there is no suffix list to maintain and no variable to flip; moving to a custom domain is a change to those URLs plus a redeploy.

**Which commit does `/api/health` report?**

The deployed one: the `version` suffix comes from `VERCEL_GIT_COMMIT_SHA` at runtime (`getBuildVersion` in `packages/env/src/lib/constants.ts`), because the sha baked at build freezes under turbo's cache whenever `@packages/env` has not changed. Off Vercel, `GIT_SHA` does the same.

**Could the api run `Bun.serve()` on Vercel too?**

A spike tests it on a preview: the Bun runtime now accepts `Bun.serve()` as an entrypoint with a WebSocket path, which would retire the Node adapter. Both are in beta there and Vercel lists upgrade-response, `drain` and backpressure differences, so the split stays until it is proven.

## It's working if

- The api build log on `canary` prints `[migrate-on-deploy] applying pending migrations, VERCEL_ENV=preview, ref=canary` and then `[migrate-on-deploy] done`; a preview build prints `[migrate-on-deploy] skip, VERCEL_ENV=preview, ref=<branch>` and goes on to bundle.
- `https://your-api.vercel.app/api/health` answers `"environment":"production"` with a `version` suffixed by the deployed commit's short sha.
- Sign-in from the web lands on `/dashboard`.
