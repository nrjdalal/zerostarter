Deploy `web/next` and `api/hono` as two Vercel projects on the same repository. Each ships a `vercel.json` naming its install command, build command, framework preset and function runtime, so a project needs two things from you: its **Root Directory** and its variables.

One Postgres ties the two together, and the api build migrates it, on production and `canary` deploys only.

## When you need this

Reach for this page when you first put the starter on Vercel, or add a custom domain to a pair that already runs. For the same stack in containers, where nothing migrates for you, see [Deploy with Docker](/docs/deployment/docker).

## Prerequisites

- A Postgres reachable from Vercel's build, not only at runtime, serving TLS with a certificate the api can verify, since under `NODE_ENV=production` its client connects no other way ([Deploy with Docker](/docs/deployment/docker#prerequisites)).
- `main` on the GitHub remote before you import. Vercel makes `main` the Production Branch when the repository has it and the default branch otherwise, and a fork pushed to an empty repository has `canary` as its default ([Releases](/docs/manage/release#prerequisites) says when `main` lands, when the first release PR opens, and why a fork's `main` does not build before that PR merges). Import after that merge. A project imported once `main` reached the remote but before the merge fails every production deploy until it lands, and one imported before `main` reached the remote tracks `canary` as production until **Settings → Environments → Production → Branch Tracking** reads `main`.

## Two projects, one runtime

| Project  | Root Directory | Framework | Function runtime   |
| -------- | -------------- | --------- | ------------------ |
| Backend  | `api/hono`     | Hono      | Bun (`bunVersion`) |
| Frontend | `web/next`     | Next.js   | Bun (`bunVersion`) |

Both projects pin `"bunVersion": "1.4.x"` (Vercel accepts only `1.4.x` or `1.x` and manages patch versions itself); the [Bun runtime](https://vercel.com/docs/functions/runtimes/bun) is in beta. Both install from the repo root with `bun install --ignore-scripts`, so `postinstall` never runs there. Why each app is on Bun differs:

- **The api** runs a bundle built with `bun build --target bun`. Its `build:vercel` writes it to `vercel-bundle/` with `--external hono`, because Vercel's Hono preset finds the entrypoint by a literal `hono` import; the Docker bundle stays self-contained.
- **The web** has to build under Bun as well as run under it: its `build:vercel` is `bun run --bun build`, which shims `node` to Bun for every binary the build spawns, `next build` included. The build command also sets `SKIP_ENV_VALIDATION_SERVER=true`, which validates only the `NEXT_PUBLIC_*` values the build inlines ([Skipping validation](/docs/manage/environment#skipping-validation)).

<Callout type="warn" title="Bun at runtime needs Bun at build">

Pin the web functions to Bun while building for Node and every function crashes on `next/dist/compiled/next-server`; only prerendered output keeps serving, which hides the break until a dynamic route is hit. Docker and local builds keep the plain `build` script.

</Callout>

## Deploy

The web needs the api's URL, so the backend goes up first.

### The api build migrates

`api/hono/vercel.json` puts the migration ahead of the build:

```json
"buildCommand": "cd ../.. && bun .github/scripts/migrate-on-deploy.ts && turbo build:vercel --filter=@api/hono"
```

`.github/scripts/migrate-on-deploy.ts` reads `VERCEL_ENV` and `VERCEL_GIT_COMMIT_REF`: on `production` or the ref `canary` it runs `bun run db:migrate` before the bundle, and every other deploy, a PR preview included, logs a skip and goes on to bundle, so an unmerged migration never reaches the shared database.

### The api first

1. **Add New Project**, select the repository, and set **Root Directory** to `api/hono`; Vercel reads the rest from its `vercel.json`.
2. Add the variables. These are the ones whose value is not the local one:

   ```txt
   HONO_APP_URL=https://your-api.vercel.app
   HONO_TRUSTED_ORIGINS=https://your-web.vercel.app
   NODE_ENV=production
   ```

   The rest (`BETTER_AUTH_SECRET`, `POSTGRES_URL` and the OAuth pairs) are as `.env.example` describes them. Agent sign-in never mounts under `NODE_ENV=production`, so a deploy with no complete OAuth pair and no magic link offers no way to sign in ([Sign-in methods](/docs/manage/authentication#sign-in-methods)); register the OAuth app where [Public suffix](#public-suffix) says. `HONO_PORT` (default `4000`) stays unset: the api binds the `PORT` the platform injects.

3. Deploy. The build log prints the migration line, then the bundle, and the deployment URL answers `/api/health`. Copy that URL for the web.

### Then the web

1. **Add New Project**, select the **same** repository, and set **Root Directory** to `web/next`.
2. Add the variables, with the api URL as `NEXT_PUBLIC_API_URL`:

   ```txt
   NEXT_PUBLIC_API_URL=https://your-api.vercel.app
   NEXT_PUBLIC_APP_URL=https://your-web.vercel.app
   NODE_ENV=production
   ```

   The optional PostHog and UserJot variables are as `.env.example` describes them. `NEXT_PUBLIC_NODE_ENV` is derived from `NODE_ENV` (`packages/env/src/web-next.ts`), so you never set it, and `INTERNAL_API_URL` is Docker's and stays unset.

3. Deploy. `https://your-web.vercel.app/api/health` answers the api's body through the web's `/api` rewrite; in the canonical starter the landing page's API status badge also turns green, while a fork's home carries no badge. Core Web Vitals arrive under the project's **Speed Insights** tab with nothing to enable: the root layout renders the beacon only when `process.env.VERCEL` is set ([Vercel Speed Insights](/docs/manage/analytics#vercel-speed-insights)).

Variables never propagate between the projects: a custom domain means updating the URL variables on both, and the OAuth callbacks to match.

## Public suffix

Two `*.vercel.app` projects cannot share a session cookie, since `vercel.app` is a public suffix ([Sessions and cookies](/docs/manage/authentication#sessions-and-cookies) has the reasoning). The build detects the shape (`packages/scripts/src/generate-env.ts` runs tldts over `HONO_APP_URL` for the api and `NEXT_PUBLIC_API_URL` for the web, once at build and never in a shipped bundle) and the client routes sign-in **same-origin through the web's `/api` proxy**, so the session cookie lands first-party on the web. It follows that:

- **OAuth registers at the web origin.** Sign-in completes on the web, so the app origin and the callback are both the web, not the api ([Callback URLs](/docs/manage/authentication#callback-urls)); a custom domain, where web and api share a parent, switches back to the api host on its next build.
- **The api infers the web origin** as the first `HONO_TRUSTED_ORIGINS` entry that is not itself. Set `HONO_WEB_URL` on the api project when that will not do: more than one trusted origin, or none that differs from the api, where the log warns `[auth] HONO_APP_URL is a public-suffix host` and sign-in cannot complete until you set it.
- **The rate limiters see a Vercel hop** behind the rewrite, so proxied visitors share one anonymous bucket ([Rate Limiting](/docs/manage/rate-limiting#common-questions)). [Better Auth's limiter](/docs/manage/rate-limiting#better-auths-limiter), on under `NODE_ENV=production`, keys on the same `x-forwarded-for`, so those visitors share its budgets too, three sign-in requests per 10 seconds among them, and `HONO_RATE_LIMIT` does not change them.

## WebSockets

The api serves WebSockets on Vercel through [Vercel's native support](https://vercel.com/docs/functions/websockets) (in beta), which needs [Fluid compute](https://vercel.com/docs/fluid-compute), the default for a new project; [Realtime](/docs/getting-started/realtime#one-route-two-hosts) states which adapter each host takes. On Vercel:

- **A connection is pinned to one function instance and closes at its [max duration](https://vercel.com/docs/functions/limitations#max-duration)**, 300 seconds by default under Fluid compute, so a client's reconnect may land on another instance ([Beyond one instance](/docs/getting-started/realtime#beyond-one-instance)).
- **On a public suffix** the client points the socket at the web origin, as it does REST, and on a custom domain at the api directly ([Realtime](/docs/getting-started/realtime#common-questions)); either way REST stays the baseline it overlays.

## Common questions

**Why does sign-in between two `*.vercel.app` projects end in `state_mismatch`?**

Because the provider returned the browser to a host without the state cookie. The browser's auth calls go to the `NEXT_PUBLIC_APP_URL` origin, so the cookie is set there, while Better Auth builds the callback on the web origin the api resolves ([Public suffix](#public-suffix)): `HONO_WEB_URL`, else the first `HONO_TRUSTED_ORIGINS` entry that is not the api. The two differ when another non-api origin is listed first, which the api logs as `[auth] inferred the web origin as the first non-api HONO_TRUSTED_ORIGINS entry`, or when `HONO_WEB_URL` names another host: set `HONO_WEB_URL` on the api to the `NEXT_PUBLIC_APP_URL` origin and register the callback there ([Authentication](/docs/manage/authentication#common-questions) has the mechanism). An api that resolves no web origin never reaches the provider: Better Auth refuses the sign-in with a 403, `Invalid callbackURL` or `Invalid origin`. If every `/api/*` request answers `508 Loop Detected` instead, `NEXT_PUBLIC_API_URL` points at the web rather than the api ([Environment Variables](/docs/manage/environment#common-questions)).

**Is there a deploy mode to set?**

No. The build derives the shape from the two URLs ([Public suffix](#public-suffix)), so there is no suffix list to maintain and no variable to flip; moving to a custom domain is a change to those URLs plus a redeploy.

**Which commit does `/api/health` report?**

The deployed one: the `version` suffix comes from `VERCEL_GIT_COMMIT_SHA` at runtime (`getBuildVersion` in `packages/env/src/lib/constants.ts`), because the sha baked at build freezes under turbo's cache whenever `@packages/env` has not changed. Off Vercel, `GIT_SHA` does the same.

## It's working if

- The api build log on `canary` prints `[migrate-on-deploy] applying pending migrations, VERCEL_ENV=preview, ref=canary` and then `[migrate-on-deploy] done`; a preview build prints `[migrate-on-deploy] skip, VERCEL_ENV=preview, ref=<branch>` and goes on to bundle.
- `https://your-api.vercel.app/api/health` answers `"environment":"production"` with a `version` suffixed by the deployed commit's short sha.
- With an OAuth pair set on the api, sign-in from the web lands on `/dashboard`.
