A skill is a `SKILL.md` file: a trigger plus a literal procedure. Not a vague "you are a helpful assistant" prompt: the exact steps for one real task in _this_ repo, with its conventions baked in and its known traps called out. The `api-endpoint` skill, for instance, hands over the Hono router template, the validation envelope, where to mount the route, the restart step, and the `curl` that proves it works.

Every skill lives in `.agents/skills/<name>/SKILL.md`. That is the one source. `.claude/skills` is a symlink to it, so Claude Code, Cursor, and Codex all read the same files. Edit a skill once and every agent tool sees the change. There is no second copy to keep in sync.

A fork scaffolded with the [CLI](/docs/getting-started/cli) inherits every skill below, rebranded, and `sync` keeps the ones it has not customized up to date.

## How an agent picks one

Each `SKILL.md` opens with frontmatter, a `name` and a `description` that states _when_ to use it:

```yaml
name: api-endpoint
description: "Add a typed Hono API endpoint or WebSocket route: router, OpenAPI docs, validation envelope, and RPC client wiring. Use when adding or modifying routes in api/hono."
```

An agent reads those descriptions, matches the task in front of it against the "Use when…" trigger, loads the one skill that fits, and follows the procedure verbatim. Only the descriptions are scanned up front, so the whole catalog costs almost nothing in context until one is needed; the full procedure loads only on a match.

When you don't know where to start, the `codebase-map` skill orients first; it maps where each kind of change lives and how types ripple across the stack. It is the one skill worth reading before you have a specific task.

## The catalog

The skills, arranged as the arc of a real task, **Navigate** to find your way, **Build** the feature, **Operate** the running app, **Maintain** the scaffolding, **Ship** the change:

| -------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Navigate | `codebase-map`       | Orient fast: the "where do I edit for X" table and how a change ripples across the stack. Start here in unfamiliar territory.                                                              |
| Build    | `add-package`        | Add a shared workspace package the repo's way: skeleton, `types: ["bun"]` for Bun scripts, where output goes (`.generated/` or committed source).                                          |
| Build    | `api-endpoint`       | Add a typed Hono route the repo's way: router, validation envelope, OpenAPI, RPC wiring, and the restart-and-`curl` test.                                                                  |
| Build    | `db-migration`       | Change the Drizzle schema and apply it: `db:generate`, then `db:migrate`.                                                                                                                  |
| Build    | `design`             | The canonical UI conventions: spacing, color, cursor, typography, tokens. Follow it for any component work.                                                                                |

| Build    | `runtime-apis`       | Prefer Bun-native APIs; fall back to Node built-ins with the required `node:` prefix.                                                                                                      |

`agent-browser`, `portless` and `writing-for-agents` are vendored; every other skill is written for this repo. `agent-browser` (from [`vercel-labs/agent-browser`](https://github.com/vercel-labs/agent-browser)) is a discovery stub: its committed `SKILL.md` just points the agent at the live workflow (`agent-browser skills get core`), installed with `npm i -g agent-browser && agent-browser install`. `portless` (from [`vercel-labs/portless`](https://github.com/vercel-labs/portless)) is copied in full and self-contained. `writing-for-agents` (from [`mattpocock/skills`](https://github.com/mattpocock/skills)) is copied in full and sets how every skill here is written. `agent-browser` and `writing-for-agents` are recorded in `skills-lock.json` with the hash of what was installed, so `bunx skills@1.7.2 update` re-vendors them; re-vendor `portless` by copying it again. A re-vendor rewrites the folder, so what this repo adds goes back in afterwards: the `source:` line in the frontmatter on each, the `## Viewport` section on `agent-browser` that sets the default viewport, and the em-dash sweep (`rg -n $'\u2014'`), since upstream prose may carry one.

## Writing your own

Make a directory under `.agents/skills/<name>/`, add a `SKILL.md`, and the symlink carries it to every tool:

````markdown
---
name: deploy-preview
description: Ship a preview build to staging. Use when asked to deploy a preview.
---

# Deploy Preview

## Workflow

### 1. Build

```bash
bun run build
```
````

Write the body with the `writing-for-agents` skill loaded: it is the standard every skill here follows, from the description's trigger to each step's completion criterion. Keep it one task, one procedure, with the real commands and the real traps; a skill earns its place by encoding what an agent would otherwise get wrong. When a convention changes, update its skill in the same commit; `AGENTS.md` makes that rule load-bearing.
