ZeroStarter develops on `canary`, the default branch and the one every pull request targets; `main` is release-only, written by the release flow and never by a direct commit. So a contribution has one shape: a worktree off `canary`, docs in the same change, a pull request back into `canary`.

## When you need this

Before your first pull request to the starter. When a hook or a pull-request check refuses your change, see [Code Quality](/docs/manage/code-quality).

## Where to start

Read `AGENTS.md` (`CLAUDE.md` symlinks to it): the rules humans and agents work under, and a skills table naming a procedure for every recurring task. Run `codebase-map` to orient, then load the task skill that fits.

## Make the change

Work in a git worktree under `.claude/worktrees/`, one per change, branched from freshly fetched `origin/canary`, so the primary checkout's branch is never touched and the change builds on current `canary`:

```bash
git fetch origin canary && git worktree add .claude/worktrees/<name> -b <branch> origin/canary
```

`.gitignore` does not list `.claude/worktrees/`, so the primary checkout's `git status` shows it as untracked until you add that line to `.git/info/exclude`. It does list `node_modules/` and `.env*`, so a new worktree has neither: run `bun install` in it and give it its own `.env` before `bun run dev`, with `POSTGRES_URL` on a disposable container for database work (the `db-migration` skill).

Two skills shape what goes in. `doc-sync`: docs move with code, so a changed command, path, convention or skill is fixed across every documented surface in the same change. `gh-commit`: one logical unit per commit in the [Conventional Commits](https://www.conventionalcommits.org) format, which commitlint checks on the `commit-msg` hook.

Run `bun run check-types` (and, in the canonical starter, `bun run test`) before pushing, and expect the audit in the pull request's CI rather than on your push; [Code Quality](/docs/manage/code-quality#the-gates-in-order) says why for both.

## Open the PR

Describe the change and its motivation, note any migration step, and link related issues; for a breaking change or a large feature, open an issue first. By contributing you agree to the [MIT license](https://github.com/nrjdalal/zerostarter/blob/canary/LICENSE.md).

## Common questions

**My commit passed the hook, so why did CI fail on formatting?**

lint-staged formats only the staged files; CI runs `bun run format:check` over the whole tree, so drift in a file you never touched fails the pull request. Run `bun run format`, commit, push.

**Why does the audit ignore an advisory?**

Because it has no patched version, so none of the `audit` skill's fixes has a release to move to, and the skill's route for that case is to ignore it by ID. The comment above the audit command in `lefthook.yml` names each ignored package and why; each one's exit criteria are in `.github/notes/dependencies.md` (canonical starter).

## It's working if

- `git log --oneline origin/canary..HEAD` in your worktree lists only your own commits.
- Your pull request names `canary` as its base branch.
