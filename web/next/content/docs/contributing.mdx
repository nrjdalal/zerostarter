ZeroStarter develops on `canary`, the default branch and the one every pull request targets; `main` is release-only, written by the release flow and never by a direct commit. So a contribution has one shape: a worktree off `canary`, docs in the same change, a pull request back into `canary`.

## When you need this

Before your first pull request to the starter, or when a hook refuses a commit or a push you thought was fine.

## Where to start

Read `AGENTS.md` (`CLAUDE.md` symlinks to it): the rules humans and agents work under, and a skills table naming a procedure for every recurring task. Run `codebase-map` to orient, then load the task skill that fits.

## Make the change

Work in a git worktree under `.claude/worktrees/`, one per change, branched from freshly fetched `origin/canary`, so the primary checkout stays clean and the change builds on current `canary`:

```bash
git fetch origin canary && git worktree add .claude/worktrees/<name> -b <branch> origin/canary
```

Two skills shape what goes in. `doc-sync`: docs move with code, so a changed command, path, convention or skill is fixed across every documented surface in the same change. `gh-commit`: one logical unit per commit in the [Conventional Commits](https://www.conventionalcommits.org) format, which commitlint checks on the `commit-msg` hook.

The pre-commit hook formats, lints and builds but runs no `check-types`, so run `bun run check-types` (and, in the canonical starter, `bun run test`) before pushing; the pre-push hook on `canary` runs `bun audit --audit-level high --ignore GHSA-vfj7-8cjw-p6xm`; the pull request reruns the full gate on GitHub.

## Open the PR

Describe the change and its motivation, note any migration step, and link related issues; for a breaking change or a large feature, open an issue first. By contributing you agree to the [MIT license](https://github.com/nrjdalal/zerostarter/blob/canary/LICENSE.md).

## Common questions

**My commit passed the hook, so why did CI fail on formatting?**

lint-staged formats only the staged files; CI runs `bun run format:check` over the whole tree, so drift in a file you never touched fails the pull request. Run `bun run format`, commit, push.

**Why does the audit ignore one advisory?**

`GHSA-vfj7-8cjw-p6xm` covers every release of `braces`, has no patched version, and reaches only dev tooling (`shadcn`, `globby`). An ignore is what the `audit` skill falls back to when none of its three rungs (update the dependency, update its parent, override) can lift an advisory; its exit criteria are in `.github/notes/dependencies.md` (canonical starter).

**Why does the audit run on push, not on every commit?**

It queries the registry, so on pre-commit it failed offline commits and a new transitive advisory blocked every commit on `canary`. Pre-push, gated to `canary`, still stops a vulnerable dependency leaving your machine.

## It's working if

- `git commit -m "add page"` is refused with `type may not be empty`; `docs: add page` lands.
- A pull request into `canary` shows the **Audit, Lint, and Build** check.
