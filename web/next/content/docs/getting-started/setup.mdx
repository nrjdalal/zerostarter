Two commands take you from an empty directory to a running app, and one click signs you in: `bunx zerostarter init` scaffolds a product, `bun run dev` starts it. `init` writes everything `bun run dev` assumes (the `.env`, the dependencies, the database and its migrations, the first commits), so the only step that can skip is the database, and only when Docker is down; the **Next steps** note at the end of the run is where that shows.

## When you need this

A fresh machine, or a new product. An existing repo or a fork is `reinit` or `sync` on [The CLI](/docs/getting-started/cli), and restarting a stack you already have is the `dev` skill in [AI Skills](/docs/resources/ai-skills).

## Prerequisites

- **Bun.** The repo pins `bun@1.4.3` in the root `package.json`, and the CLI shells out to `bunx` and `bun` for every step, so run it with `bunx`, not `npx`.
- **Docker**, optional. With a daemon running, `init` provisions a local Postgres for you; without one you point `POSTGRES_URL` at a database yourself.

## `zerostarter init`

```bash
bunx zerostarter init
```

Run it in an empty directory of its own: the directory name becomes the project name. A directory with files in it prompts for a name and scaffolds into a subdirectory of that name, and a directory inside an existing workspace stops before writing anything, because `bun install` would climb into the parent lockfile.

One run fetches the latest starter without its sample content, rebrands it to the project name (the agent skills and `AGENTS.md` included), asks which optional surfaces to ship (the [CLI page](/docs/getting-started/cli) lists the flags and their defaults; each is flippable later in [Features](/docs/manage/features)), installs with Bun, commits on a `canary` branch with `main` seeded behind it, and writes `.env` from `.env.example` with a generated `BETTER_AUTH_SECRET` and `AGENT_SIGNIN_ENABLED=true`. Then it asks whether to provision a local Postgres, defaulting to yes when Docker is up: [pglaunch](https://github.com/nrjdalal/pglaunch) starts a container, `init` waits for it to accept connections, points `POSTGRES_URL` at it, and applies the migrations. `--db` skips that prompt, and `--yes` takes every default.

The run ends on `<name> is ready` and a **Next steps** note. With a database, that note is `bun run dev` alone.

<Callout type="warn" title="If Docker was down">

`init` leaves `POSTGRES_URL` empty, and the note says so: `set POSTGRES_URL in .env`, then `bun run db:migrate`. Until both are done, `bun run dev` fails the API's env check with `Invalid environment variables` naming `POSTGRES_URL`. Any Postgres works, a hosted one like [Neon](https://neon.com) included; the migrate script builds the env package first, and Drizzle Kit talks to the database through the Node `postgres` driver that `packages/db` carries, since it cannot use `bun:sql`, so the command runs on a fresh scaffold.

</Callout>

## `bun run dev`

```bash
bun run dev
```

Turborepo starts both apps through [portless](https://portless.sh), one proxy on `:1355` serving named `.localhost` hosts, so the URLs never depend on which port a process won. `init` names the hosts after the project, lowercased with every other character run turned into a hyphen (`My App` serves `my-app.localhost`); `<name>` below is that slug, and `zerostarter` in the starter itself:

- **web** (Next.js) at `http://<name>.localhost:1355`
- **api** (Hono) at `http://api.<name>.localhost:1355`, with the API reference at `/api/docs`

`PORTLESS=0 bun run dev` skips the proxy for fixed ports instead (web `:3000`, api `:4000`), which is what OAuth callback URLs expect, since providers reject `.localhost` redirect URIs (see [Callback URLs](/docs/manage/authentication#callback-urls)). `bunx portless list` prints the active hosts. Restarting, the `bun --hot` trap where a new route answers `NOT_FOUND`, and the detached start an agent needs are the `dev` skill in [AI Skills](/docs/resources/ai-skills).

## Sign in

A fresh scaffold has no OAuth configured, so **Login** in the navbar opens a dialog with one button, **Login (agents)**: `init` set `AGENT_SIGNIN_ENABLED=true`, and the route it posts to mints a real session with no OAuth round-trip, an `owner` the first time because that sign-in creates the account. It lands on `/dashboard`. The curl form is the `dev` skill's Agent login, and why the route cannot exist in a deploy is in [Working with Agents](/docs/getting-started/working-with-agents). Real users come from GitHub or Google in [Authentication](/docs/manage/authentication); each button appears once its credentials are set.

## Common questions

**Can I run it with `npx`?**

Not without Bun installed: `npx zerostarter init` on a machine without it used to die on the first spawn with `spawnSync bunx ENOENT`. It now stops before any prompt, prints the `bunx --bun zerostarter init` re-run, and offers to install Bun.

**What happens when I run `init` again?**

The database step is idempotent. pglaunch names its container after the directory and refuses a second one of the same name, but it still prints the running one's URL, so `init` reuses that container instead of failing, and `init` asks pglaunch for a fresh one only when that first run printed no URL; a migration that fails is a warning (`run bun run db:migrate`), never a new container. When `.env` already has a `POSTGRES_URL`, `init` leaves it alone and ignores `--db`.

**Can two checkouts run `bun run dev` at once?**

Under portless, yes: in a linked worktree each host is prefixed with the last segment of the branch name, on the same proxy, so `fix-ui.<name>.localhost:1355` and `<name>.localhost:1355` run side by side. `PORTLESS=0` serves one stack at a time, since both would bind `:3000` and `:4000`.

## It's working if

- `init` ends on `<name> is ready` and its **Next steps** note lists only `bun run dev`; a `set POSTGRES_URL in .env` line there means the database step was skipped.
- `bunx portless list` shows `<name>` and `api.<name>` (branch-prefixed in a worktree).
- `curl http://api.<name>.localhost:1355/api/health` prints `"message":"ok"`, and `http://<name>.localhost:1355/` answers 200.
- `http://api.<name>.localhost:1355/api/docs` renders the Scalar API reference.
- **Login (agents)** lands on `/dashboard`.
