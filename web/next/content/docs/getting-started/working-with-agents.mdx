An AI coding agent that opens most repositories has to guess: where routes live, what the response shape is, how to run the thing, how to log in and test. ZeroStarter hands it a playbook instead. Point Claude Code, Cursor, or your own agent at the repo and it can build a real feature (and check that it works) without you narrating every step.

The playbook ships in the repo and moves in the same change as the code, so what an agent reads is what the code does.

## When you need this

Reach for this page when you are handing the repo to an agent, or when one stalls on a step a human does by hand: running the stack, signing in, checking its work. For the skill catalog, see [AI Skills](/docs/resources/ai-skills); end-user agents that operate your product in production are your app to design.

## The loop

Scaffold, run, sign in, build, verify; the skill holds the commands:

| Step     | What happens                                                           | Skill                                    |
| -------- | ---------------------------------------------------------------------- | ---------------------------------------- |
| Scaffold | `bunx zerostarter init` writes `AGENT_SIGNIN_ENABLED=true` into `.env` | [the CLI](/docs/getting-started/cli)     |
| Run      | `bun run dev`, named `.localhost` URLs, branch-prefixed in a worktree  | `dev`                                    |
| Sign in  | one request mints a session as `LocalAgent`, no OAuth                  | `dev`, under Agent login                 |
| Build    | a route, a migration or a page, by its recipe                          | `api-endpoint`, `db-migration`, `design` |
| Verify   | drive the running app in a real browser, screenshot the result         | `ui-verify`, with `agent-browser`        |

### Skills

Each step's skill is a procedure an agent loads by its description, with this repo's conventions and traps; [AI Skills](/docs/resources/ai-skills) says how they load and lists them all. The `dev` skill, for instance, holds the trap that stalls agents most: `bun --hot` misses a file created after its importers reloaded, so a new router answers `NOT_FOUND` until a full restart.

A fork inherits all of it, rebranded: `init` ships every skill and `AGENTS.md`, and `sync` reconciles them per skill, keeping the ones you have edited; the rules, and the one case where an edit is replaced, are under [Skills you have customized](/docs/getting-started/cli#skills-you-have-customized).

### agent-browser

With the session in place, the vendored `agent-browser` skill drives the real app: open a page, read the accessibility tree as a snapshot with element refs, click, type, screenshot. The `ui-verify` skill is the procedure around it, before and after included.

## Local sign-in

Anything behind auth normally needs an OAuth round-trip an agent cannot complete. `POST /api/agents/sign-in-as` returns a real session in one request; the curl pair and the browser path (**Login**, then **Login (agents)**) are the `dev` skill's Agent login. The sign-in that creates the account makes it an `owner`; after that its rung stands, so you can demote it to see what a lower rung sees, and `bun run console:roles grant agent@local.host owner` puts it back.

The route mounts only when `NODE_ENV` is `local` **and** `AGENT_SIGNIN_ENABLED` is `true` (one predicate, `api/hono/src/lib/agent-signin.ts`). The stage alone would not do: `.env.example` ships `NODE_ENV=local`, so a self-host that copies it as it is would keep an admin-minting route reachable. The flag is the second lock: it ships blank in `.env.example` and defaults to false, and `init` turns it on only in the gitignored `.env`, so a fresh clone and any deployed default env answer `404` on the route, a deploy's `NODE_ENV` keeps it down regardless, and exposure takes two misconfigurations. The same predicate gates the route's `/api/auth/providers` advertisement, so the **Login (agents)** button never points at a route that is not there, and the button exists only in a dev build. A trusted `Origin` still guards each request.

## The context an agent reads

### llms.txt

Before it crawls the tree, an agent can read the docs as flat markdown at `/llms.txt` and `/llms-full.txt`; [llms.txt](/docs/manage/llms-txt) says what each file holds and how `codebase-map` uses the full one.

### Managed blocks in AGENTS.md

`AGENTS.md` (`CLAUDE.md` is a symlink to it) is hand-written apart from its two skills tables, which the `skills-manager` skill generates, and a fork's `sync` tracks edits to the rest, so an edited guide stays the fork's. Two tools would write a block of their own for AI coding agents, and both are off: Turbo's would land in the root guide, where in a fork it reads as an edit that stops the guide syncing. `next dev` upserts a managed block pointing at the installed Next docs when it detects an agent, creating `AGENTS.md` where none exists, which from `web/next/` means a second file; `agentRules: false` in `web/next/next.config.ts` turns it off. `turbo` writes one into the root `AGENTS.md` before repository-scoped commands when an agent is detected; `"agentGuidance": false` in the root `turbo.json` turns that off. Their docs match the installed versions, under `node_modules` at `next/dist/docs/` and `turbo/docs/`.

## Common questions

**Why did a managed block appear in `AGENTS.md`?**

Both writers are on by default, so a block in a diff means one of the switches above was removed, not that the block belongs there. Put the switch back: Next removes its block on the next `next dev`, while Turbo leaves its block for you to delete.

## It's working if

- After the `dev` skill's Agent login, `curl -sS -b cookies.txt "$API/api/v1/user"` returns a user named `LocalAgent`.
- In a dev build, **Login** opens a dialog with **Login (agents)** while `AGENT_SIGNIN_ENABLED=true`; blank it and restart, and the button is gone and the route answers `404`.
