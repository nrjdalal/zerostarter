ZeroStarter is one type-safe monorepo. A single type describes a row in Postgres, the API that returns it, and the component that renders it, so a change in the database surfaces as a compile error, not as a bug in production.

One exported `AppType` crosses every boundary: the web app imports the API's own type, so no client is generated and no schema is kept in sync by hand. Everything on this page is wired and running together, not only listed in `package.json`.

## When you need this

Reach for this page when you are judging whether the stack fits, or planning a change that crosses the database, the API and the UI at once. For where each file lives, see [Project Structure](/docs/getting-started/project-structure); for how the type crosses the wire, see [The Type-Safe API](/docs/getting-started/type-safe-api).

## The shape

Two deployable apps share the packages they both import:

![Architecture graph](/marketing/graph-build.svg)

A request flows in a straight line, and the types flow back:

```
Browser → Next.js (web) → typed RPC client → Hono (api) → Drizzle → Postgres
```

- **`web/next`** renders the UI and calls the API through a client that infers its types from the backend.
- **`api/hono`** owns the routes, validates input with Zod, and talks to the database.
- **`packages/*`** hold the pieces both apps share: the Drizzle schema, the auth instance, validated env, and the brand config.

Because it is one repository, there is one place to look, one version of every dependency (the Bun catalog in the root `package.json`), and one graph an agent or a new teammate can hold in their head.

## Why one type

The point is not "it uses TypeScript". It is that the _same_ type crosses every boundary:

- Rename a column in the Drizzle schema and the route that selects it stops compiling.
- Change a route's response and the frontend call to it stops compiling.
- There is no client to generate and no schema to keep in sync: `web/next` reads the `AppType` that `api/hono` exports.

You feel this most when you refactor: the compiler walks you from the database to the button, and nothing ships half-changed.

## Common questions

**Is Bun a lock-in?**

No, and it is not the differentiator either: the typed architecture is, and the stack is meant to evolve rather than freeze. The honest cost of leaving Bun today is a set of named files rather than a flag: the database client is Bun's SQL driver (`packages/db/src/index.ts`), the server adapter imports `hono/bun` (`api/hono/src/lib/server.ts`), and the rate limiter hashes API keys with Bun's `hash` (`api/hono/src/middlewares/rate-limiter.ts`). `web/next` already runs under Node in `next dev`; Docker and Vercel serve it under Bun.

**Can the frontend be swapped for TanStack Start?**

The API never imports from the web app, so the frontend is replaceable by design, and a complete migration exists on the branch `web/cutover`, verified locally against the full end-to-end suite. It is parked on its deploy: TanStack Start's SSR emits Bun-only `direct` streams, which Vercel's Node runtime rejects, and Vercel's Bun runtime does not trace the OG renderer into the function. Self-hosting the Docker image is the path that works; the starter tracks the state in `.github/notes/plans/tanstack-start-migration.md`.

## It's working if

- Rename a column in `packages/db/src/schema/` and `bun run check-types` fails in `api/hono`, naming the router that selects it.
- Rename a key in a route's response and the same command fails in `web/next`, naming the component that reads it.
- `bun run check-types` from the repo root reports either failure on its first run, since it rebuilds the API's declaration file before `web/next` reads it.
