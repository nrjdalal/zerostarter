The `zerostarter` CLI starts a project and keeps it current: `init` scaffolds a fresh product, `reinit` re-scaffolds a repo you already have, and `sync` re-baselines a fork on the latest starter without discarding its work. All three rebrand what they fetch to your project.

Every command fetches a subtree, never a remote: [gitpick](https://github.com/nrjdalal/gitpick) copies the starter's files at `main` (or `canary`) with no git history riding along, so a fork has no upstream to merge, and the boundary between what is yours and what is the starter's is a file, not a merge.

## When you need this

Scaffolding a product, re-scaffolding a repo that already has history and secrets, or re-baselining a fork on a newer starter. The first run, start to finish, is [Quickstart](/docs/getting-started/setup); what a fork does with the skills it inherits is [Working with Agents](/docs/getting-started/working-with-agents).

## Prerequisites

- Bun. The commands run under `bunx`, and when bun is missing the CLI offers to install it (`--yes` installs without asking; a non-interactive run without it prints the re-run line and exits).
- Git with a commit identity: `user.name` and `user.email` set, or a machine whose host name git can build an address from. `init` and `reinit` treat a failed commit as nothing to commit, so without an identity `init` into a target with no `.git` stops at `git branch main` with the files fetched and nothing committed (delete the directory before running it again, since a re-run takes it for a non-empty directory), and an in-place `init` or a `reinit` finishes without its commit.
- A clean working tree for `reinit` and `sync`. Both refuse uncommitted changes, because their rollback restores only what is committed.

## The commands

| Command  | Fetches                             | Commits?                                                                                                                                                             | Clean tree? | On failure                                                                                               |
| -------- | ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- | -------------------------------------------------------------------------------------------------------- |
| `init`   | `main`, or `canary` with `--canary` | Yes: two commits on `canary`, `main` seeded behind, when the target has no `.git`; one commit on the current branch when it converts a checkout with `.git` in place | No          | Stops where it failed; nothing is rolled back                                                            |
| `reinit` | `main`                              | Yes, on the current branch                                                                                                                                           | Yes         | Resets the tree to your last commit                                                                      |
| `sync`   | `main`                              | No: the diff stays in your tree for review                                                                                                                           | Yes         | Resets the tree to your last commit, except an install failure after the overlay, which leaves the files |

### `init`

```bash
bunx zerostarter init [dir]
```

Fetches the starter into `dir` (default `.`), rebrands it to the directory name, installs dependencies, commits (two commits or one, as the table above says), seeds `.env` (creates it from `.env.example` when missing, then sets a blank or missing `BETTER_AUTH_SECRET` to a generated secret and a blank or missing `AGENT_SIGNIN_ENABLED` to `true`), and offers to provision a local Postgres and migrate. The target names the project: an empty directory (or `.`) names it after itself, while one holding only `.git`, such as an empty clone, passes the emptiness check and then stops at the fetch, because gitpick refuses a directory that is not empty; a non-empty directory that is not already a starter prompts for a name and scaffolds into a directory of that name under the current directory, not under `dir`, and with `--yes` or without a terminal stops with `Directory is not empty` instead; a directory that already holds the starter is converted in place, where `--canary` is ignored since nothing is fetched. A target inside an existing workspace is refused, because `bun install` would climb into that workspace and fail.

| Flag                            | Default   | Effect                                                                                                            |
| ------------------------------- | --------- | ----------------------------------------------------------------------------------------------------------------- |
| `--yes`, `-y`                   | off       | Skip every prompt and take defaults; provisions Postgres when Docker is running.                                  |
| `--canary`                      | off       | Fetch the `canary` branch instead of `main`, for testing unreleased changes.                                      |
| `--db`                          | off       | Provision a local Postgres (pglaunch) and migrate; needs Docker; ignored when `.env` already sets `POSTGRES_URL`. |
| `--dry-run`                     | off       | Print target, name, mode and features; write nothing.                                                             |
| `--<feature>`, `--no-<feature>` | see below | Turn an optional surface on or off; any feature flag skips the interactive picker.                                |
| `--help`, `-h`                  | -         | Print usage.                                                                                                      |

The feature flags are `--allowlist`, `--api-docs`, `--blog`, `--docs`, `--internal-docs` and `--waitlist`, all on by default except `allowlist` and `waitlist`; `--no-<feature>` wins over `--<feature>`. Each gates a surface a fork can drop or enable later in its config, see [Features](/docs/manage/features).

### `reinit`

```bash
bunx zerostarter reinit [dir]
```

Deletes every file except the top-level `.git` and any `.env*` at any depth, fetches the latest `main`, rebrands to the directory name, installs, seeds `.env` as `init` does (so a blank or missing `AGENT_SIGNIN_ENABLED` becomes `true`), and commits on the current branch, then prints the next steps: `set POSTGRES_URL in .env` while `.env` has none, `bun run db:migrate`, `bun run dev` and `git push`, since it migrates nothing itself. There is no picker, no `--canary` and no `--db`: it takes `main` and the default features. `--yes`/`-y` skips the confirmation and `--help`/`-h` prints usage.

<Callout type="warn" title="reinit deletes files">

Committed files come back on rollback, but a gitignored file that is not `.env*` is gone for good, so commit or stash anything you want to keep first. That includes a linked worktree inside the tree, such as one under `.claude/worktrees/` that `.git/info/exclude` hides from the clean-tree check: only the top-level `.git` is kept, so the worktree loses every file but its `.env*`, uncommitted work included (its commits stay on its branch), and git lists it as prunable. Commit that work, or remove the worktrees, before `reinit`.

</Callout>

### `sync`

```bash
bunx zerostarter sync [dir]
```

Overlays the latest starter onto the fork: every shared starter file takes the upstream version (a local edit to one is replaced), the fork's own paths come back (next section), the root `package.json` identity and each workspace manifest's extra dependencies are re-merged over the starter's, the portless dev-URL names are re-applied, and the skills and agent guide are reconciled per file. It does not commit: the result is a diff in your working tree to review with `git status` and commit yourself, `.agents/skills/.sync.json` included. The overlay and the reconcile run under rollback; `bun install` runs after them, so an install failure leaves the synced files in place and `bun install` on its own is the fix. A fork whose `AGENTS.md` predates the generated skills tables gets a warning naming the two marker pairs to add, since its own pre-commit hook fails without them.

## The fork boundary

The boundary is the starter's root `.gitpickignore`, fetched from GitHub's `main` on every sync, while an in-place `init` reads the checkout's own copy (gitpick never carries the file into a fork), so a sync is measured against upstream's current file. It has two parts: the excludes, paths a fork never receives, and the `PRESERVE_ON_SYNC` line, paths `sync` restores after the overlay. The boundary applies to gitpick fetches only; a plain `git clone` still gets the whole repository.

| Path                                                                                                                                    | At `init`                                                                                                                                              | At `sync`                                                                                                           |
| --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| `web/next/content/`, `web/next/public/`                                                                                                 | Fresh stubs: a docs index, a blog index with one sample post, the console docs index, an empty `public/`                                               | Never fetched, so yours stays                                                                                       |
| The `(marketing)` route group (`/`, `/hire`, `/resume`) with `components/marketing/`, `lib/marketing/` and `fonts/marketing/`           | Never received on a fetch (an in-place `init` removes them); a fresh `app/page.tsx` is written and the Hire entry is stripped from `common/navbar.tsx` | Never fetched; the Hire entry is stripped again                                                                     |
| `packages/config/src/site.ts`, `README.md`, the root `package.json` identity (name, version, author fields)                             | Regenerated from the project name                                                                                                                      | `site.ts` and `README.md` never fetched; `package.json` fetched, its identity re-merged over the starter's manifest |
| `packages/cli/`, `tests/`, `.github/notes/`, the CLI release workflow, and the rest of the starter's own files `.gitpickignore` lists   | Never received on a fetch; an in-place `init` removes them                                                                                             | Never fetched                                                                                                       |
| `AGENTS.md`, `bun.lock`, `packages/db/drizzle/`, `packages/db/src/schema/`, `web/next/docs.config.ts`, the favicon (`PRESERVE_ON_SYNC`) | `AGENTS.md` shipped rebranded; `docs.config.ts` regenerated as a stub listing only the docs and console docs index pages; the rest shipped whole       | Restored after the overlay, and a starter file the overlay added under one of them is removed                       |
| Everything else                                                                                                                         | Shipped as fetched, except each skill's `SKILL.md` and the two apps' portless names, which are rebranded ([Rebrand](#rebrand))                         | Overwritten by the upstream version, except what [`sync`](#sync) re-merges, re-applies or reconciles                |

A clone that skips `init` draws the marketing line by hand: delete `web/next/src/app/(marketing)`, add an `app/page.tsx`, and remove the Hire link in `common/navbar.tsx`.

### Skills you have customized

`init` rebrands the skills in `.agents/skills/` and `AGENTS.md` with the directory name where the starter says `ZeroStarter` and its slug where it says `zerostarter`; a sync rebrands the ones it updates from the root `package.json` `name`, the slug, for both. The starter's skills and `AGENTS.md` name the brand only in the lowercase form (the dev hosts, the dev log path, the cookie host), so a project in `MyApp/` reads `myapp` there either way. Each skill the CLI syncs from the starter opens with a `[!CAUTION]` note whose `> Synced from` line is the opt-in (a vendored skill is written without one), and sync decides per skill, by its `SKILL.md` alone, whether an update is yours to take (any other file in the directory follows the overlay, as [Common questions](#common-questions) says):

| The skill                                                                                  | Sync does                                                                                                                                                           |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `source` is this repo, the `[!CAUTION]` note is intact, and the body is what the CLI wrote | Takes the update                                                                                                                                                    |
| `source: local`, a tool name (vendored), or another upstream                               | Keeps its `SKILL.md` as it is, and never restamps its `source`                                                                                                      |
| That note, or its `> Synced from` line, removed                                            | Yours; left alone                                                                                                                                                   |
| Edited since the CLI wrote it                                                              | Keeps your version and names it in the summary; to take upstream's, delete the skill directory, commit that, and sync again, since sync refuses an uncommitted tree |
| No record in `.sync.json` (scaffolded by an older CLI)                                     | Takes the update and names it; `git restore --source=HEAD -- .agents/skills/<name>/SKILL.md` brings an edit back                                                    |

The ledger, `.agents/skills/.sync.json`, records per skill a hash of the upstream file and of the file as written to your fork; comparing the prose itself cannot work, since sync rebrands the body. Commit it with the rest of the sync. `bun .github/scripts/skills-manager.ts --outdated` reads it to say which synced skills upstream has moved on, and which you have edited.

Two cases still replace an edited `SKILL.md`: a skill with no record (the table's last row), and a skill sourced from the starter that was edited before `init` converted the fork in place again. That `init` restamps every `source: local` skill as synced from the starter and records each skill, edits and all, as what the CLI wrote, so the next sync reads the edit as the CLI's own; a vendored skill keeps its tool `source` and stays yours. The same `init` also stamps a second `[!CAUTION]` note, its URL rebranded to the slug, into each skill that already had one: a starter skill loses it at the next sync, but a skill only the fork has gains another note on every sync, so delete the extras by hand.

`AGENTS.md` (`CLAUDE.md` symlinks to it) follows the same contract: while you have not edited it, sync hands you the starter's latest; once you have, it is yours and sync says so. An in-place `init` re-records it as the CLI's, like the skills, so the next sync replaces a guide you had edited with the starter's without naming it; take yours back from the diff before you commit. The generated skills tables do not count as an edit, so adding a skill of your own does not freeze the guide. A fork scaffolded before the guide shipped has the short stub older CLIs wrote: untouched, the next sync replaces it; written into, sync leaves it, and to take the starter's guide you delete `AGENTS.md`, commit that on its own, and sync again. On its own, because the pre-commit hook regenerates the tables inside `AGENTS.md` whenever a skill is staged, and fails while the guide is missing.

## Rebrand

`init` and `reinit` regenerate `packages/config/src/site.ts` from the project name (the name, plus a placeholder description, tagline and socials to fill in), rewrite the root `package.json` to name `<slug>`, version `0.0.0` and no author fields, rebrand the [portless](/docs/getting-started/setup) dev-URL names to `<slug>` and `api.<slug>`, and strip the demo `/hire` nav entry. In a repo that already has `v*` tags, set `version` back to at least the last tag before the next release, which stops on a tree below it ([Releases](/docs/manage/release#the-window)).

The app reads its identity from `@packages/config/site` (the metadata, the navbar, the OG images, `llms-full.txt`), so that file is the brand a visitor sees. Both apps import its built `dist`, which `bun run dev` builds once as it starts, so restart the dev server to see an edit. The dev hosts (`portless.name` in `web/next/package.json` and `api/hono/package.json`), the skills and `AGENTS.md` take the root `package.json` `name` instead, so renaming the project means changing both. A new `name` reaches them only when the next `sync` rewrites them, which also overlays the latest starter and leaves a skill or guide you edited on the old name; to move the dev hosts sooner, edit the two `portless.name` values by hand. The rebrand stops with an error when the starter's shape has drifted (a missing `portless` block, a marketing font in the shared `fonts.ts`, a Hire entry the strip did not catch) rather than commit a broken identity. `reinit` and `sync` then roll the tree back; `init` has no rollback, so it stops with the conversion half-applied and uncommitted.

Into a target with no `.git`, `init` also starts the repository: `canary` as the working branch, and `main` behind it at the scaffold commit, the starter as fetched, which has no `site.ts` and so does not build until the first release merges `canary` into it. There is no remote, so a bare `git push` stops with `No configured push destination`: create the GitHub repository empty (no README, license or `.gitignore`), add it as `origin` (`git remote add origin <url>`), and `git push -u origin canary` publishes `canary` while the pre-push hook prints steps for the repository's Actions settings, more than the release flow needs ([Releases](/docs/manage/release#prerequisites) names the one setting it does). A repository created with any of those files starts with a commit of its own on a default branch, usually `main`, that shares no history with `canary` and stays the default; the hook finds that `main` on the remote and pushes nothing. The next `git push` seeds `main` from inside the hook, as a separate push that starts no workflow, so the release PR opens on the first push that moves `canary` after it: that same push when it carries a new commit, otherwise the next one, or, without a commit, `gh workflow run auto-canary-into-main.yml --ref canary`. The hook does nothing for a remote that is not on GitHub. An in-place conversion of a checkout that already has `.git` gets its one commit on whatever branch is checked out, and `init` creates no branch, so `canary` and `main`, which the release flow runs between, are yours to create. See [Releases](/docs/manage/release#prerequisites).

## Common questions

**Sync overwrote a skill I had customized.**

Sync rewrites only a skill whose `source` is this repo and whose body is what the CLI last wrote, and a fork-authored, vendored, edited or note-less skill keeps your version, named in the summary. Two cases still replace an edit, both named under [Skills you have customized](#skills-you-have-customized), and a file beside the `SKILL.md` is replaced on every sync.

**`--outdated` says every skill differs from upstream.**

A copy of `skills-manager.ts` from before the ledger compares prose, which the rebrand guarantees never matches; `sync` brings the current one. That one compares the hash recorded in `.sync.json` against upstream `main`, the ref every entry records (an `init --canary` fork included), and says separately when you have edited a skill: an edited skill keeps its record and prints `edited here (sync keeps your version)`. A skill with no record prints `untracked`: one last synced by a CLI older than the ledger, or one sourced from another repository. The `customized here` hint on that line does not hold, since an edit never drops the record.

**Does a fork get the skills?**

Every skill and the agent guide ship to the fork, rebranded. The first CLI stripped them all, which is why a fork from that era has none; a `sync` brings them in.

**Does sync overwrite my migrations and schema?**

No: `packages/db/drizzle/` and `packages/db/src/schema/` are `PRESERVE_ON_SYNC`, restored after the overlay, and a starter migration the overlay added under them is removed, so the fork's migration history stays its own. The flip side is that an upstream schema change does not arrive through sync, and the auth side lives in two shared starter files the overlay replaces with the starter's copies: `packages/auth/src/schema.ts` comes back without your own plugins and `additionalFields`, and `packages/auth/src/index.ts` without any table you added to the adapter `schema` map it lists by hand. Put both back from the diff before you commit the sync, because the auth instance spreads the same declaration and runs without them until then:

- A column of yours that the starter's copy no longer declares and that is `NOT NULL` with no default, which is what the generator writes for a field not marked `required: false` unless it sets a static `defaultValue`, fails Better Auth's schema check under `Required columns Better Auth never writes`, so every Better Auth request and session read throws `Drizzle schema mismatch`, every `/api/v1` request with them ([The generated auth schema](/docs/manage/database#the-generated-auth-schema)). A nullable or defaulted one is only missing from the running app.
- A plugin restored without its table in the map fails the same check under `Missing tables`.
- Regenerated from the starter's copy alone, `packages/db/src/schema/auth.ts` loses your columns, and the next `bun run db:generate` writes a migration that drops them. The error's help line suggests that regeneration (`npx auth generate`), or making the columns nullable, giving them defaults or removing them; restoring the declaration is the fix that leaves your columns as they are.

The rest you port and migrate yourself.

**Can a synced skill have more than one file?**

Not as one unit. The CLI rebrands, records and protects `SKILL.md` alone, so a file the starter ships beside one reaches the fork through the overlay unrebranded, is overwritten by every sync without being named, whichever row of the table the skill falls in, and never shows in `--outdated`. The starter keeps each custom skill in one file for that reason; the vendored `writing-for-agents` carries two more files, which take the starter's version on every sync.

## It's working if

- `bunx zerostarter init <dir> --dry-run` prints `target`, `name`, `mode` (`fetch main` or `in place`) and `features`, and writes nothing.
- After `init` into a directory with no `.git`, `git branch` lists `canary` (checked out) and `main`, and `git log` shows the scaffold commit and the re-baseline commit.
- After `sync`, `git status` lists the changed files, `.agents/skills/.sync.json` among them once any skill took an update, and the summary names every skill it left alone.
