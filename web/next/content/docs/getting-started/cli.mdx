The `zerostarter` CLI starts a project and keeps it current: `init` scaffolds a fresh product, `reinit` re-scaffolds a repo you already have, and `sync` re-baselines a fork on the latest starter without discarding its work. All three rebrand what they fetch to your project.

Every command fetches a subtree, never a remote: [gitpick](https://github.com/nrjdalal/gitpick) copies the starter's files at `main` (or `canary`) with no git history riding along, so a fork has no upstream to merge, and the boundary between what is yours and what is the starter's is a file, not a merge.

## When you need this

Scaffolding a product, re-scaffolding a repo that already has history and secrets, or re-baselining a fork on a newer starter. The first run, start to finish, is [Quickstart](/docs/getting-started/setup); what a fork does with the skills it inherits is [Working with Agents](/docs/getting-started/working-with-agents).

## Prerequisites

- Bun. The commands run under `bunx`, and when bun is missing the CLI offers to install it (`--yes` installs without asking; a non-interactive run without it prints the re-run line and exits).
- A clean working tree for `reinit` and `sync`. Both refuse uncommitted changes, because their rollback restores only what is committed.

## The commands

| Command  | Fetches                             | Commits?                                           | Clean tree? | On failure                                                                                               |
| -------- | ----------------------------------- | -------------------------------------------------- | ----------- | -------------------------------------------------------------------------------------------------------- |
| `init`   | `main`, or `canary` with `--canary` | Yes: two commits on `canary`, `main` seeded behind | No          | Stops where it failed; nothing is rolled back                                                            |
| `reinit` | `main`                              | Yes, on the current branch                         | Yes         | Resets the tree to your last commit                                                                      |
| `sync`   | `main`                              | No: the diff stays in your tree for review         | Yes         | Resets the tree to your last commit, except an install failure after the overlay, which leaves the files |

### `init`

```bash
bunx zerostarter init [dir]
```

Fetches the starter into `dir` (default `.`), rebrands it to the directory name, installs dependencies, commits the pristine starter and then the rebrand, seeds `.env`, and offers to provision a local Postgres and migrate. The target names the project: an empty directory (or `.`) names it after itself; a non-empty directory that is not already a starter prompts for a name and scaffolds into a subdirectory of that name; a directory that already holds the starter is converted in place, where `--canary` is ignored since nothing is fetched. A target inside an existing workspace is refused, because `bun install` would climb into that workspace and fail.

| Flag                            | Default   | Effect                                                                                                            |
| ------------------------------- | --------- | ----------------------------------------------------------------------------------------------------------------- |
| `--yes`, `-y`                   | off       | Skip every prompt and take defaults; provisions Postgres when Docker is running.                                  |
| `--canary`                      | off       | Fetch the `canary` branch instead of `main`, for testing unreleased changes.                                      |
| `--db`                          | off       | Provision a local Postgres (pglaunch) and migrate; needs Docker; ignored when `.env` already sets `POSTGRES_URL`. |
| `--dry-run`                     | off       | Print target, name, mode and features; write nothing.                                                             |
| `--<feature>`, `--no-<feature>` | see below | Turn an optional surface on or off; any feature flag skips the interactive picker.                                |
| `--help`, `-h`                  | -         | Print usage.                                                                                                      |

The feature flags are `--allowlist`, `--api-docs`, `--blog`, `--docs`, `--internal-docs` and `--waitlist`, all on by default except `allowlist` and `waitlist`; `--no-<feature>` wins over `--<feature>`. Each gates a surface a fork can drop or enable later in its config, see [Features](/docs/manage/features).

### `reinit`

```bash
bunx zerostarter reinit [dir]
```

Deletes every file except the top-level `.git` and any `.env*` at any depth, fetches the latest `main`, rebrands to the directory name, installs, and commits on the current branch; the next step it prints is `git push`. There is no picker, no `--canary` and no `--db`: it takes `main` and the default features. `--yes`/`-y` skips the confirmation and `--help`/`-h` prints usage.

<Callout type="warn" title="reinit deletes files">

Committed files come back on rollback, but a gitignored file that is not `.env*` is gone for good, so commit or stash anything you want to keep first.

</Callout>

### `sync`

```bash
bunx zerostarter sync [dir]
```

Overlays the latest starter onto the fork: every shared starter file takes the upstream version (a local edit to one is replaced), the fork's own paths come back (next section), the root `package.json` identity and each workspace manifest's extra dependencies are re-merged over the starter's, the portless dev-URL names are re-applied, and the skills and agent guide are reconciled per file. It does not commit: the result is a diff in your working tree to review with `git status` and commit yourself, `.agents/skills/.sync.json` included. The overlay and the reconcile run under rollback; `bun install` runs after them, so an install failure leaves the synced files in place and `bun install` on its own is the fix. A fork whose `AGENTS.md` predates the generated skills tables gets a warning naming the two marker pairs to add, since its own pre-commit hook fails without them.

## The fork boundary

The boundary is the starter's root `.gitpickignore`, fetched from GitHub's `main` on every sync, while an in-place `init` reads the checkout's own copy (gitpick never carries the file into a fork), so a sync is measured against upstream's current file. It has two parts: the excludes, paths a fork never receives, and the `PRESERVE_ON_SYNC` line, paths `sync` restores after the overlay. The boundary applies to gitpick fetches only; a plain `git clone` still gets the whole repository.

| Path                                                                                                                                    | At `init`                                                                                                                                              | At `sync`                                                                                                           |
| --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| `web/next/content/`, `web/next/public/`                                                                                                 | Fresh stubs: a docs index, a blog index with one sample post, the console docs index, an empty `public/`                                               | Never fetched, so yours stays                                                                                       |
| The `(marketing)` route group (`/`, `/hire`, `/resume`) with `components/marketing/`, `lib/marketing/` and `fonts/marketing/`           | Never received on a fetch (an in-place `init` removes them); a fresh `app/page.tsx` is written and the Hire entry is stripped from `common/navbar.tsx` | Never fetched; the Hire entry is stripped again                                                                     |
| `packages/config/src/site.ts`, `README.md`, the root `package.json` identity (name, version, author fields)                             | Regenerated from the project name                                                                                                                      | `site.ts` and `README.md` never fetched; `package.json` fetched, its identity re-merged over the starter's manifest |
| `packages/cli/`, `tests/`, `.github/notes/`, the CLI release workflow, and the rest of the starter's own files `.gitpickignore` lists   | Never received on a fetch; an in-place `init` removes them                                                                                             | Never fetched                                                                                                       |
| `AGENTS.md`, `bun.lock`, `packages/db/drizzle/`, `packages/db/src/schema/`, `web/next/docs.config.ts`, the favicon (`PRESERVE_ON_SYNC`) | Shipped whole                                                                                                                                          | Restored after the overlay, and a starter file the overlay added under one of them is removed                       |
| Everything else                                                                                                                         | Shipped, rebranded                                                                                                                                     | Overwritten by the upstream version                                                                                 |

A clone that skips `init` draws the marketing line by hand: delete `web/next/src/app/(marketing)`, add an `app/page.tsx`, and remove the Hire link in `common/navbar.tsx`.

### Skills you have customized

The overlaid skills in `.agents/skills/` are rebranded to your project name (read from `package.json`), matching `init`. Each skill the CLI writes opens with a `[!CAUTION]` note whose `> Synced from` line is the opt-in, and sync decides per skill whether an update is yours to take:

| The skill                                                                                  | Sync does                                                                                                        |
| ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `source` is this repo, the `[!CAUTION]` note is intact, and the body is what the CLI wrote | Takes the update                                                                                                 |
| `source: local`, a tool name (vendored), or another upstream                               | Leaves it exactly as it is, and never restamps its `source`                                                      |
| That note, or its `> Synced from` line, removed                                            | Yours; left alone                                                                                                |
| Edited since the CLI wrote it                                                              | Keeps your version and names it in the summary; delete the skill directory and sync again to take upstream's     |
| No record in `.sync.json` (scaffolded by an older CLI)                                     | Takes the update and names it; `git restore --source=HEAD -- .agents/skills/<name>/SKILL.md` brings an edit back |

The ledger, `.agents/skills/.sync.json`, records per skill a hash of the upstream file and of the file as written to your fork; comparing the prose itself cannot work, since sync rebrands the body. Commit it with the rest of the sync. `bun .github/scripts/skills-manager.ts --outdated` reads it to say which synced skills upstream has moved on, and which you have edited.

`AGENTS.md` (`CLAUDE.md` symlinks to it) follows the same contract: while you have not edited it, sync hands you the starter's latest; once you have, it is yours and sync says so. The generated skills tables do not count as an edit, so adding a skill of your own does not freeze the guide. A fork scaffolded before the guide shipped has the short stub older CLIs wrote: untouched, the next sync replaces it; written into, sync leaves it, and to take the starter's guide you delete `AGENTS.md`, commit that on its own, and sync again. On its own, because the pre-commit hook regenerates the tables inside `AGENTS.md` whenever a skill is staged, and fails while the guide is missing.

## Rebrand: one edit, whole system

`init` and `reinit` regenerate `packages/config/src/site.ts` from the project name (the name, plus a placeholder description, tagline and socials to fill in), rename the root package to a slug and drop its author fields, rebrand the [portless](/docs/getting-started/setup) dev-URL names to `<slug>` and `api.<slug>`, and strip the demo `/hire` nav entry. Every surface reads its identity from `@packages/config/site`, so that one file is your brand. The rebrand fails loud rather than half-applying when the starter's shape has drifted (a missing `portless` block, a marketing font in the shared `fonts.ts`, a Hire entry the strip did not catch), so a fork never ships a broken identity.

`init` also seeds git: `canary` as the working branch with `main` behind it. Your first `git push` publishes `canary` and the next seeds `main`, both through a pre-push hook that prompts for the Actions permissions the release flow needs. See [Releases](/docs/manage/release).

## Common questions

**Sync overwrote a skill I had customized.**

It no longer does: sync rewrites only a skill whose `source` is this repo and whose body is what the CLI last wrote, and a fork-authored, vendored, edited or note-less skill keeps your version, named in the summary. The one exception is a fork last synced by a CLI older than the ledger: with no record to compare against, those skills take the update once, by name, and the edit is in the diff to restore.

**`--outdated` says every skill differs from upstream.**

An older checker compared prose, which the rebrand guarantees never matches. It now compares the hash recorded in `.sync.json` against upstream at the ref the skill was synced from, and says separately when you have edited it. A skill with no record reads as untracked: customized here, or synced before tracking existed.

**Does a fork get the skills?**

Every skill and the agent guide ship to the fork, rebranded. The first CLI stripped them all, which is why a fork from that era has none; a `sync` brings them in.

**Does sync overwrite my migrations and schema?**

No: `packages/db/drizzle/` and `packages/db/src/schema/` are `PRESERVE_ON_SYNC`, restored after the overlay, and a starter migration the overlay added under them is removed, so the fork's migration history stays its own. The flip side is that an upstream schema change does not arrive through sync: the auth tables regenerate with `bun run auth:schema` once the new `packages/auth/src/schema.ts` lands, and the rest you port and migrate yourself.

**Can a synced skill have more than one file?**

Not yet. The CLI tracks `SKILL.md` alone, so a sibling file reaches the fork through the overlay unrebranded, is overwritten by the next sync without being named, and never shows in `--outdated`. The starter keeps each custom skill in one file for that reason.

## It's working if

- `bunx zerostarter init <dir> --dry-run` prints `target`, `name`, `mode` (`fetch main` or `in place`) and `features`, and writes nothing.
- After `init`, `git branch` lists `canary` (checked out) and `main`, and `git log` shows the scaffold commit and the re-baseline commit.
- After `sync`, `git status` lists the changed files, `.agents/skills/.sync.json` among them once any skill took an update, and the summary names every skill it left alone.
