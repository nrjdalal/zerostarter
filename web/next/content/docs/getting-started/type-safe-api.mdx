One type describes the API: every route's path, input and response. The web app imports that type and the whole client falls out of it, so a call to a route that changed stops compiling, and nothing is generated or kept in sync by hand.

The type is the server's own. `api/hono/src/index.ts` exports `AppType = typeof routes`, and `web/next` reads it through `@api/hono`'s built `dist` rather than its source, so a stale build is a stale type.

## When you need this

Reach for this page when you are calling the API from the web app and want to know what a call gives back and what the compiler checks for you. For adding a route, the `api-endpoint` skill holds the recipe ([AI Skills](/docs/resources/ai-skills)); for the envelope and its error codes, see [API Conventions](/docs/manage/api-conventions).

## One type, one direction

`api/hono/src/index.ts` chains every router onto one `routes` object and exports its type as `AppType`. `web/next/src/lib/api/client.ts` imports that type from `@api/hono`, hands it to [Hono RPC](https://hono.dev/docs/guides/rpc)'s `hc`, and exports `apiClient`, so `apiClient.v1.session.$get()` carries the path, query, body and response the route declares. Rename the route, or drop a field from its response, and every call to it stops compiling.

The direction is one way: the API never imports from the web app, and the web app imports the API's declaration file, built into `@api/hono`'s `dist`. `bun run check-types` from the repo root rebuilds it first (turbo's `check-types` depends on `^build`), so the root command catches a rename that a check inside `web/next` alone would miss.

The same routes feed the API reference: `describeRoute` and the Zod schemas on each route generate `/api/openapi.json`, which `/api/docs` renders with [Scalar](https://scalar.com), so the document cannot describe a route that does not exist. Both sit behind the `apiDocs` [feature](/docs/manage/features#the-flags) in `packages/config/src/site.ts` and 404 while it is off (Better Auth's own reference under `/api/auth` is outside the flag, as its row says); 429 and 500 are documented on every method, and a route adds its own 400 and 401.

## Reading a response with `unwrap`

Every route the api defines answers in the envelope, `{ data }` or `{ error: { code, message } }`, apart from the exceptions [API Conventions](/docs/manage/api-conventions) lists, and `unwrap`, exported beside `apiClient`, reads it:

```ts
import { apiClient, unwrap } from "@/lib/api/client"

const { data, error } = await unwrap(apiClient.health.$get())
```

Exactly one side is non-null and `unwrap` never throws. `data` is the payload inside `{ data }`, typed from the route; `error.code` is a closed set you can `switch` on: the server's codes plus the two transport codes `unwrap` adds on the client, all listed in [API Conventions](/docs/manage/api-conventions#the-envelope-and-its-codes). The client sends `credentials: "include"`, so a route behind `authMiddleware` is the same call with the session cookie along. A client component reads it through TanStack Query as `web/next/src/components/common/access.tsx` does: the `queryFn` unwraps and throws on `error`.

## What the type does not cover

`AppType` types what Hono sees. Two surfaces the web app calls through `apiClient` hand their bodies to something else:

- **`/api/auth/*`**: the path is typed, so `apiClient.auth.providers.$get()` returns a typed envelope and `apiClient.auth["get-session"].$url()` builds the URL, but Better Auth's own bodies are not: `/get-session` and the wildcard pass its `Response` through untouched. For a typed session read, call `apiClient.v1.session.$get()` on the client, or the helper in `web/next/src/lib/auth/index.ts` on the server.
- **`/api/health/ws`**: the path is typed, so `apiClient.health.ws.$ws()` derives the socket URL from the same base, but the frames are not: a plain `WebSocket`, no envelope, listed in the reference as a `101`. Parse each frame and read only what you need, per [Realtime](/docs/getting-started/realtime).

## Common questions

**Why does `apiClient` not have the route I just added?**

The type travels through `@api/hono`'s built `dist`, so the web app sees a new route once that package is rebuilt: `bun run check-types` from the repo root does that first, `bunx turbo run check-types --filter=@web/next` does it for the one app, and `tsc` inside `web/next` reads the last build. The route also has to sit inside the `routes` chain in `api/hono/src/index.ts`, since `AppType` is `typeof routes`. If the type is there and the call still answers `NOT_FOUND`, the API's `bun --hot` missed the new file: restart the stack (the `dev` skill).

## It's working if

- In the editor, `data` after `unwrap(apiClient.health.$get())` completes to `environment`, `message` and `version`, the fields the route declares in `api/hono/src/index.ts`, and nothing else.
- `/api/docs` renders the reference and `/api/openapi.json` lists your route with a 429 on it while `apiDocs` is on; both 404 when it is off.
