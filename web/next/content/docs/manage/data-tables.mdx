A table here is composed, not configured: the page owns its [TanStack Table](https://tanstack.com/table) instance, and one module, `web/next/src/components/data-table.tsx`, supplies every piece, the way the [shadcn data-table guide](https://ui.shadcn.com/docs/components/base/data-table) builds one. A page picks the exports it needs and wires them to its own columns, fetcher and layout; there is no prop machine to outgrow.

Every table scrolls infinitely inside its own region with virtualized rows, its state lives in the URL, and a column's width is arithmetic over the sans's metrics rather than a number someone eyeballed. The console users table at `app/(console)/console/(access)/users/components/` is the reference every other table copies.

## When you need this

Reach for this page when you are adding a table, or when a column sizes, sorts or selects in a way you did not expect. The `design` skill holds the conventions a table follows (cells, ids, sort UI, time columns); this page holds the mechanics beneath them. For the endpoint a server-driven table talks to, see [API Conventions](/docs/manage/api-conventions).

## The exports

| Export                               | Provides                                                                                                                                                                                                                                                                            |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `applyColumnManager`, `ColumnConfig` | The fold that applies the per-column layout contract onto the defs, and the contract's type, from `lib/data-table-layout.ts`, which also holds `acceptedFacet`, `facetOptions` and `resolveSort`: no React, no DOM, tested under `tests/web/next/src/lib/` in the canonical starter |
| `DataTable`                          | The virtualized infinite-scroll region: sticky header, windowed rows, load-more near the bottom, a spinner, an `Empty` fallback, an inline Retry when a batch fails, the status line, and the floating selection bar                                                                |
| `DataTableCellText`                  | A text cell shaped by its column config: truncate with a tooltip only when cut, or wrap and let the measured row grow                                                                                                                                                               |

| `DataTableFacetedFilter`             | A multi-select value filter in a command palette; counts render only where faceted row models are registered, which the shared `features` leaves out, since a count over loaded rows would understate a server-filtered total                                                       |
| `DataTableToolbar`                   | The search box, a children slot for filters, reset, column visibility, and an `actions` slot for table-level actions                                                                                                                                                                |

| `features`                           | The registered TanStack features and row-model slots, from `lib/data-table-features.ts`; v9 bundles nothing by default, so every `ColumnDef`, `Column` and `Table` type is generic over this one value                                                                              |
| `selectColumn`                       | The checkbox column, taking the label that names each row for a screen reader                                                                                                                                                                                                       |

| `useDataTableState`                  | The URL layer alone (`q`, `sort`, filter arrays through [nuqs](https://nuqs.dev)) for a client-side table; given the sortable ids, it drops a URL sort naming a column the table does not have                                                                                      |

## Column config

Layout is data that lives beside each table: its `data-columns.tsx` exports the column defs (header, cell, `meta.label`) and a `Record<string, ColumnConfig>` written in column order.

```ts
type ColumnConfig = {
  align?: "center" | "left" | "right" // default left
  extra?: number // allowance over a measured label, default 10
  flex?: boolean // default false
  width?: number // spacing units; omit to measure the header
  wrap?: boolean // default false: truncate with a tooltip
}
```

Widths are Tailwind spacing units (one unit is `0.25rem`, 4px at the default scale) rendered through `calc(var(--spacing) * n)`, so a table rides the theme token. A fixed column is exact; a flex column treats the number as a floor and grows. A column with no entry takes the defaults, so it cannot inherit TanStack's pixel-minded `size` of 150.

Omit `width` and the column sizes itself: the label's advance in the header font plus `extra`, rounded up to a multiple of three units (12px at the default scale). The font is bundled data, not a canvas measurement: `packages/scripts/src/data-table-metrics.ts` runs ahead of `build`, `check-types` and `dev:app`, parses the sans woff2 at the header's weight and size, and writes per-character advances and kerning deltas to `.generated/data-table-metrics.json` (the `generated/*` alias), so a label measures identically on server and client and SSR ships final widths. `lib/data-table-layout.ts` imports that file and `data-table.tsx` re-exports the layout, so the metrics land in whichever chunk imports any `data-table` export: a widely shared module that imported one would carry them onto every page. `meta.label` is the one source for the header text, its width and its view-options entry. Swapping the sans is the `fonts` skill, whose "Wire the role" step moves the `FONT` path that script reads.

`flex` decides who grows: it reaches capability back to every column before it, and of the visible capable columns only the last grows, so hiding that column hands growth to the one before it. A table with no flex column spreads its widthless columns instead, and dead space never trails a row. A centered column drops its horizontal padding, since the shadcn cell strips its right padding when it holds a checkbox and a padded center would skew. When a column takes `extra` over `width`, how an id is named, and where a select column earns its place are the `design` skill's rules.

## Server-driven tables

The users table resolves sorting, search and filters on the API and streams rows in on scroll through [TanStack Query's infinite pattern](https://tanstack.com/query/latest/docs/framework/react/guides/infinite-queries). Its wiring, from `app/(console)/console/(access)/users/components/data-table.tsx`:

```tsx
const { selected, table, tableProps } = useDataTable({
  columnConfig: usersColumnConfig,
  columns,
  defaultSorting: DEFAULT_SORTING,
  enableRowSelection: true,
  fetchPage: fetchUsers, // (input: DataTablePageInput) => Promise<DataTablePage<Row>>
  filterIds: ["role"],
  getRowId: (row) => row.id,
  queryKey: "console-users",
})

<DataTableToolbar table={table} searchMaxLength={Q_MAX} searchPlaceholder="Search users...">
  <DataTableFacetedFilter column={table.getColumn("role")} options={ROLE_OPTIONS} title="Role" />
</DataTableToolbar>
<DataTable {...tableProps} aria-label="Users" selectionActions={/* Ban, Unban, Set role */} />
```

- `fetchPage` receives `{ filters, page, perPage, search, sorting }` and returns `{ rows, hasNextPage, page, total }`: `getNextPageParam` reads `hasNextPage` off the last page rather than comparing what has loaded against a total that can move mid-scroll. Column ids map onto the endpoint's sort whitelist through a `satisfies`-checked record read by `resolveSort`, so a server rename is a compile error, and the row type derives from `InferResponseType`.
- `selected` is the filtered selection model as rows, which is what a selection action acts on. Selection covers loaded rows only, so "12 of 25 row(s) selected" can sit next to a larger total, and it resets when search, sort or a filter changes. The toolbar's `searchMaxLength` mirrors the endpoint's `q` cap so a long paste cannot fail the request.
- `defaultSorting` applies as real table state when the URL carries no sort, so the header chevron and `aria-sort` show it while the URL stays clean; a hand-written multi-sort URL clamps to its first entry. `keepPreviousData` holds rows on screen while a sort or filter refetches.
- A first load that errors renders the message with a Retry rather than "No results", so an outage never reads as an empty table, and a failed batch parks load-more rather than retrying forever. `DataTable`'s optional `empty` prop, the page's own message for a table that holds nothing, is kept for that genuine zero-row case: it shows only while no search or filter is active, since a filter that matches nothing gets "No results".
- The endpoint (`api/hono/src/routers/admin.ts`) whitelists sort columns and appends `nulls last` to every one, escapes `LIKE` wildcards through `escapeLike`, filters roles with null as `user`, breaks ties on `asc(user.id)`, counts the total on every batch, and sits behind the console gate.

## Client-side tables

For a payload that fits in the browser, skip `useDataTable`: wire `useDataTableState`, `applyColumnManager`, `defaultColumn: { minSize: 0 }` (sizes are spacing units, and TanStack's pixel clamp would inflate them) and the shared `features`. All rows exist up front, the virtualizer windows them, and `DataTable` gets no `onLoadMore`, the callback `useDataTable` hands it to fetch the next batch near the bottom. Naming a filter or sort function by string means registering it first: v9 resolves `filterFn` against `filterFns` on `features` and `sortFn` against `sortFns`, and anything unregistered is a compile error. The console resolves both on the server, so `data-table-features.ts` registers neither map and no faceted row model; a client-side table adds what it names there, once, for every table.

## Filling the viewport

The table takes all the height below the page header, so it needs a definite height to scroll in its region; the classes that give it one are in the `design` skill's "Layout and landmarks" section. Without a definite ancestor the region grows with its content, the page scrolls instead of the table, and the always-near bottom loads every batch at once.

<Callout type="warn" title="TanStack Table and the React Compiler">

`useTable` mutates one stable instance during render, so a compiler-memoized component comparing that identity freezes one render behind and misses a sort, a selection or a new batch. The module carries `"use no memo"` at the top, and so must every file that reads a `table` or `column` instance.

</Callout>

## Accessibility

Grid and flex display strip implicit table semantics, so `DataTable` restates every structural role and reports `aria-rowcount` for the full set with per-row `aria-rowindex`. The scroll region is named and focusable (`role="region"`, `tabIndex={0}`), sorted headers set `aria-sort`, the sort icons are labeled native buttons, the search is labeled, and tooltips mirror truncated values.

## Common questions

**Why TanStack Table v9?**

Because the shadcn recipe this module is modelled on is written for v9, so the guide stays a working reference for the module. v9 is a rewrite rather than a rename: nothing is bundled by default, a method exists on the instance only when its feature is registered and a row model only when its slot is filled, and `lib/data-table-features.ts` is where both happen.

**Why is there no numbered pagination?**

Because a fixed region that streams batches keeps the toolbar and header in view while the reader scans, and never resizes with its content. The module exports no pagination component, and `useDataTableState` keeps only `q`, `sort` and the filters in the URL, no page. The endpoint still takes `page` and `perPage`, so a numbered UI could be built on it, but nothing in the module renders one.

**Can a row be skipped or repeat while I scroll?**

Yes. The endpoint pages by offset, so a row inserted or deleted above the current window between two batches shifts every later row by one: the next batch can start one row late, or repeat the row that was last. A repeat is a duplicate `getRowId`, so a duplicate React key and a selection that aliases. Keyset pagination is the remedy, and the sort order already ends on the unique tiebreaker it needs; the canonical starter keeps the change's open shape in `.github/notes/plans/data-table-offset-pagination.md`.

**How many requests does a bulk action send?**

One per `MAX_BATCH` ids, the set route's cap in `packages/config/src/console.ts`. The selection goes to a [set route](/docs/manage/api-conventions#lists-and-sets) as `{ ids }` and each id answers with its own outcome, so "2 changed, 1 refused" is reported rather than claimed. `runBatched` in `web/next/src/lib/api/bulk.ts` sends a larger selection as sequential slices of that size, and a request refused as a whole stops the rest, counting their ids as failed, rather than spending the rate limit on requests doomed the same way.

## It's working if

- `/console/users` fills the viewport with the table scrolling inside its region and the page itself never scrolling; the status line counts up (`25 of 61`) as you reach the bottom.
- A new column with only a `meta.label` and no config entry gets a header wide enough for its label and sort icon, with no manual width.
- Sort, search or filter, then reload: the URL carries the state and the table comes back the same.
