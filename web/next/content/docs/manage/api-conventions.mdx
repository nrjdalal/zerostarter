A response from the api is one of two shapes: a success carries `data`, a failure carries `error` with a stable `code` and a human `message`. These answer in their own formats instead:

- `POST /api/agents/sign-in-as`: a 302 to `/dashboard` with no body on success; its failures are enveloped.
- Better Auth's `/api/auth/*`, all but `/api/auth/providers`.
- `/api/docs`: the Scalar reference, an HTML page.
- `/api/health/ws`: a 101, then bare JSON frames ([Realtime](/docs/getting-started/realtime)).
- `/api/openapi.json`: the OpenAPI document.

One envelope means one way to read a response and one closed set of codes to `switch` on, on the server and in the web client alike.

A handler never builds `{ error }`: it returns `c.json({ data })` and otherwise throws an `ApiError` (a domain code) or Hono's `HTTPException`, and `errorHandler` in `api/hono/src/lib/error.ts` turns the throw into the envelope through `jsonError`, the one function in that file that writes `{ error }`. Three failures never throw and call `jsonError` directly: the 401 from `authMiddleware`, the 429 from the rate limiter and the 404 from `app.notFound`, so a change made in `errorHandler` alone misses them. `errorHandler` is also the one place that decides what a 500 is allowed to say.

## When you need this

Reach for this page when you are reading a response, in the Scalar reference at `/api/docs`, a `curl` or a failing test, or writing a handler and need to know what it may answer and what already ran before it. For the envelope as a typed `{ data, error }` result in the web app, see [The Type-Safe API](/docs/getting-started/type-safe-api); for the router template and the `curl` that proves a new route, the `api-endpoint` skill under [AI Skills](/docs/resources/ai-skills).

## The envelope and its codes

A success is `{ data }`. A failure is `{ error: { code, message } }` plus whatever the throw site attached: a validator's 400 carries `issues`, the failing fields, which ride through `ApiError`'s `extra` and survive `unwrap` on the client.

`errorHandler` (registered with `app.onError` in `api/hono/src/index.ts`) dispatches in order: an `ApiError` keeps its status and code; a `ZodError` becomes a 400 `VALIDATION_ERROR`; any other `HTTPException` keeps its status, mapped to a code where one exists and `ERROR` where none does; anything else is a 500 `INTERNAL_SERVER_ERROR`. Two answers never reach a handler: a path nothing matches is a 404 from `app.notFound`, and a route behind a feature that is off answers the same 404 from `requireFeature` (`api/hono/src/middlewares/feature.ts`), so a disabled surface looks absent to whoever gets that far. Under `/api/v1` both wait behind gates mounted on every path below them, matched or not: `authMiddleware` answers a caller without a session with the 401, and under `/api/v1/admin` the console gate answers a non-admin with the 403, so a path that does not exist answers there like the console's allowlist and waitlist routes behind a flag that is off, and only a caller past the gates sees the 404. Probe a new `/api/v1` route signed in (the `dev` skill's Agent login), since without a session a missing route and a present one both answer 401.

The codes are the `ERROR_CODES` list in `lib/error.ts`, one `as const` array the `ErrorCode` union, the OpenAPI schema and the web client all derive from. On the web, `unwrap` adds two transport codes of its own, `NETWORK_ERROR` and `UNKNOWN_ERROR`, so `error.code` there is this list plus those two and nothing else. Adding a code means extending that list, which keeps this table honest. The status is the whole request's; a set route's per-row refusals reuse three of these codes inside a 200 ([Lists and sets](#lists-and-sets)):

| Code                    | Status   | When                                                                                     |
| ----------------------- | -------- | ---------------------------------------------------------------------------------------- |
| `AGENT_LOGIN_FAILED`    | 500      | Local agent sign-in failed (`routers/agents.ts`)                                         |
| `BAD_REQUEST`           | 400      | Malformed JSON or form body (Hono's own `HTTPException`)                                 |
| `CONFLICT`              | 409      | The value already exists (an allowlist rule added twice)                                 |
| `ERROR`                 | (varies) | An `HTTPException` whose status maps to no code                                          |
| `FORBIDDEN`             | 403      | Below the rung a route asks for, or banned; `/headers` outside `local` and `development` |
| `INTERNAL_SERVER_ERROR` | 500      | An unhandled error                                                                       |
| `NOT_FOUND`             | 404      | No such route, or its feature is off                                                     |
| `TOO_MANY_REQUESTS`     | 429      | Over the rate limit                                                                      |
| `UNAUTHORIZED`          | 401      | No session, or an invalid one                                                            |
| `VALIDATION_ERROR`      | 400      | The request failed its schema; `issues` names the fields                                 |

## Lists and sets

A list names its collection for what it holds (`events`, `rules`, `signups`, `users`) and spreads the paging fields beside it, both from `api/hono/src/lib/paging.ts`:

| Field         | Meaning                                                   |
| ------------- | --------------------------------------------------------- |
| `hasNextPage` | The end signal, computed server-side from the three below |
| `page`        | The page asked for, echoed                                |
| `perPage`     | The page size asked for, echoed                           |
| `total`       | Every matching row, counted                               |

Flat siblings beside the collection, not a nested paging object, is the shape most REST frameworks answer and the one a reader expects. `total` stays because the console shows the count, and every batch counts again beside its rows. That is cheap while a table is small, and only `allowlist` stays the size of your staff: `user` grows with every account, `waitlist` with every signup and `activity` without bound, so those are where counting becomes the expensive half ([Waitlist](/docs/manage/waitlist) has the arithmetic), and where a large install would count on the first page only, or drop the count. Keys order by relevance first, then A→Z: the collection is what the response is about, so it leads and the paging fields follow, the same on every list, while a row's own fields are plain A→Z with `id` among them. Paging is by offset (`?page=2&perPage=25`), which can skip or repeat a row when rows shift between requests; the shape is additive, so a `nextCursor` can join it without moving anything.

A set route acts on rows the caller picked: ban a selection, change a role across it, remove several rules. Every guard runs per target, so one request can change three rows and refuse two, and `api/hono/src/lib/batch.ts` holds the shape that answers that, in the order a request meets it: what it sends, what comes back, then the limits it runs under:

| Rule                               | What it means                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ids travel in the body             | `{ ids: string[], ...fields }` on `DELETE /allowlist`, `PATCH /users/role`, `PATCH /users/status` and `DELETE /waitlist` under `/api/v1/admin`, with no `/users/:id/role` beside them; a single row is a set of one                                                                                                                                                                                                                                                                                                                                                             |
| 200 with one outcome per id        | `{ data: { results } }`, each `{ id, ok: true }` or `{ id, ok: false, code, message }`, in the order asked, never 207                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `{ error }` means nothing happened | The request was refused as a whole (no session, not an admin, a malformed body, more than `MAX_BATCH` ids), so there are no outcomes                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| A refusal code is narrower         | A row can be `CONFLICT` (its role changed mid-request), `FORBIDDEN` (the guard refused it) or `NOT_FOUND` (it is gone); anything else is a whole-request failure the envelope already covers                                                                                                                                                                                                                                                                                                                                                                                    |
| Capped at `MAX_BATCH`              | 100 ids per request (`packages/config/src/console.ts`), deduplicated; the console splits a larger selection into serial chunks                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| One transaction per request        | The set's writes and their activity lines commit or roll back together. On `PATCH /users/role` and `PATCH /users/status` targets are read without a lock and each write is a compare-and-set on the role it read, so another admin's role change landing in between makes that row answer `CONFLICT`, while a concurrent ban or unban is not in the check and the later write wins. The delete routes remove their rows in one statement, so an id another request already removed answers `NOT_FOUND`. The guarantee is per request: a 250-row selection is three transactions |

The `api-endpoint` skill's set-route section carries the steps, from `batchInput` to `runBatched` on the web.

## What runs before your handler

The first three rows run on every request, in that order, from `api/hono/src/index.ts` (`cors()` answers a preflight itself, so the other two never see one); the rest attach where their row says. A row that refuses answers in the envelope, and the handler never sees the request it refused; `cors()` and `logger()` refuse nothing:

| Middleware       | Where                                                                                              | What it refuses                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cors()`         | Every route                                                                                        | Nothing on the server: it answers every preflight with a 204 and sets `Access-Control-Allow-Origin` only for an origin in `HONO_TRUSTED_ORIGINS`, so a browser page on another origin cannot read the response and does not send a request that needs a preflight (a JSON body, an `authorization` header, `DELETE`, `PATCH` or `PUT`). A simple `GET` or form `POST` from any origin still reaches the handler, and the `SameSite=Lax` session cookie rides along when the page is same-site (on a custom domain, any host under the cookie's parent domain) or is a link navigating with `GET`. The starter's own `POST` routes with a body (adding an allowlist rule, joining the waitlist) refuse a form one only because they validate JSON, so a route of yours that changes state takes a JSON body, or checks `Origin` itself as the agent sign-in does, and changes nothing on `GET`. `curl` sends no preflight at all |
| `logger()`       | Every route                                                                                        | Nothing; two lines per request on the api's stdout, `<--` with the method and path on arrival and `-->` with the status and time once answered                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Rate limiter     | Every route                                                                                        | 429 `TOO_MANY_REQUESTS`, keyed by IP; [Rate Limiting](/docs/manage/rate-limiting) has the tiers                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `authMiddleware` | `/api/v1/*`                                                                                        | 401 `UNAUTHORIZED` without a session; otherwise sets `user` and `session` on the context and adds the per-user limiter at twice the budget                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Console gate     | `/api/v1/admin/*`                                                                                  | 403 `FORBIDDEN` below `admin` on the role ladder or when banned, read past the [cookie cache](/docs/manage/authentication#sessions-and-cookies) so a demotion lands on the next request. A console ban deletes the person's sessions, so their next request finds none and answers 401 `UNAUTHORIZED`; the 403 covers a ban written straight to the database. That is one uncached session read per admin request, paid per batch by a surface that fetches in batches                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `requireFeature` | `/api/docs`, `/api/openapi.json`, `/api/waitlist`, and the console's allowlist and waitlist routes | 404 `NOT_FOUND` while the feature in `packages/config/src/site.ts` is off, on the console's routes only after the two gates above have passed; `/api/agents/*` 404s the same way unless `NODE_ENV` is `local` and `AGENT_SIGNIN_ENABLED` is on (`api/hono/src/lib/agent-signin.ts`)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

## Common questions

**Why is a refused row a 200 and not a 403?**

Because the status describes the request, which ran, and the guard that said no runs per row. The refusal arrives as `ok: false` with `FORBIDDEN` and the guard's message inside `{ data }`, and the client raises it from the outcome; the console's row menu, which sends a set of one, does exactly that. 207 Multi-Status would add nothing: it is still 2xx, so `unwrap` would treat it like a 200, while each set route's declared responses and the reference would carry a status nothing else uses.

**Why is my 500's message just "Internal Server Error"?**

Because an unhandled error's real message reaches the envelope only when `NODE_ENV` is `local`; everywhere else `errorHandler` substitutes the generic line so a stack trace or a database error never leaks. Read the api's log for the cause. A thrown `ApiError` or `HTTPException` carries a message a developer wrote, so those are always shown.

**Why does a list carry `hasNextPage` when it already carries `total`?**

Because the two can disagree. A client inferring the end from `total` compares what it has loaded against a count that moves when rows are deleted mid-scroll, and under an infinite list a stale one keeps asking for a page that no longer exists. The server knows, so the server says.

**Can a route add its own error code?**

Only by extending `ERROR_CODES` in `lib/error.ts`, so a code outside the list cannot be thrown and a `switch` over it stays exhaustive. A set route's per-row codes are a `satisfies`-checked subset of the same list, so there is no second vocabulary.

## It's working if

With `API=$(bunx portless get api.<name>)` from a running stack (the `dev` skill), `<name>` being the project's slug, its name lowercased and hyphenated (`zerostarter` in the canonical starter):

- `curl "$API/api/nope"` answers `{"error":{"code":"NOT_FOUND","message":"Not Found"}}`.
- With the waitlist feature on (`features.waitlist` in `packages/config/src/site.ts`), `curl -X POST -H "Content-Type: application/json" -d '{"email":"nope"}' "$API/api/waitlist"` answers a 400 `VALIDATION_ERROR` whose `issues` names `email`; with it off, the route answers the `NOT_FOUND` above.
- `curl "$API/api/v1/session"` without a cookie answers a 401 `UNAUTHORIZED`.
