The console is the staff-facing area behind `/console`, and a rule here is how you let a whole domain (`@example.com`) or a single address (`ada@example.com`) into it without finding each person in the Users table. Signing up stays open to everyone and every signed-in person gets the dashboard; a rule decides only who reaches the console. Manage the list at **Console > Access > Allowlist**, admin and above.

A rule grants `member` once per account, on sign-in, only where `user.role_set_at` is empty. That column is the whole model: every deliberate rung change stamps it, by a rule or by a person, so a rule reaches someone nobody has ruled on, never overrules an admin, and never undoes a demotion, even while a rule still matches the account.

## When you need this

Reach for this page when a team at one domain should open the console and you do not want to promote them one at a time. A rule only ever grants the bottom rung; for lifting one person, or anyone to `admin` or `owner`, see the role ladder in [Authentication](/docs/manage/authentication#the-console-role-ladder).

## Prerequisites

The `allowlist` [feature](/docs/manage/features) on, in `packages/config/src/site.ts`. The starter ships it on; a fork made with `init` starts with it off unless you pass `--allowlist` or pick it in the prompt, so console access there is granted per person until you flip it. With it off the page renders the console's not-found page, the nav drops it, `/api/v1/admin/allowlist*` 404s for an admin (a caller without a session gets the 401 and a non-admin the 403 first, [API Conventions](/docs/manage/api-conventions#what-runs-before-your-handler) says why), and the sign-in hook returns before reading a rule.

## What a rule does

A rule lifts a matching account to `member`, the console's bottom rung: its holder opens the console and changes nothing. Member reaches what the starter puts there, which is the internal docs, and nothing under Access, so no rule hands a whole domain write access or sight of your users. Admin and owner stay per-person promotions from the Users table.

The grant lands on sign-in, not only at sign-up, so adding `@example.com` covers colleagues who already have accounts on their next sign-in. One hook on session creation does it, so GitHub, Google and magic link are covered by the same rule. It never lowers anyone: someone already at admin or owner keeps their rung, and a rung granted by hand is untouched.

The grant is the one write around the console that is best effort: it sits on the sign-in path, so a database failure there is logged and skipped rather than stopping anyone signing in, and the next sign-in applies it. It still records itself in [Activity](/docs/manage/activity), naming the rule rather than a person, `Allowlist rule @example.com`, since nobody was signed in to do it.

<Callout type="warn" title="A rule needs a verified address">

Matching is by address, so a rule is only as strong as the proof behind the address, and the hook grants nothing to an account without `emailVerified`. GitHub and Google set it from the provider, and magic link, once you turn it on, proves possession. A fork that adds email and password without `requireEmailVerification` sees rules quietly stop granting, rather than turning a domain rule into self-service console access for anyone who can claim an address there.

</Callout>

## How rules are read

- **An empty list grants nothing.** A rule is a grant, so no rules means nobody is lifted, and adding your first one cannot hand the console to everyone by accident.
- **A domain rule covers every address at that domain**, matched exactly. `@example.com` does not cover `@mail.example.com`, which needs its own rule.
- **An address rule covers exactly one address.** Plus-addressing is not stripped, so a rule for `ada@example.com` does not cover `ada+test@example.com`, while a domain rule covers both.
- **An address rule beats a domain rule** covering the same person. The specific rule is the one that grants, so the Activity line names it rather than whichever row the database returned first.
- **Case never matters.** Rules are saved lowercase, so one rule cannot be added twice in different cases; the second attempt is refused as a `CONFLICT`.

The matching is `findAllowlistRule` in `packages/auth/src/access.ts`, a pure function the canonical starter covers in `tests/packages/auth/src/access.test.ts`, and the sign-in hook asks it rather than deciding inline.

## Taking access away

Removing a rule stops future grants and nothing else. Remove one from its row menu or several from a selection, and anyone already lifted keeps their rung, because a list edit that could silently demote a room full of people would make every edit dangerous. The removal deletes the row that held who added it, so [Activity](/docs/manage/activity) is the only place it leaves a trace.

To take the console away from a person, demote them in the Users table, in either order and whether or not a rule still matches them: the demotion stamps `role_set_at`, so no later sign-in undoes it. Offboarding is a [role change or a ban](/docs/manage/authentication#changing-a-role-banning-an-account), never a list edit.

## Common questions

**Does a rule gate sign-up?**

No. A rule decides who reaches the console and nothing about who may create an account; the starter has no sign-up gate. The two look like one list and are not: an empty console grant must admit nobody, while an empty sign-up gate must admit everybody, and one table carrying both is how an install locks itself out or opens itself up on a flag flip. If your fork needs a gate, `matchesAllowlist` and `parseAllowlistRule` in `@packages/auth/access` are pure and take any list, so the matching half exists and only the policy and its storage are yours; the canonical starter keeps the open shapes in `.github/notes/plans/signup-gating.md`.

**Can a rule lift someone I revoked?**

Not once the revoke has stamped `role_set_at`, from the Users table or from `bun run console:roles revoke <email>`. The exception is history: the column starts empty on every row that existed before it did, and an empty record reads as "nobody has decided yet", so an account revoked to `user` before the allowlist shipped can be lifted once by a matching rule. Old data cannot tell those apart, which is why the column exists. If it matters on your install, re-run the revoke after upgrading; it stamps the record and the demotion is final from then on.

**Why can a colleague still not open the console after I added their domain?**

Check, in order: they have not signed in again since the rule was added, because the grant lands on session creation and a session already open stays `user`; their address is not verified; their row already carries `role_set_at`, because someone once set or revoked their rung; the rule names the parent domain and they sign in from a subdomain; the `allowlist` feature is off.

## It's working if

- After adding `@yourdomain.com`, a colleague at that domain signs out and back in, and **Console** appears in their dashboard user menu.
- Console > History > Activity shows `Changed colleague@yourdomain.com from user to member` with the actor `Allowlist rule @yourdomain.com`, and `Added @yourdomain.com to the allowlist` under your own address just below it.
- Adding `@YourDomain.com` a second time is refused with `@yourdomain.com is already on the list.` rather than saved as a second row.
- With `allowlist: false`, Access shows no Allowlist entry and `/console/allowlist` renders the console's not-found page.
