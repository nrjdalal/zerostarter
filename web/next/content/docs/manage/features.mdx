Not every product wants a public blog, a docs site or a waitlist, so each optional surface is a **feature**: one boolean in `packages/config/src/site.ts`, read at runtime, so turning one off removes its routes, links, sitemap and search entries without deleting code. The starter ships with every feature on, since it demos them all; a fork picks its set at `init` and flips any of them later with a config edit.

## When you need this

Reach for this page when a surface you do not want is still showing, or one you do want answers 404, and you need the row that says what its flag covers. For the flags `init` takes and the fork defaults, see the [CLI](/docs/getting-started/cli#init); for what the allowlist does once it is on, see [Allowlist](/docs/manage/allowlist).

## The flags

The `features` export is typed `boolean` rather than `as const`, so a fork can flip a value and the runtime gates stay live code. One row per flag:

| Flag           | Surface                                                                                          | Off means                                                                                                                                                                                                                                           |
| -------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `allowlist`    | Console > Access > Allowlist, `/api/v1/admin/allowlist*`, and the grant on sign-in               | the API 404s behind the console's gates, the console page renders the not-found, the nav drops it, the sign-in hook does nothing, and console access is granted per person                                                                          |
| `apiDocs`      | `/api/docs`, the Scalar reference, and the `/api/openapi.json` document it reads                 | both 404, and the navbar drops "API Docs"; Better Auth's own reference (`/api/auth/reference`) and schema (`/api/auth/open-api/generate-schema`) stay public, since `openAPIPlugin()` in `packages/auth/src/schema.ts` mounts them outside the flag |
| `blog`         | `/blog` and its posts                                                                            | `/blog` 404s; the navbar link, `/og/blog`, the sitemap and the `llms.txt` blog entries drop                                                                                                                                                         |
| `docs`         | `/docs`                                                                                          | `/docs` 404s; the navbar and dashboard links, `/og/docs`, search (`/api/search`), the sitemap and the `llms.txt` docs entries drop                                                                                                                  |
| `internalDocs` | `/console/docs`, the internal docs, member and above                                             | the page renders the not-found, the console nav drops it, and its search (`/api/console/search`) 404s                                                                                                                                               |
| `waitlist`     | `/waitlist` and `/api/waitlist`, plus Console > Waitlist > Signups and `/api/v1/admin/waitlist*` | the page and `/api/waitlist` 404, and the admin API does too behind the console's gates; the console page renders the not-found, the nav drops the group, and a fresh fork's home becomes a plain landing page                                      |

"Off" is not a stub: outside the console the route returns a real 404, inside it the page renders the console's not-found, and the surface leaves the nav, the sitemap, `llms.txt` and search. Content routes get this from one seam, `contentSource` in `web/next/src/lib/content.ts`, which reads as an empty collection when its kind is off; the API gets it from the `requireFeature` middleware, which on a console route runs after the auth and console gates, so only an admin meets that 404 ([API Conventions](/docs/manage/api-conventions#what-runs-before-your-handler)). Auth, the console shell, the dashboard and organizations are not flags: they reach into the database, login and route protection.

The console's 404 is soft: the area is `force-dynamic` and Next commits a 200 before a page-level `notFound()` fires, so a disabled console page renders the not-found with an HTTP 200. An unknown console path lands in the same boundary through a catch-all, on purpose, so a forbidden page and a nonexistent one cannot be told apart; the area is gated and `noindex`.

## Set at `init`, changed in config

`zerostarter init` writes the `features` block from a flag per surface or an interactive picker; the [CLI](/docs/getting-started/cli#init) page owns the flags and the fork defaults. Turning a feature on later is a one-line edit to `site.ts`: `init` only writes the values, and every surface stays in the tree behind a runtime read. What a surface keeps while it is off is its own page's to say: the [Waitlist](/docs/manage/waitlist) keeps its table.

The fork's home follows the same rule: a fork's `web/next/src/app/page.tsx` is written by `init` (from `packages/cli/src/templates.ts`, a canonical starter file a fork does not take), and it redirects to `/waitlist` when `features.waitlist` is on and renders your name and tagline when off. It exports no `dynamic` and reads no request API, so it prerenders at build and a flipped flag reaches it only with a redeploy. The starter's marketing home under `(marketing)/` does not ship to a fork.

## Common questions

**Are these per-user flags?**

No. `features` is configuration, read by the server and bundled into the client, so every visitor sees the same set and changing one is a deploy. Per-user flags from PostHog or a service are an idea on file in `.github/notes/plans/feature-flags.md` (canonical starter), not a feature.

**Does `init` accept `--allowlist`?**

Yes. The argument parser, the `--help` text and the interactive picker are generated from one list of surfaces, so a flag cannot be listed in one place and rejected in another.

**Why does `/api/openapi.json` still list a route whose flag is off?**

The routers stay mounted behind the runtime 404 so a fork can flip a flag on without an `AppType` change. `apiDocs` gates the document and the Scalar UI together, but the other flags do not rewrite the document, so with `waitlist` off, `/api/waitlist` appears in it and answers 404.

## It's working if

- Set `blog: false` in `packages/config/src/site.ts` and restart the dev server: `/blog` returns a 404 and the navbar no longer shows Blog.
- `/sitemap.xml` and `/llms.txt` list no `/blog/` URL while it is off.
- With `waitlist: false`, `/waitlist` returns a real 404 and `/console/waitlist` renders the console's not-found page with a 200.
