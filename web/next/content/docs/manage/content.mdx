Everything you publish is MDX under `web/next/content/`, split on one axis: docs take their metadata from `docs.config.ts`, blog posts carry their own. `docs/` and `blog/` are two [Fumadocs](https://fumadocs.dev) collections; a third, `console/docs/`, holds internal docs served inside the console, [unlisted rather than private](/docs/manage/authentication#the-console-role-ladder).

A docs page is declared centrally, so you write only its body and a generator keeps the frontmatter and reading order in step; a blog post owns its frontmatter, and the listing builds itself from the posts. Each collection is a [feature](/docs/manage/features): off, its routes 404 and it drops from the nav, search, sitemap and `llms.txt`.

## When you need this

Reach for this page when you are adding a docs page or a blog post, or when one is missing from the sidebar, the listing or the search and you want the file that decides. For the flags that turn a collection off, see [Features](/docs/manage/features); for how the docs become `/llms.txt`, see [llms.txt](/docs/manage/llms-txt).

## Docs: the config is the source of truth

`web/next/docs.config.ts` is the single source for the docs' structure and metadata; its header comment is the spec. Groups are ordered arrays of single-key records, keyed by a page URL (its metadata) or a subgroup label (nested items), and a group's name is independent of the URL, so pages regroup without changing links. `label` overrides the sidebar text when it should differ from `title`.

A generator, `.github/scripts/docs.ts`, reads that config. An unflagged run, which `dev:app` and `check-types` make and `bun .github/scripts/docs.ts` makes by hand, writes:

- each page's frontmatter (`slug`, `label` only when it differs from `title`, `title`, `description`), so you only author the body;
- `content/docs/meta.json`, the reading order behind prev/next and `llms.txt`;
- a stub `.mdx` for a page declared but missing on disk.

Under `--strict`, the mode the production build runs (the `build` script in `web/next/package.json`), it still writes `meta.json` but never touches an `.mdx`. It reports frontmatter out of step with the config, a declared page with no file, a file the config does not list, and a blog post with a missing `createdAt`, an invalid timestamp, or neither `publishedAt` nor `draft: true`, then exits 1 if it found any.

Adding a page is three steps: add the entry to `docs.config.ts`, run `bun .github/scripts/docs.ts` to scaffold the file, then write the body. The dev server runs the generator only when it starts and nothing watches the config, so a running one scaffolds nothing until you run that command or restart it. Leave the frontmatter alone: every unflagged run rewrites it, and the build fails on a hand edit.

<Callout type="warn" title="Don't edit meta.json">

`content/docs/meta.json` is generated and git-ignored. The generator overwrites it, so a hand edit is lost on the next build.

</Callout>

## Blog: one file per post

A blog post is a single MDX file in `web/next/content/blog/` that owns its metadata in frontmatter. There is no list to maintain; `/blog` derives itself from the posts, newest first.

Two timestamps decide visibility: `createdAt` is bookkeeping and `publishedAt` is consent to publish. **A post is public only when it is not a draft and `publishedAt` is set and not in the future.**

```yaml
---
title: "My Post Title"
description: "A short summary of the post."
createdAt: 2026-06-11
publishedAt: 2026-06-11
---
```

Set `draft: true` to hide a post regardless of its timestamps, and omit `publishedAt` for a draft with no release time yet. The schema also takes `author` and `tags` (article Open Graph metadata) and `updatedAt` (rendered on the post, and the modified time in the sitemap and article metadata). A timestamp is `YYYY-MM-DD`, the start of that day in UTC, or an ISO datetime with an offset (`"2026-06-18T09:00:00+05:30"`) for an exact release time.

Running `bun .github/scripts/docs.ts` stamps a missing `createdAt` with today's date on a new post and prints what it wrote; review and commit that line. `--strict` reports the missing field and exits 1 instead, so the line is there before the build.

The starter's post images sit under `web/next/public/marketing/blog/<slug>/images/`, referenced by absolute path; `web/next/public/` does not ship to a fork, which keeps its images under its own `public/`.

The publishing rule lives in one place, `web/next/src/lib/blog-policy.ts`, and the listing, sitemap, `llms.txt` and OG routes all read it, so they can never disagree about what is public.

## Search

Full-text search runs on [Orama](https://orama.com) through Fumadocs, at `web/next/src/app/api/search/route.ts`. Press `Cmd+K` (or `Ctrl+K`) on any docs page; the sidebar's search button sends the same keystroke. The index holds the `docs` collection only: the blog is not indexed, and the console docs have their own at `/api/console/search`, which answers 404 to anyone the console would not admit. Both 404 when their feature is off.

## The console docs

`web/next/source.config.ts` defines the third collection, `consoleDocs`, served at `/console/docs` under the console layout's `member` check. The page asserts nothing of its own, so that layout is its only check; [Authentication](/docs/manage/authentication#the-console-role-ladder) says what a layout's check leaves open. No public route references its source, so it is outside the public search, the sitemap and `llms.txt` by construction.

## Common questions

**What decides the order of pages?**

For docs, the order of `docs.config.ts`: the sidebar reads it directly, and the generator writes it into `meta.json`, which prev/next, `/llms.txt` and `/llms-full.txt` read, so they cannot disagree. For the blog, newest `publishedAt` first, with `createdAt` as the fallback and the slug as the tiebreak; nothing is hand-ordered.

**Which timezone does `publishedAt` use?**

UTC, on both ends: a bare date is the start of that day in UTC, not on your machine, and dates render in UTC too, so the date you wrote is the date readers see. For a release at a local hour, use the datetime form with its offset.

**Can a post go live without a rebuild?**

Yes. `/blog`, the post pages, the sitemap, `llms.txt` and the OG images are static with a sixty-second revalidation that re-evaluates the publish rule, so a scheduled post appears within about a minute. Only the prev/next links wait for the next deploy, since `meta.json` lists the posts published at build time.

## It's working if

- Add an entry to `docs.config.ts` and run `bun .github/scripts/docs.ts`: the stub `.mdx` appears on disk, and the page shows in the sidebar in that position.
- A post with `publishedAt` set to tomorrow is absent from `/blog`, `/sitemap.xml` and `/llms.txt/blog` today, and `/blog/<slug>` answers 404.
- `bun .github/scripts/docs.ts --strict` exits 0; a page on disk that the config does not list fails it with "exists but is not listed in docs.config".
