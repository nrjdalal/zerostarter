## Overview

ZeroStarter uses a one-button release cycle built on `canary` (development) and `main` (production) branches. The one human step is merging the draft release PR; everything downstream (changelog generation, version bump, boundary tag, and the published GitHub Release) is automated by `auto-release.yml`.

## Prerequisites

1. Enable the following GitHub setting for the workflow to function:

   **Settings → Actions → General → Workflow permissions**
   - ✅ **Allow GitHub Actions to create and approve pull requests**

   This setting is required for the automated workflows to create draft PRs.

2. **Changelog Generation**: The release workflow uses `changelogen` to generate the changelog from conventional commits. `changelog.config.json` disables the bare `ci` type: it is reserved for pipeline-generated commits (`ci(changelog): ...`) that should never appear in release notes. Real CI work uses a scope instead (`fix(ci): ...`, `feat(ci): ...`) and lands in the changelog normally.

   `changelogen` is pinned to an exact version: the workflow's content gate parses its output format, so an unreviewed format change could silently break releases.

## Workflow

<Steps>
<Step>

### Development Branch (canary)

Feature PRs are **squash-merged** into `canary`. Each push to `canary` triggers `auto-canary-into-main.yml`, which maintains a draft release PR:

- Title: `ci(release): 🚀 merge canary into main`
- Head: `canary` → Base: `main`

No open release PR means nothing is unreleased, or the last `canary` push came from the pipeline itself (`GITHUB_TOKEN` pushes do not trigger workflows); the next feature push recreates it.

</Step>

<Step>

### Merge the Release PR (the one human step)

Review the draft PR, mark it ready, and merge it **with a merge commit**:

```bash
gh pr ready <N>
gh pr merge <N> --merge
```

**Never squash a release PR.** A squash disconnects `main`'s history from `canary` and poisons every future release diff. Only the release direction uses merge commits; feature PRs into `canary` are squashed.

</Step>

<Step>

### Automated Release

Merging triggers `auto-release.yml`, which runs entirely on `canary`:

1. Generates the changelog section from conventional commits since the last `v*` tag
2. Bumps the version in `package.json`
3. Commits `ci(changelog): update changelog and bump version` **directly to canary**; the commit is mechanical (generated from already-reviewed PR titles), so no review round-trip
4. Tags `vX.Y.Z` at the coverage boundary and pushes branch and tag **atomically**: they land together or not at all
5. Publishes a GitHub Release whose notes mirror the new changelog section

**Content gate**: a commit range containing only filtered-out types still bumps the version, so the workflow also requires at least one entry in the new section before releasing. Otherwise it skips cleanly.

</Step>

<Step>

### Verify

```bash
gh run list --workflow auto-release.yml --limit 1     # expect success
git fetch --tags origin && git log --oneline origin/canary -1   # expect the ci(changelog) commit
gh release list --limit 1                             # expect new vX.Y.Z as Latest
```

</Step>
</Steps>

### Build Checks

`auto-check-build.yml` runs on pushes to `canary` and PR updates, executing lint, build, and type checks.

## GitHub Releases

Releases are published by the pipeline: don't create them by hand and don't use GitHub's "Generate release notes" feature. The notes are the `CHANGELOG.md` section for that version: categorized changes, commit links, and contributor credits.

## Failure Recovery

- **Late failure after pushes** (release missing but tag and changelog commit present): re-run the workflow; the skip path backfills the missing GitHub Release idempotently.
- **Tag collision** (`tag vX.Y.Z exists at <sha> but boundary is <sha>`): a previous cycle left inconsistent state; investigate which tag is right before re-running. This should be unreachable in the direct-commit flow.
- **Race** (`canary` moved during the run): the non-force push fails loudly with no partial state; re-run.
