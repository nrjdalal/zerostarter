Two long-lived branches carry the project: `canary` takes every feature PR as a squash, one Conventional Commit each, and `main` is production. A release is one merge of a pull request that opens itself, `canary` into `main`; the changelog, tag and GitHub release follow on their own.

The number is decided before that merge: while a release is pending, every push to `canary` moves the root `package.json` to what the **window** (the commits since the last `v*` tag) has earned, as `ci(version): bump to vX.Y.Z`, so production carries the released number the moment the merge lands. The `release` skill holds the procedure; this page holds the why.

## When you need this

Reach for this page when you are about to cut a release, want more than the patch a window earns, or need to know why a run released nothing.

## Prerequisites

<Callout type="warn" title="A fresh fork's Actions token is read-only">

Until it has write access the release workflows fail with `403 Resource not accessible by integration` and no release PR opens. Under **Settings → Actions → General → Workflow permissions**, select **Read and write permissions**, check **Allow GitHub Actions to create and approve pull requests**, and save; the pre-push hook prints these steps on the push that publishes `canary`.

</Callout>

![GitHub Workflow permissions settings](/marketing/docs/release/workflow-permissions.png)

`main` must also exist on the remote: `init` creates it locally and the pre-push hook seeds it on the push after `canary`'s, so `canary` stays the default branch.

## The window

A window earns changelogen's reading of the commits it keeps, applied to the last tag's version rather than to `package.json`, so a number set early is never bumped twice; no tag yet counts from `v0.0.0`. Below 1.0 a breaking change earns a minor and anything else a patch; from 1.0, the usual semver. `packages/scripts/src/release-version.ts` decides, its header holds the rules, and `bun run release:version` prints the `next` that ships.

The tree moves forward only. For a minor or a major, set the `version` in the root `package.json` on `canary` through a PR: a hand-set number ahead of the window stays, one the window outgrows is lifted, and a tree below the last tag stops the run loudly.

A commit counts when its type is enabled in `changelog.config.json`, which turns `ci` off, and is not a non-breaking `chore(deps)`, which changelogen drops by itself. A window that keeps nothing cannot release, so a dependency refresh is `build(deps)` and pipeline work is `fix(ci)`, never a bare `ci:`; the `gh-commit` skill holds the table.

## From push to release

**A window opens.** Every push to `canary` runs `.github/workflows/auto-canary-into-main.yml`: with `canary` ahead of `main` it opens the draft PR `ci(release): 🚀 merge canary into main` if none is open, then pushes the `ci(version)` commit with the workflow token, which starts no further workflow, so the next human push recomputes.

**One merge.** Mark the PR ready, review it, and merge with a merge commit, so `main` keeps `canary`'s history and the next release PR diffs only its own window. `.github/rulesets/main.json` (fork-excluded, with the rest of `.github/rulesets/`) records that as the one method `main` allows, with one approving review and no required status check; the live ruleset is re-exported from the file when they differ. The missing status check is the trap: when the head is a commit the workflow pushed, the `ci(version)` bump most often, GitHub holds its `pull_request` build for approval, so the PR reads mergeable with no build at all. Approve the held run and let it pass first; a head you pushed yourself builds on its own.

**Changelog, tag, release.** The merge fires `auto-release.yml`, which checks out `canary`, generates `CHANGELOG.md` from the last tag, refreshes `.github/assets/graph-build.svg`, and commits `ci(changelog): update changelog and bump version` straight onto `canary`: mechanical, from PR titles already reviewed, so no second PR, and nothing flows from `main` back. It tags `v<version>` on the merged head, pushes branch and tag atomically, and publishes a GitHub release whose notes mirror the new section. A failed run is re-run with `gh run rerun --failed`, never re-tagged by hand, and a run that tagged but died before publishing is backfilled by the next.

## The CLI rides the same release

Canonical starter only: `packages/cli/`, `tests/` and `cli-release.yml` are fork-excluded; `.gitpickignore` at the root is the list. The `zerostarter` package carries a `0.0.0` placeholder that `cli-release.yml` stamps at publish time from the tag:

| Trigger                                                                                                        | Publishes                             | npm tag  |
| -------------------------------------------------------------------------------------------------------------- | ------------------------------------- | -------- |
| `auto-release.yml` succeeds, a release is published by hand, or `gh workflow run cli-release.yml --ref canary` | the latest `v*` tag's version, once   | `latest` |
| a push to `canary` touching `packages/cli`, `packages/scripts` or `tests`                                      | `<next version>-canary.<n>`           | `canary` |
| the repository owner comments `/release` on a same-repo PR                                                     | `0.0.0-<short sha>` of that PR's head | `test`   |

Every path but `/release` runs the suite on Linux, macOS and Windows first; `/release` is for a package to try in seconds, `bunx zerostarter@0.0.0-<short sha> init`. Publishing is [npm Trusted Publishing](https://docs.npmjs.com/trusted-publishers) through `id-token: write`, so there is no token to leak and every version carries provenance; the manual run re-publishes a failed publish leg, since a re-run replays its own workflow file.

## Common questions

**The run logged `No releasable changelog content`. Why did nothing ship?**

The window kept nothing the changelog counts, usually because it holds only a `chore(deps)` refresh or bare `ci:` commits. Land a releasable commit, `build(deps)` for the refresh, and merge the next release PR; the earlier commits ride along.

**No release PR opened on my fork.**

In order: the Actions token is still read-only, `main` is not on the remote yet, or `canary` is not ahead of `main`. The workflow's log names which.

## It's working if

- `gh pr list --head canary --base main --state open` lists one draft titled `ci(release): 🚀 merge canary into main`, its head the `ci(version)` commit.
- After the merge, `gh release list -L 1` shows `vX.Y.Z` marked Latest and `git pull origin canary` brings the `ci(changelog)` commit and the tag together.
- Canonical starter: `npm view zerostarter version` matches the tag.
