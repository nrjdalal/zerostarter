Two long-lived branches carry the project: `canary` takes every feature PR as a squash, one Conventional Commit each, and `main` is production. A release is one merge of a pull request that opens itself, `canary` into `main`; the changelog, tag and GitHub release follow on their own.

The number is decided before that merge: while a release is pending, every push to `canary` moves the root `package.json` to what the **window** (the commits since the last `v*` tag) has earned, as `ci(version): bump to vX.Y.Z`, so production carries the released number the moment the merge lands. The `release` skill holds the procedure; this page holds the why.

## When you need this

Reach for this page when you are about to cut a release, want more than the patch a window earns, or need to know why a run released nothing.

## Prerequisites

<Callout type="warn" title="A fresh fork's Actions token is read-only">

Until it has write access the release workflows fail with `403 Resource not accessible by integration` and no release PR opens. Under **Settings → Actions → General → Workflow permissions**, select **Read and write permissions**, check **Allow GitHub Actions to create and approve pull requests**, and save; the pre-push hook prints these steps on the push that publishes `canary`.

</Callout>

![GitHub Workflow permissions settings](/marketing/docs/release/workflow-permissions.png)

`main` must also exist on the remote. Into a target with no `.git`, `init` creates it locally at its scaffold commit, and the pre-push hook pushes that `main` on the push after `canary`'s, so `canary` stays the default branch. The scaffold commit is the fetched starter before the rebrand writes `packages/config/src/site.ts`, so a fork's `main` does not build until the first release PR merges `canary` into it. A target that already had `.git` gets `init`'s one commit on its current branch and neither branch is created: create whichever of `canary` and `main` it lacks before the first push.

## The window

A window earns changelogen's reading of the commits it keeps, applied to the last tag's version rather than to `package.json`, so a number set early is never bumped twice; no tag yet counts from `v0.0.0`. Below 1.0 a breaking change earns a minor and anything else a patch; from 1.0, the usual semver. `packages/scripts/src/release-version.ts` decides, its header holds the rules, and `bun run release:version` prints the `next` that ships.

The tree moves forward only. For a minor or a major, set the `version` in the root `package.json` on `canary` through a PR: a hand-set number ahead of the window stays, one the window outgrows is lifted, and a tree below the last tag stops the run loudly.

A window that keeps no releasable commit cannot release; [Commit messages](/docs/manage/code-quality#commit-messages) names the types that count.

## From push to release

**A window opens.** Every push to `canary` runs `.github/workflows/auto-canary-into-main.yml`: with `canary` ahead of `main` it opens the draft PR `ci(release): 🚀 merge canary into main` if none is open, then pushes the `ci(version)` commit with the workflow token. That push starts no push-triggered workflow, so nothing loops and the next human push recomputes; the release PR's `pull_request` build on it is created but held for approval (below).

**One merge.** Mark the PR ready, review it, and merge with a merge commit, so `main` keeps `canary`'s history and the next release PR diffs only its own window. In the canonical starter, `.github/rulesets/main.json` records merge as the one method `main` allows, with one approving review and no required status check, and the `release` skill passes `--merge` explicitly because the history depends on it.

<Callout type="warn" title="A head the workflow pushed merges unbuilt">

GitHub holds the `pull_request` build of a workflow-pushed head, the `ci(version)` bump most often, as `action_required`, and without a required status check the PR reads mergeable with no build at all. Approve the held run and let it pass before merging; the `release` skill's step 4 has the commands.

</Callout>

**Changelog, tag, release.** The merge fires `auto-release.yml`, which checks out `canary`, generates `CHANGELOG.md` from the last tag, refreshes `.github/assets/graph-build.svg`, and commits `ci(changelog): update changelog and bump version` straight onto `canary`: mechanical, from PR titles already reviewed, so no second PR, and nothing flows from `main` back. It tags `v<version>` on the merged head, pushes branch and tag atomically, and publishes a GitHub release whose notes mirror the new section. The tag is the workflow's alone, so a run that stops short is recovered by the `release` skill's step 5, never by tagging by hand.

## The CLI rides the same release

Canonical starter only: `packages/cli/`, `tests/` and `cli-release.yml` are fork-excluded; `.gitpickignore` at the root is the list. The `zerostarter` package carries a `0.0.0` placeholder that `cli-release.yml` stamps at publish time from the tag:

| Trigger                                                                                                        | Publishes                             | npm tag  |
| -------------------------------------------------------------------------------------------------------------- | ------------------------------------- | -------- |
| `auto-release.yml` succeeds, a release is published by hand, or `gh workflow run cli-release.yml --ref canary` | the latest `v*` tag's version, once   | `latest` |
| a push to `canary` touching `packages/cli`, `packages/scripts` or `tests`                                      | `<next version>-canary.<n>`           | `canary` |
| the repository owner comments `/release` on a same-repo PR                                                     | `0.0.0-<short sha>` of that PR's head | `test`   |

Every path but `/release` runs the suite on Linux, macOS and Windows first; `/release` is for a package to try in seconds, `bunx zerostarter@0.0.0-<short sha> init`. Publishing is [npm Trusted Publishing](https://docs.npmjs.com/trusted-publishers) through `id-token: write`, so there is no token to leak and every version carries provenance; a failed publish leg is recovered by the `release` skill's step 5.

## Common questions

**The run logged `No releasable changelog content`. Why did nothing ship?**

The window kept no commit the changelog counts: [Commit messages](/docs/manage/code-quality#commit-messages) names the types that do, and the `release` skill's step 5 holds the recovery.

**Why did no release PR open on my fork?**

In order: the Actions token is still read-only, `main` is not on the remote yet, or `canary` is not ahead of `main`. The workflow's log names which.

**The run stopped with `package.json is at 0.0.0, below the last release`. Why?**

`reinit`, or `init` run again on an existing fork, rewrites the root `package.json` version to `0.0.0`, and [the window](#the-window) refuses a tree below the last tag. Set `version` back to at least that tag on `canary` through a PR.

## It's working if

- `gh pr list --head canary --base main --state open` lists one draft titled `ci(release): 🚀 merge canary into main`, its head the `ci(version)` commit when the last push moved the version.
- After the merge, `gh release list -L 1` shows `vX.Y.Z` marked Latest and `git pull origin canary` brings the `ci(changelog)` commit and the tag together.
- Canonical starter: `npm view zerostarter version` matches the tag.
