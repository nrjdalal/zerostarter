An LLM doesn't browse; it ingests. HTML docs and the interactive [Scalar reference](/docs/manage/api-conventions) at `/api/docs` are built for a human clicking around; `/llms.txt` hands an agent the same knowledge as flat markdown it can read top to bottom, with no JavaScript and no navigation to crawl. Both are generated from the docs at build time, so they never drift from the pages they mirror.

Two shapes:

- **`/llms.txt`**: an index. Lists every docs page (each linked as its `.md` alias) plus a link to the blog. The `/llms.txt/docs` and `/llms.txt/blog` section indexes are served as their own routes too.
- **`/llms-full.txt`**: everything in one file. A `# {site.name}` title (with an `LLM Context File` label) and `> {site.description}` blockquote, then `llmsFullPreamble` from `packages/config/src/site.ts` (the monorepo layout, import map, stack, and conventions), then every docs and blog page concatenated with `---` separators.

Every page is also available on its own as plain text: append `.md` or `.txt` to any docs or blog URL, e.g. `/docs/manage/llms-txt.md`.

In development, `curl "$(bunx portless get zerostarter)/llms-full.txt"` hands an agent the whole project as one file before it writes a line, which is exactly what the `codebase-map` skill does to orient.

## How they're generated

Two `force-static` route handlers (both `revalidate = 60`) build the files from Fumadocs sources:

- `web/next/src/app/(llms.txt)/llms.txt/[[...slug]]/route.ts`: the `/llms.txt` index, the `/docs` and `/blog` section indexes, and every per-page alias. It sorts docs by `meta.json` order and lists only published blog posts. Console docs are excluded on purpose (privacy boundary).
- `web/next/src/app/(llms.txt)/llms-full.txt/route.ts`: the single-file dump, preamble first.

The docs and blog are [features](/docs/manage/features): turn one off and its pages, section index, and per-page aliases drop from both files, so `/llms.txt` never points at a route that 404s.

Page bodies come from `getLLMText` in `web/next/src/lib/llms.ts`. It reads each page's processed markdown (available because every collection in `web/next/source.config.ts` sets `includeProcessedMarkdown: true`), runs `decodeHTML` to undo Fumadocs' HTML-escaping, and prefixes a `# [title](url)` heading that links back to the live page. Each per-page docs alias also appends a footer pointing back to `/llms.txt`, so an agent that lands on one page can find the rest of the navigation.

<Callout type="info" title="Where the aliases come from">

The per-page `.md`/`.txt` rewrites (in `web/next/next.config.ts`) cover `/docs/*` and `/blog/*`, and the top-level `/docs.md`, `/docs.txt`, `/blog.md`, and `/blog.txt` forms resolve to the section indexes (`/llms.txt/docs` and `/llms.txt/blog`). An alias for a page that does not exist answers with a markdown 404 (below), never the HTML not-found page.

</Callout>

## Markdown from the same URL

An agent does not have to know the alias: the pages that have a markdown sibling serve it from their own URL through [content negotiation](https://acceptmarkdown.com). A request for `/`, `/docs/...` or `/blog/...` whose `Accept` names `text/markdown` gets the markdown (`/` answers with the `/llms.txt` index), with `Vary: Accept` so a cache keys on the header; a browser's `Accept` gets the HTML. A client whose `Accept` names neither representation nor a wildcard (say `Accept: application/pdf`) gets `406 Not Acceptable` with a plain-text body naming both; a missing or `*/*` header means no constraint and stays HTML. Pages without a markdown sibling are left alone.

```bash
curl -sI -H "Accept: text/markdown" https://zerostarter.dev/docs/manage/llms-txt | grep -i -E "content-type|vary"
```

It is routing, not code: `next.config.ts` carries `beforeFiles` rewrites (the rules come from `web/next/src/lib/rewrites.ts`) that match the `Accept` header and send the request to the page's llms.txt route, or to the `/406` route handler. Next documents this pattern and Vercel's CDN evaluates it before any cache or function, so the HTML pages stay static hits; a `proxy.ts` would have put a function invocation in front of every request to them, which measured as roughly 200ms of added TTFB on a cached page. The price is that a header regex cannot rank q-values. In practice that never bites: every agent that asks for markdown ([the support matrix](https://acceptmarkdown.com/status)) lists `text/markdown` first at `q=1`, and the rule still honors an explicit `text/markdown;q=0` as a rejection.

Not-found answers follow the same split: an unknown docs or blog path asked for as markdown, or any `.md`/`.txt` alias that resolves to nothing, is a real `404` whose body is markdown and points at `/llms.txt`, `/llms-full.txt` and `/sitemap.xml`; the HTML not-found page carries the same three links for browsers. Every docs and blog page, and the homepage, also carries `<link rel="alternate" type="text/markdown" href="...">` pointing at its markdown, for agents that fetch HTML first and follow the link rather than negotiate (Codex CLI does). The `/llms.txt` index opens with a short "When to use" section, so an agent deciding whether this site is the right tool reads that before the page list.

The markdown response shape (headers, the 404 and 406 bodies) lives in `web/next/src/lib/markdown.ts`. The markdown variant, the 406 and the markdown 404 carry `Vary: Accept` themselves; the HTML variant carries only Next's own `Vary`, which is safe on Vercel, whose CDN already keys its cache on `Accept`, and means a CDN placed in front of a self-hosted deployment would need to add the header itself.
