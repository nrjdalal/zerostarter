Multi-tenancy comes from the Better Auth [Organization plugin](https://www.better-auth.com/docs/plugins/organization), registered with `teams` enabled in `packages/auth/src/schema.ts`. Organizations, members, teams, invitations and an active organization per session are rows in the same Drizzle schema as the rest of your data (`packages/db/src/schema/auth.ts`, generated from that declaration), so a tenant is rows you already own, not a separate service.

An org role on `member.role` governs one tenant; the console ladder on `user.role` never reads it. The `owner` of an organization is a plain `user` to `/console` until the ladder says otherwise, and a console `admin` holds no seat in any organization until a `member` row gives them one. The starter wires the two flows a product needs on day one, creating an organization and switching between them, and leaves the rest of the plugin (invitations, teams, member management) available but unwired, for your product logic.

## When you need this

Reach for this page when you are building a tenant feature: anything scoped to an organization, a team, or a seat in one. For platform roles, who reaches `/console` and what they may change there, see [Authentication](/docs/manage/authentication).

## The data model

Five tables in `packages/db/src/schema/auth.ts` hold the tenancy. Rows cascade from their organization, team or user on delete; `invitation.teamId` alone carries no foreign key.

| Table          | Holds                                                                                                                                                     |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `organization` | The tenant: `name`, a unique `slug`, an optional `logo`, and free-form `metadata`.                                                                        |
| `member`       | A user's seat in an organization, with the org `role` (default `member`).                                                                                 |
| `team`         | A named group inside an organization; `memberCount` is kept current by the plugin on every seat change.                                                   |
| `teamMember`   | A user's seat in a team, flat, with no per-team role; `membershipKey` is unique, written on every add and checked before one, so a seat is never doubled. |
| `invitation`   | A pending invite: `email`, target `role`, optional `teamId`, `status`, `expiresAt`, and the `inviterId`.                                                  |

The active organization and team ride on the session row as `session.activeOrganizationId` and `session.activeTeamId`, so every request knows the current tenant without a second lookup. `memberCount` and `membershipKey` arrived with Better Auth 1.7 (`packages/db/drizzle/0004_better_auth_1_7.sql`, which also backfills the count); a fork on an older migration takes them the way [Database](/docs/manage/database) describes.

Three roles come with the plugin: `owner`, `admin` and `member`. Whoever creates an organization becomes its `owner`; everyone else joins as `member` unless an invitation names another role. Teams are flat, so membership is the only distinction inside one.

## Wired and available

The client plugin in `web/next/src/lib/auth/client.ts` exposes the whole surface as hooks and methods on `authClient`; the dashboard sidebar's switcher (`web/next/src/components/dashboard/sidebar.tsx`) calls four of them:

```ts
import { authClient } from "@/lib/auth/client"

const { data: orgs } = authClient.useListOrganizations()
const { data: activeOrg } = authClient.useActiveOrganization()

await authClient.organization.create({ name, slug })
await authClient.organization.setActive({ organizationId })
```

Everything else works against the backend as soon as you build UI for it:

| Capability                     | State                         | Build on                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------------ | ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Create an organization         | wired, in the sidebar         | `organization.create`; the form takes a name of 2 to 32 characters and derives the slug from it                                                                                                                                                                                                                                                                                                                                     |
| Switch the active organization | wired, in the sidebar         | `organization.setActive`; the choice survives a reload and a new sign-in                                                                                                                                                                                                                                                                                                                                                            |
| Invitations                    | available, no UI and no email | the `invitation` table and the invite, accept and reject endpoints exist, but no `sendInvitationEmail` is configured, so an invite creates a row without delivering a link. Add `sendInvitationEmail` to the plugin in `packages/auth/src/schema.ts`, importing the sender inside the callback as [Authentication](/docs/manage/authentication) shows for magic link, then build the accept page on `organization.acceptInvitation` |
| Teams                          | available, no UI              | `teams.enabled` is on and the tables are there, but nothing reads or writes `activeTeamId`; start from `createTeam` and `setActiveTeam`                                                                                                                                                                                                                                                                                             |
| Member management              | available, no UI              | `removeMember`, `updateMemberRole` and `leave`                                                                                                                                                                                                                                                                                                                                                                                      |
| Permission checks              | available                     | `hasPermission`                                                                                                                                                                                                                                                                                                                                                                                                                     |

## The active organization

When a user switches, the switcher calls `setActive` and writes a per-user cookie, `last-active-org_<userId>`, so the choice survives a reload. On the next protected render, `web/next/src/app/(protected)/layout.tsx` reads that cookie only when the session has no active organization yet, and POSTs to the plugin's `organization/set-active` endpoint with the request headers forwarded, so the session cookie goes along and the tenant is restored server-side before the page draws: no flash of the wrong organization.

<Callout type="info" title="The cookie nominates; the session decides">

`last-active-org_<userId>` is written with `document.cookie`, not `HttpOnly`, so it is a UI convenience the browser can read and rewrite, never a security boundary. The source of truth is `session.activeOrganizationId` on the row; the cookie only says which organization to reactivate.

</Callout>

<Callout type="warn" title="Role and org changes can lag five minutes">

Better Auth caches the session in a cookie for `maxAge: 300` (`packages/auth/src/index.ts`), so a role or active-org change made elsewhere can take up to five minutes to show unless the cache is bypassed. The protected layout and the console gate both read the session with the cache disabled for exactly this reason, and the switcher refetches its queries after each mutation so its own view stays current.

</Callout>

## Common questions

**What does the server check when an organization is created?**

Less than the form does. The plugin's own route accepts any non-empty `name` and `slug`, and the database adds only that the slug is unique; the 2 to 32 character limit and the slug derivation live in the sidebar form. A direct `POST /api/auth/organization/create` from curl bypasses both, so an unbounded name or an uppercase, non-URL-safe slug is possible today. The slug is not routed anywhere (organizations switch by id), so a collision is hygiene rather than a security hole. The backend rules, a `beforeCreateOrganization` hook sharing one schema with the form and `organizationLimit` for a per-user cap, are a backlog item in `.github/notes/plans/org-creation-restrictions.md`.

**The active organization did not come back after a reload. Where do I look?**

The web server's log. The restore is best-effort and never blocks the page: a non-2xx answer logs `failed to restore active organization: <status>` and a thrown fetch logs `failed to restore active organization` with the error, both from the protected layout. It runs only when the session has no active organization and the `last-active-org_<userId>` cookie is present, and it posts through `INTERNAL_API_URL` when that is set, so inside Docker a wrong internal URL is the usual cause.

**Is there an organizations endpoint under `/api/v1`?**

No. The organization surface is the plugin's own routes under `/api/auth/organization/*`, which `api/hono/src/routers/auth.ts` passes straight to Better Auth, so the typed client for it is the plugin's, not the RPC client. `/api/v1/session` leaves `activeOrganizationId` out of its response on purpose: it documents the session fields it names and nothing the plugins add. Read the active tenant from `authClient.useActiveOrganization()` in the browser, or `auth.api.getSession` on the server, as the protected layout does.

## It's working if

- Creating an organization from the sidebar switcher ends in the toast `Organization created!`, and the switcher shows its name and slug as the active one.
- A full reload, and a sign-out and sign-in, both come back with that organization active.
- The creator's `member` row carries `role = owner`, and `session.active_organization_id` matches the organization's id.
