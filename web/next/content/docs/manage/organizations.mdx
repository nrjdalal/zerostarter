Multi-tenancy comes from the Better Auth [Organization plugin](https://www.better-auth.com/docs/plugins/organization), registered with `teams` enabled in `packages/auth/src/schema.ts`. Invitations, members, organizations and teams are rows in the same Drizzle schema as the rest of your data (`packages/db/src/schema/auth.ts`, generated from that declaration), and so is the active organization on each session, so a tenant is rows you already own, not a separate service.

An org role on `member.role` governs one tenant and nothing on the [console ladder](/docs/manage/authentication#the-console-role-ladder), which reads `user.role` alone: an organization's `owner` is a plain `user` to `/console` until that ladder says otherwise, and a console `admin` holds no seat until a `member` row gives them one. The starter wires the two flows a product needs on day one, creating an organization and switching between them, and leaves the rest of the plugin (invitations, member management, and teams beyond the [default one](#the-data-model) each organization gets) available but unwired, for your product logic.

## When you need this

Reach for this page when you are building a tenant feature: anything scoped to an organization, a team, or a seat in one. For who reaches `/console` and what they may change there, see [Authentication](/docs/manage/authentication).

## The data model

Five tables in `packages/db/src/schema/auth.ts` hold the tenancy. Rows cascade from their organization, team or user on delete; `invitation.teamId` alone carries no foreign key.

| Table          | Holds                                                                                                                                                     |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `invitation`   | A pending invite: `email`, `expiresAt`, the `inviterId`, the target `role`, `status`, and an optional `teamId`.                                           |
| `member`       | A user's seat in an organization, with the org `role` (default `member`).                                                                                 |
| `organization` | The tenant: an optional `logo`, free-form `metadata`, a `name`, and a unique `slug`.                                                                      |
| `team`         | A named group inside an organization; `memberCount` is kept current by the plugin on every seat change.                                                   |
| `teamMember`   | A user's seat in a team, flat, with no per-team role; `membershipKey` is unique, written on every add and checked before one, so a seat is never doubled. |

The active organization and team ride on the session row as `session.activeOrganizationId` and `session.activeTeamId`, so every request knows the current tenant without a second lookup. `memberCount` and `membershipKey` are Better Auth 1.7 columns, added by `packages/db/drizzle/0004_better_auth_1_7.sql`, which also backfills the count. A fork on an older migration takes them the way [Database](/docs/manage/database#the-generated-auth-schema) describes, but Drizzle Kit writes only the new columns: append that file's closing `UPDATE "team" SET "member_count" = ...` to the generated SQL by hand, or every existing team reads a `memberCount` of 0 whatever its seats.

Three roles come with the plugin: `owner`, `admin` and `member`. Whoever creates an organization becomes its `owner`; everyone else joins as `member` unless an invitation names another role. Teams are flat, so membership is the only distinction inside one.

Every organization created, the sidebar's included, also gets a default team named after it, with its creator seated (`memberCount` 1), and the creating session's `activeTeamId` is set to that team. `setActive` on another organization writes only `activeOrganizationId`, so `activeTeamId` can go on naming a team in the organization you left; nothing in the starter reads it. `teams: { enabled: true, defaultTeam: { enabled: false } }` in `packages/auth/src/schema.ts` turns the default team off.

## The client surface

The client plugin in `web/next/src/lib/auth/client.ts` exposes the whole surface as hooks and methods on `authClient`; the dashboard sidebar's switcher (`web/next/src/components/dashboard/sidebar.tsx`) calls four of them:

```ts
import { authClient } from "@/lib/auth/client"

const { data: orgs } = authClient.useListOrganizations()
const { data: activeOrg } = authClient.useActiveOrganization()

await authClient.organization.create({ name, slug })
await authClient.organization.setActive({ organizationId })
```

Everything else works against the backend as soon as you build UI for it. The wired rows come first, then the available ones, each group A→Z:

| Capability                     | State                         | Build on                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------ | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Create an organization         | wired, in the sidebar         | `organization.create`; the sidebar form bounds the name and derives the slug from it                                                                                                                                                                                                                                                                                                                                                    |
| Switch the active organization | wired, in the sidebar         | `organization.setActive`; the choice survives a reload, and a new sign-in when [Better Auth's origin check](#the-active-organization) lets the restore through                                                                                                                                                                                                                                                                          |
| Invitations                    | available, no UI and no email | the `invitation` table and the invite, accept and reject endpoints exist, but no `sendInvitationEmail` is configured, so an invite creates a row without delivering a link. Add `sendInvitationEmail` to the plugin in `packages/auth/src/schema.ts`, importing the sender inside the callback as [Authentication](/docs/manage/authentication) describes for magic link, then build the accept page on `organization.acceptInvitation` |
| Member management              | available, no UI              | `leave`, `removeMember` and `updateMemberRole`                                                                                                                                                                                                                                                                                                                                                                                          |
| Permission checks              | available                     | `hasPermission`                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Teams                          | available, no UI              | `teams.enabled` is on and each organization gets a [default team](#the-data-model), but nothing in the starter reads `activeTeamId`; start from `createTeam` and `setActiveTeam`                                                                                                                                                                                                                                                        |

## The active organization

When a user switches, the switcher calls `setActive` and writes a per-user cookie, `last-active-org_<userId>`, so the choice survives a reload. On the next protected render, `web/next/src/app/(protected)/layout.tsx` reads that cookie only when the session has no active organization yet, and POSTs to the plugin's `organization/set-active` endpoint with the request headers forwarded, so the session cookie goes along and the session row is restored server-side before the page draws. The layout reads only whether that answer succeeded, so the cookies it carries, the refreshed cookie cache included, stay on the web server.

Because that `POST` carries the session cookie, Better Auth runs its origin check on it: the forwarded `Origin`, or the `Referer` when there is none, must be a trusted origin. A page load sends no `Origin`, so the `Referer` of the load that reached the protected page decides. A load that started on your own site passes, the redirect after **Login (agents)** among them. A load that started on another site, such as a provider's consent page or an email client, carries that site's `Referer` or none, so the restore answers `403` and logs it (below), the page draws with no active organization, and picking one in the switcher sets it again.

The cookie nominates and the session decides. `last-active-org_<userId>` is written with `document.cookie`, not `HttpOnly`, so it is a UI convenience the browser can read and rewrite, never a security boundary; the source of truth is `session.activeOrganizationId` on the row, and the cookie only says which organization to reactivate.

A role or active-org change made elsewhere, the server-side restore included, can trail by the [cookie cache](/docs/manage/authentication#sessions-and-cookies) in a client read; the protected layout reads past it, and the switcher refetches its queries after each mutation so its own view stays current.

## Common questions

**What does the server check when an organization is created?**

Less than the form does. The plugin's own route accepts any non-empty `name` and `slug` except a slug already taken, which it refuses with `ORGANIZATION_ALREADY_EXISTS` before the database's unique index would; the 2 to 32 character limit and the slug derivation live in the sidebar form. A direct `POST /api/auth/organization/create` from curl bypasses both, so an unbounded name or an uppercase, non-URL-safe slug is possible. The slug is not routed anywhere (organizations switch by id), so a collision is hygiene rather than a security hole. The backend rules, a `beforeCreateOrganization` hook sharing one schema with the form and `organizationLimit` for a per-user cap, are open shapes the canonical starter keeps in `.github/notes/plans/org-creation-restrictions.md`.

**The active organization did not come back after a reload. Where do I look?**

The web server's log. The restore is best-effort and never blocks the page: a non-2xx answer logs `failed to restore active organization: <status> <statusText>` and a thrown fetch logs `failed to restore active organization` with the error, both from the protected layout. It runs only when the session has no active organization and the `last-active-org_<userId>` cookie is present, and it posts through `INTERNAL_API_URL` when that is set, so inside Docker a thrown fetch usually means a wrong internal URL. A `403` is Better Auth refusing the restore: either its origin check found no trusted `Referer` on the forwarded headers ([The active organization](#the-active-organization)), or the user is no longer a member of that organization.

**Is there an organizations endpoint under `/api/v1`?**

No. The organization surface is the plugin's own routes under `/api/auth/organization/*`, which `api/hono/src/routers/auth.ts` passes straight to Better Auth, so the typed client for it is the plugin's, not the RPC client. `/api/v1/session` leaves `activeOrganizationId` out of its response on purpose: it documents the session fields it names and nothing the plugins add. Read the active tenant from `authClient.useActiveOrganization()` in the browser, or `auth.api.getSession` from `@/lib/auth` on the server, as the protected layout does.

## It's working if

- Creating an organization from the sidebar switcher ends in the toast `Organization created!`, and the switcher shows its name and slug as the active one.
- A full reload comes back with that organization active, and after a sign-out and **Login (agents)** the first protected page sets `session.active_organization_id` back to it.
- The creator's `member` row carries `role = owner`, and `session.active_organization_id` matches the organization's id.
