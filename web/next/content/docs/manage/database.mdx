Your database schema is TypeScript. The tables in `packages/db/src/schema/` are the only source of truth: Drizzle Kit writes each SQL migration by diffing them against the last snapshot, and Drizzle types every query against them, so a renamed column is a compile error in the API rather than a `null` in production.

One file in that directory is not yours. `auth.ts` is the output of Better Auth's generator for the plugins and columns the app declares, and it is never edited by hand; every other table is yours to shape.

## When you need this

Reach for this page when you are adding a table or a column, or working out which file a table lives in and why it is shaped the way it is. For the steps (a throwaway database, generate, review, apply, rebuild), the `db-migration` skill in [AI Skills](/docs/resources/ai-skills) carries them; for what the auth tables hold, see [Authentication](/docs/manage/authentication).

## The schema by concern

Files group by concern, not by table, so a new table joins the file its neighbours are in rather than getting one of its own. Drizzle Kit reads every file in the directory, since `packages/db/drizzle.config.ts` points it at the directory rather than at `index.ts`, so a table reaches a migration whichever file holds it; `index.ts` re-exports each file because the typed `db` client and every import from `@packages/db` see only what it exports.

| File          | Tables                                                                                                                                                                                                                                                    | Owner                                                                      |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `auth.ts`     | `account`, `invitation`, `member`, `organization`, `session`, `team`, `teamMember`, `user`, `verification`, with their relations and foreign-key indexes                                                                                                  | Better Auth's generator; see [Authentication](/docs/manage/authentication) |
| `console.ts`  | `activity` behind [Console > History](/docs/manage/activity), who changed what; `allowlist` behind [Console > Access](/docs/manage/allowlist), whose `kind` is a stored generated column, so a write sets only `value` and `kind` cannot disagree with it | the console                                                                |
| `waitlist.ts` | `waitlist`, no foreign keys, behind the public `/waitlist` page and [Console > Waitlist](/docs/manage/waitlist)                                                                                                                                           | the waitlist                                                               |

The `db` client in `packages/db/src/index.ts` is typed from these files and runs on Bun's SQL driver; Drizzle Kit runs from the `db:*` scripts on the `postgres` driver the package declares for it alone.

## The generated auth schema

`bun run auth:schema` writes `auth.ts` as exactly what the Better Auth CLI emits for `packages/auth/src/schema.ts`: the plugins (admin, openAPI, organization with teams) and the app's own columns, in one declaration that the auth instance and the generator both read, so the two cannot disagree. After editing `packages/auth/src/schema.ts`, run `bun run auth:schema --check` (`packages/scripts/src/auth-schema.ts`): it fails when the committed file differs from a fresh generation. The canonical starter runs the same check automatically as `tests/packages/db/src/schema/auth.test.ts`, which a fork does not take.

A column of your own on `user` or `session` is therefore an `additionalFields` entry in that declaration, not an edit to `auth.ts`. The console's `roleSetAt` is the example: declared there, regenerated with `bun run auth:schema`, then migrated like any other change. A Better Auth upgrade takes the same path: bump, regenerate, and `bun run db:generate` writes the migration from your own snapshot. Drizzle Kit writes only the schema change, so a value an upgrade needs filled in on existing rows is an `UPDATE` you append to the generated SQL by hand, the way `0004_better_auth_1_7.sql` backfills `team.member_count`; skip it and every existing row keeps the column default.

The generator runs under Node on purpose: under Bun a function's text prints as `() => new Date` without the call, which is what the CLI inspects before emitting a database default, so a Bun run silently drops every `defaultNow()`. It loads `packages/auth/auth-schema.config.ts`, an instance with no database, because the real one imports Bun's SQL client and cannot load there.

## Conventions, and where they bend

Every file names its columns in `snake_case`. Outside the generated `auth.ts`, with `waitlist.ts` as the example, `created_at` is `timestamp("created_at").defaultNow().notNull()` and the primary key is `text` filled by `crypto.randomUUID()`; inside it the generator writes what Better Auth declares: the library fills its own primary keys, and `created_at` has no database default on `member`, `organization` and `team` and allows null on `team_member`, because the library stamps it itself. A new table's foreign key is `onDelete: "cascade"` with an index on its column. That rule comes from the generated `auth.ts`, where every foreign key cascades and all but `invitation.inviter_id` are indexed; `waitlist.ts` has no foreign key, and the console tables bend it for their `actor_id`.

Any other index is added when your own row counts and query plans ask for it, not in advance; the auth tables add `invitation.email` and `verification.identifier`. Where the choice shows:

- **`user.role` has no index and no database default.** The console filters and sorts `user` by it, and `user` holds every account, not only your staff: at starter scale that scan is cheap, and the index waits, like any other, until your account count and query plans ask for it. The default is absent because the admin plugin stamps `user` on every account it creates, and the generated schema says only what the plugin declares.
- **The console tables bend the delete rule and the index rule.** Their `actor_id` is `set null`, not `cascade`, because deleting the admin who added a rule must not delete the rule, nor the history they made. Beyond the primary key, `allowlist.value` carries the unique index its constraint creates and `activity` carries none, though it grows without bound: its index waits for your row counts like any other. Each stores an `actor` text beside the id, so a row stays readable once the id is null. `activity.actor` is never null and can name an actor that was never an account (`console:roles`, an allowlist rule); `allowlist.actor` is the author's email, or null for a rule seeded outside the console.

## From an edit to a running table

The loop is edit, generate, review, apply. `bun run db:generate` diffs the schema against the snapshot in `packages/db/drizzle/meta/` and writes a numbered `.sql` beside a fresh snapshot, never touching the database; `bun run db:migrate` runs the pending files against `POSTGRES_URL`. You read the SQL in between because it is the exact DDL that will run against your data, and an applied migration is immutable: a fix is a new one. The `db-migration` skill in [AI Skills](/docs/resources/ai-skills) carries the steps and the two traps around them: every step runs against a throwaway database, because a migration applied to a database a deploy reads reaches that deploy at once (in the canonical starter, `canary` and production read one), and the running stack does not see a new table until `@packages/db` is rebuilt and dev restarted.

In production the schema, the SQL and the snapshot travel in the commit that needs them, and the API build on Vercel applies pending migrations on production and canary deploys (`.github/scripts/migrate-on-deploy.ts`), skipping PR previews. `bun run db:studio` opens Drizzle Studio on whatever `POSTGRES_URL` names.

## Common questions

**Why does Drizzle Kit ask for `pg` or `postgres` when the app runs on Bun's driver?**

Because Drizzle Kit cannot use Bun's driver, so `postgres` is a dev dependency of `packages/db` for the `db:*` scripts; the message means it is not installed, and `bun install` fixes it. A fresh clone needs no build first, because each `db:*` script builds `@packages/env` before Drizzle Kit reads the config.

**Does `sync` overwrite my migrations and schema?**

No. `packages/db/drizzle/` and `packages/db/src/schema/` are restored after the overlay, so a fork's migration history stays its own. The flip side is that an upstream schema change does not arrive through sync: you port and migrate it yourself.

`packages/auth/src/schema.ts` is not restored: the overlay replaces it with the starter's copy like any shared starter file, so your own plugins and `additionalFields` are gone from it after a sync. The auth instance reads that same declaration at runtime, so until you put them back from the sync's diff they are gone from the running app too; restore them before you commit the sync. Regenerating from the starter's copy also removes your columns from `auth.ts`, and the next `bun run db:generate` writes a migration that drops them. See [CLI](/docs/getting-started/cli#common-questions).

**Can the migrations be squashed into one baseline?**

Only for a database treated as new. A fresh baseline carries a new timestamp, so `migrate` tries to apply it against tables that already exist and fails. Once a migration has been applied anywhere, keep appending.

**Why does the auth schema check report drift when I did not touch `auth.ts`?**

Something upstream of it changed: a plugin or an `additionalFields` entry in `packages/auth/src/schema.ts`, or a Better Auth bump whose generator now emits something new. Run `bun run auth:schema`, read the diff, and if it adds or alters a column, generate a migration for it. Line endings are not drift: the check compares with both sides normalized, so a Windows checkout passes.

## It's working if

- `bun run auth:schema --check` prints `auth schema is in sync` and exits 0.
- `bun run db:generate` after a schema edit writes a numbered `.sql` into `packages/db/drizzle/` with a matching `meta/` snapshot, and with nothing changed says `No schema changes, nothing to migrate`.
- `bun run db:studio` opens Drizzle Studio on `POSTGRES_URL` with `activity`, `allowlist`, `waitlist` and the auth tables listed, one for each table the files in `packages/db/src/schema/` declare.
