Your database schema is TypeScript. The tables in `packages/db/src/schema/` are the only source of truth: Drizzle Kit writes each SQL migration by diffing them against the last snapshot, and Drizzle types every query against them, so a renamed column is a compile error in the API rather than a `null` in production.

One file in that directory is not yours. `auth.ts` is the output of Better Auth's generator for the plugins and columns the app declares, and it is never edited by hand; every other table is yours to shape.

## When you need this

Reach for this page when you are adding a table or a column, or working out which file a table lives in and why it is shaped the way it is. For the steps (a throwaway database, generate, review, apply, rebuild), the `db-migration` skill in [AI Skills](/docs/resources/ai-skills) carries them; for what the auth tables hold, see [Auth & Organizations](/docs/manage/authentication).

## The schema by concern

Files group by concern, not by table, so a new table joins the file its neighbours are in rather than getting one of its own. `index.ts` re-exports each file, and a file it does not export never reaches a migration.

| File          | Tables                                                                                                                                                                                                                  | Owner                                                                            |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `auth.ts`     | `user`, `session`, `account`, `verification`, `organization`, `member`, `team`, `teamMember`, `invitation`, with their relations and foreign-key indexes                                                                | Better Auth's generator; see [Auth & Organizations](/docs/manage/authentication) |
| `console.ts`  | `allowlist` behind [Console > Access](/docs/manage/allowlist), whose `kind` is a generated column so a row stores only the rule `value`; `activity` behind [Console > History](/docs/manage/activity), who changed what | the console                                                                      |
| `waitlist.ts` | `waitlist`, no foreign keys, behind the public `/waitlist` page and [Console > Waitlist](/docs/manage/waitlist)                                                                                                         | the waitlist                                                                     |

The `db` client in `packages/db/src/index.ts` is typed from these files and runs on Bun's SQL driver; Drizzle Kit runs from the `db:*` scripts on the `postgres` driver the package declares for it alone.

## What is generated, and how your own column enters

`bun run auth:schema` writes `auth.ts` as exactly what the Better Auth CLI emits for `packages/auth/src/schema.ts`: the plugins (organization with teams, admin, openAPI) and the app's own columns, in one declaration that the auth instance and the generator both read, so the two cannot disagree. A test fails when the committed file differs from a fresh generation, so a hand edit cannot survive.

A column of your own on `user` or `session` is therefore an `additionalFields` entry in that declaration, not an edit to `auth.ts`. The console's `roleSetAt` is the example: declared there, regenerated with `bun run auth:schema`, then migrated like any other change. A Better Auth upgrade takes the same path: bump, regenerate, and `bun run db:generate` writes the migration from your own snapshot, which is how the 1.7 columns on `team` and `team_member` arrived.

The generator runs under Node on purpose: under Bun a function's text prints as `() => new Date` without the call, which is what the CLI inspects before emitting a database default, so a Bun run silently drops every `defaultNow()`. It loads `packages/auth/auth-schema.config.ts`, an instance with no database, because the real one imports Bun's SQL client and cannot load there.

## Conventions, and where they bend

Outside `auth.ts`, every table follows one shape, with `waitlist.ts` as the plain example: `text` primary keys filled by `crypto.randomUUID()`, `snake_case` column names, `timestamp("created_at").defaultNow().notNull()`, and `onDelete: "cascade"` with an index on every foreign-key column. Inside `auth.ts` the generator writes what Better Auth declares: the library fills its own primary keys, and `created_at` has no database default on `organization`, `team` and `member` and allows null on `team_member`, because the library stamps it itself.

Indexes are added when your own row counts and query plans ask for them, not in advance. The auth tables index most foreign-key columns plus `verification.identifier` and `invitation.email`, which are not foreign keys; `invitation.inviter_id` carries none. Where the choice shows:

- **`user.role` has no index and no database default.** The console filters and sorts by it, and a handful of rungs over a table the size of your staff list is a sequential scan either way. The default is absent because the admin plugin stamps `user` on every account it creates, and the generated schema says only what the plugin declares.
- **The console tables bend the delete rule and the index rule.** Their `actor_id` is `set null`, not `cascade`, because deleting the admin who added a rule must not delete the rule, nor the history they made. Neither carries an index beyond its primary key, because at console sizes the sequential scan wins. Each stores an `actor` text beside the id, so a row stays readable once the id is null and can name an actor that was never an account.

## From an edit to a running table

The loop is edit, generate, review, apply. `bun run db:generate` diffs the schema against the snapshot in `packages/db/drizzle/meta/` and writes a numbered `.sql` beside a fresh snapshot, never touching the database; `bun run db:migrate` runs the pending files against `POSTGRES_URL`. You read the SQL in between because it is the exact DDL that will run against your data, and an applied migration is immutable: a fix is a new one. The `db-migration` skill in [AI Skills](/docs/resources/ai-skills) carries the steps and the two traps around them: every step runs against a throwaway database, because `canary` and production share one, and the running stack does not see a new table until `@packages/db` is rebuilt and dev restarted.

In production the schema, the SQL and the snapshot travel in the commit that needs them, and the API build on Vercel applies pending migrations on production and canary deploys (`.github/scripts/migrate-on-deploy.ts`), skipping PR previews. `bun run db:studio` opens Drizzle Studio on whatever `POSTGRES_URL` names.

## Common questions

**Drizzle Kit says to install `pg` or `postgres`, but the app runs on Bun's driver.**

Both are true. Drizzle Kit cannot use Bun's driver, so `postgres` is a dev dependency of `packages/db` for the `db:*` scripts; the message means it is not installed, and `bun install` fixes it. A fresh clone needs no build first, because each `db:*` script builds `@packages/env` before Drizzle Kit reads the config.

**Does `sync` overwrite my migrations and schema?**

No. `packages/db/drizzle/` and `packages/db/src/schema/` are restored after the overlay, so a fork's migration history stays its own. The flip side is that an upstream schema change does not arrive through sync: the auth tables regenerate with `bun run auth:schema` once the new `packages/auth/src/schema.ts` lands, and the rest you port and migrate yourself. See [CLI](/docs/getting-started/cli).

**Can the migrations be squashed into one baseline?**

Only for a database treated as new. The starter did it once, regenerating `0000_zero_starter.sql` from the schema of the day; a fresh baseline carries a new timestamp, so `migrate` tries to apply it against tables that already exist and fails. Once a migration has been applied anywhere, keep appending.

**The auth schema check reports drift, and I did not touch `auth.ts`.**

Something upstream of it changed: a plugin or an `additionalFields` entry in `packages/auth/src/schema.ts`, or a Better Auth bump whose generator now emits something new. Run `bun run auth:schema`, read the diff, and if it adds or alters a column, generate a migration for it. Line endings are not drift: the check compares with both sides normalized, so a Windows checkout passes.

## It's working if

- `bun run auth:schema --check` prints `auth schema is in sync` and exits 0.
- `bun run db:generate` after a schema edit writes a numbered `.sql` into `packages/db/drizzle/` with a matching `meta/` snapshot, and with nothing changed says `No schema changes, nothing to migrate`.
- `bun run check-types` from the repo root fails in `api/hono` after you rename a column that a router selects.
