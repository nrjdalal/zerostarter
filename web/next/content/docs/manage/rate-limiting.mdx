Every request to the API passes a rate limiter before any route runs, and a signed-in request passes a second, larger one on its way into `/api/v1`. Both come from one factory in `api/hono/src/middlewares/rate-limiter.ts`, built on [`hono-rate-limiter`](https://github.com/rhinobase/hono-rate-limiter).

A request is keyed by who before where: user id, then API key, then IP, in a per-process store. An office behind one address stops sharing a budget the moment its people sign in, and a count lives on the instance that served the request, not across a fleet.

## When you need this

Reach for this page when you are seeing 429s, or deciding what the limits should be for your deployment. For the envelope a throttled request gets and the code to `switch` on, see [API Conventions](/docs/manage/api-conventions).

## How a request is keyed

The key is the first of these the limiter can resolve (`generateRateLimitKey` in `rate-limiter.ts`):

| Tier    | Key              | Comes from                                                                                        |
| ------- | ---------------- | ------------------------------------------------------------------------------------------------- |
| User    | `userid:<id>`    | the session `authMiddleware` sets on `/api/v1/*` before its limiter runs                          |
| API key | `apikey:<hash>`  | a resolver no limiter passes today: the starter has no API-key auth, so this branch waits for one |
| Address | `ip:<address>`   | `findIp` from `@arcjet/ip`, a header parser with no account and no network call                   |
| None    | `ip:<random id>` | a fresh id per request when no address resolves, which leaves that request unbounded              |

The global limiter passes no resolver, so it always keys on address; the per-user limiter supplies the session's user id.

<Callout type="warn" title="Anonymous limiting is off on a bare Bun deploy">

`findIp` runs bare, with no `platform` and no trusted `proxies`. Where Bun owns the socket with nothing in front (Docker, any self-host), the request carries no peer address, so the library reads client-controllable headers: a forged `x-forwarded-for` names its own bucket, and a client that sends none lands on the random tier, one bucket per request. Vercel [overwrites `x-forwarded-for`](https://vercel.com/docs/headers/request-headers#x-forwarded-for), so the direct path there is unaffected. Put a proxy you control in front, or pass `platform` and `proxies` to `findIp` for your host; the canonical starter tracks the fix in `.github/notes/plans/rate-limit-ip-resolution.md`.

</Callout>

## Two tiers from one factory

`createRateLimiter` wraps the library's middleware with the key above and the envelope as its handler. Two instances exist:

| Limiter                                       | Runs on                                                             | Budget per window                     | Keyed by |
| --------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------- | -------- |
| `rateLimiterMiddleware`                       | every request, after CORS and the logger in `api/hono/src/index.ts` | `HONO_RATE_LIMIT`, 60 by default      | address  |
| the per-user limiter in `middlewares/auth.ts` | `/api/v1/*`, once the session is set                                | `HONO_RATE_LIMIT * 2`, 120 by default | user id  |

Both windows are `HONO_RATE_LIMIT_WINDOW_MS`, 60000 by default, and both variables are validated in `packages/env/src/api-hono.ts` ([Environment Variables](/docs/manage/environment)). The two stack rather than replace: a signed-in request still counts against the address budget it shares with everyone behind that address, so from one address a user meets the 60 before the 120. The larger tier binds only for a user spread across addresses, or on a deploy where the address tier resolves nothing (the callout above) and it is the only limit left.

## What a throttled request sees

A `429` in the standard envelope, `{ "error": { "code": "TOO_MANY_REQUESTS", "message": "Too Many Requests" } }`, with a `Retry-After` header. Every response, throttled or not, carries the `draft-6` headers (`RateLimit-Limit`, `RateLimit-Policy`, `RateLimit-Remaining`, `RateLimit-Reset`), the library's default, so a client can back off without guessing. The `429` is documented on every method in the OpenAPI document, so the [reference](/docs/getting-started/type-safe-api) shows it on each route.

## Common questions

**Why do all anonymous visitors on a `*.vercel.app` host share one bucket?**

On a public hosting suffix the web app proxies its calls to the API through its own `/api` rewrite ([sessions and cookies](/docs/manage/authentication#sessions-and-cookies) says why). The last forwarded address the API sees, the one `findIp` keys on, is then a Vercel hop rather than the client, so every visitor on that path draws from one anonymous budget of `HONO_RATE_LIMIT` per window, and a busy sign-in page can throttle itself; through a custom domain, where the browser reaches the API directly, the same request lands in the client's own bucket. Whether Vercel stamps the original client anywhere on the rewrite path is unverified, so the limiter does not read one yet. Until it does, raise `HONO_RATE_LIMIT` on a public-suffix deploy, or move to a custom domain.

**Are the limits shared across instances?**

No. The store is the library's `MemoryStore`, one per process, so each replica, and each serverless instance on Vercel, counts on its own: a client's 60 is 60 per instance it reaches. That is right for one container and for local work; behind a load balancer or on serverless, hand `rateLimiter` a shared `store` inside `createRateLimiter`, since the package exports `RedisStore` and `UnstorageStore`.

## It's working if

- The 61st anonymous request to `/api/health` inside one minute returns `429` with `TOO_MANY_REQUESTS` in the envelope and a `Retry-After` header, and the 60 before it carried `RateLimit-Remaining` counting down. Against a Bun-served stack, send the same `x-forwarded-for` on every request, since nothing else resolves there (the callout above).
