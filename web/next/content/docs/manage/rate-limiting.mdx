Every request to the API passes a rate limiter before any route runs, and a signed-in request passes a second, larger one on its way into `/api/v1`. Both come from one factory in `api/hono/src/middlewares/rate-limiter.ts`, built on [`hono-rate-limiter`](https://github.com/rhinobase/hono-rate-limiter).

Each limiter keys on one thing, in a per-process store: the global one on the client address, the per-user one on the session's user id. The two limiters stack rather than replace: signing in adds a per-user budget and never lifts the per-address one, so an office behind one address shares that budget whether or not its people sign in, and the larger per-user budget binds first only for a user spread across addresses. A count lives on the instance that served the request, not across a fleet.

## When you need this

Reach for this page when you are seeing 429s, or deciding what the limits should be for your deployment. For the envelope a throttled request gets and the code to `switch` on, see [API Conventions](/docs/manage/api-conventions).

## How a request is keyed

The key is the first of these the limiter can resolve (`generateRateLimitKey` in `rate-limiter.ts`):

| Tier    | Key              | Comes from                                                                                            |
| ------- | ---------------- | ----------------------------------------------------------------------------------------------------- |
| User    | `userid:<id>`    | the session `authMiddleware` sets on `/api/v1/*` before its limiter runs                              |
| API key | `apikey:<hash>`  | a resolver no limiter passes, since the starter has no API-key auth; a fork that adds it supplies one |
| Address | `ip:<address>`   | `findIp` from `@arcjet/ip`, a header parser with no account and no network call                       |
| Random  | `ip:<random id>` | a fresh `randomUUIDv7()` per request when no address resolves, which leaves that request unbounded    |

The global limiter passes no resolver, so it keys on address, falling to the random tier when none resolves; the per-user limiter supplies the session's user id.

<Callout type="warn" title="Anonymous limiting is off on a bare Bun deploy">

`findIp` runs bare, with no `platform` and no trusted `proxies`. Where Bun owns the socket with nothing in front (Docker, any self-host), the request carries no peer address, so the library reads client-controllable headers: a forged `x-forwarded-for` holding a public address names its own bucket (a loopback or private one resolves to nothing), and a client that sends none lands on the random tier, one bucket per request. Vercel [overwrites `x-forwarded-for`](https://vercel.com/docs/headers/request-headers#x-forwarded-for), so the direct path there is unaffected. Put a proxy you control in front, or pass `platform` and `proxies` to `findIp` for your host; the canonical starter tracks the fix in `.github/notes/plans/rate-limit-ip-resolution.md`.

</Callout>

## Two tiers from one factory

`createRateLimiter` wraps the library's middleware with the key above and the envelope as its handler. Two instances exist:

| Limiter                                       | Runs on                                                             | Budget per window                     | Keyed by |
| --------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------- | -------- |
| `rateLimiterMiddleware`                       | every request, after CORS and the logger in `api/hono/src/index.ts` | `HONO_RATE_LIMIT`, 60 by default      | address  |
| the per-user limiter in `middlewares/auth.ts` | `/api/v1/*`, once the session is set                                | `HONO_RATE_LIMIT * 2`, 120 by default | user id  |

Both windows are `HONO_RATE_LIMIT_WINDOW_MS`, 60000 by default, and both variables are validated in `packages/env/src/api-hono.ts` ([Environment Variables](/docs/manage/environment)). On a deploy where the address tier resolves nothing (the callout above), the per-user tier is the only limit a signed-in request meets.

## What a throttled request sees

A `429` in the standard envelope, `{ "error": { "code": "TOO_MANY_REQUESTS", "message": "Too Many Requests" } }`, with a `Retry-After` header. Every response, throttled or not, carries the `draft-6` headers (`RateLimit-Limit`, `RateLimit-Policy`, `RateLimit-Remaining`, `RateLimit-Reset`), the library's default, and each limiter overwrites the last one's: on a signed-in `/api/v1` request they describe the per-user budget, though for a user on one address the per-address budget binds first. Browser code on another origin, such as the web on a custom domain, cannot read them or `Retry-After`, because the CORS config in `api/hono/src/index.ts` exposes only `content-length`; add them to `exposeHeaders` for a client that backs off on them. The `429` is documented on every method in the OpenAPI document, so the [reference](/docs/getting-started/type-safe-api) shows it on each route.

## Common questions

**Why do all anonymous visitors on a `*.vercel.app` host share one bucket?**

On a public hosting suffix the web app proxies its calls to the API through its own `/api` rewrite ([sessions and cookies](/docs/manage/authentication#sessions-and-cookies) says why). The last forwarded address the API sees, the one `findIp` keys on, is then a Vercel hop rather than the client, so every visitor on that path draws from one anonymous budget of `HONO_RATE_LIMIT` per window, and a busy sign-in page can throttle itself; through a custom domain, a call the browser makes to the API directly lands in the client's own bucket. The web server's own call, the session read behind every dashboard and console render (`web/next/src/lib/auth/index.ts`), comes from the web host carrying the browser's headers, so its bucket depends on what your host does to `x-forwarded-for` on that hop, and a `429` there reads as signed out, because that read treats any answer that is not OK as no session. Nothing in the limiter recovers the original client on that path, so raise `HONO_RATE_LIMIT` on a public-suffix deploy, or move to a custom domain.

**Are the limits shared across instances?**

No. The store is the library's `MemoryStore`, one per process, so each replica, and each serverless instance on Vercel, counts on its own: a client's 60 is 60 per instance it reaches. That is right for one container and for local work; behind a load balancer or on serverless, hand `rateLimiter` a shared `store` inside `createRateLimiter`, since the package exports `RedisStore` and `UnstorageStore`.

## It's working if

- The 61st anonymous request to `/api/health` inside one minute returns `429` with `TOO_MANY_REQUESTS` in the envelope and a `Retry-After` header, and the 60 before it carried `RateLimit-Remaining` counting down. Against a Bun-served stack, send the same public address on every request (`x-forwarded-for: 1.1.1.1`), since nothing else resolves there and a loopback or private one never does (the callout above).
