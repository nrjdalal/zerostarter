One Rust toolchain, [Oxc](https://oxc.rs), lints and formats the monorepo through `oxlint` and `oxfmt`, and [Lefthook](https://github.com/evilmartians/lefthook) runs it on every commit beside a build and a message check, so a commit that lands is formatted, linted and building.

The hooks see only your staged files and your machine, so the pull request repeats every check over the whole tree and adds the two no hook runs, `check-types` and the test suite. A skipped hook changes your branch, never what reaches `canary`.

## When you need this

Reach for this page when a hook or a pull-request check fails, or to find which gate runs what. How the commits become a version is [Releases](/docs/manage/release); the same toolchain on save is [IDE Setup](/docs/resources/ide-setup).

## The gates, in order

`lefthook.yml` holds the hooks, `.lintstagedrc.json` what runs on a staged file, and `auto-check-build.yml` the pull request's run. Oxc reads `.oxlintrc.jsonc`, every rule at its default, and `.oxfmtrc.jsonc`: no semicolons, sorted imports and Tailwind classes, `.agents/**` left alone.

| Gate         | Runs                                      | What has to pass                                                                                                                                                                         |
| ------------ | ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pre-commit` | each commit                               | `skills-manager` when a skill is staged; `oxfmt` then `oxlint` on the staged files, re-staging what the formatter fixed (plus the dependency manager on `package.json`); `bun run build` |
| `commit-msg` | each commit                               | Commitlint                                                                                                                                                                               |
| `pre-push`   | each push                                 | `bun audit --audit-level high` on `canary` only, accepted advisories ignored by id; `ensure-remote-branches.ts` seeds `main` on a fresh GitHub remote                                    |
| pull request | each push to a PR into `canary` or `main` | the audit, `format:check`, `lint`, `check-types`, `test` and `build`                                                                                                                     |

The pre-commit hook is `piped`, so the first failure stops the rest, and a new push cancels the pull-request run in progress, which shows as a cancelled check. Canonical starter only: `cli-release.yml` also runs the suite on Linux, macOS and Windows when a `canary` push touches `packages/cli`, `packages/scripts` or `tests`, and `.github/notes/dependencies.md` records each audit override and ignore (the `audit` skill).

<Callout type="warn" title="The local build sees your real .env">

CI builds with `SKIP_ENV_VALIDATION=true`; the pre-commit build validates the `.env` you have, so a missing required variable fails the commit while the same change passes in CI.

</Callout>

## Commit messages

`<type>(<scope>): <subject>`, checked against `@commitlint/config-conventional` (the `commitlint` key in the root `package.json`). The `gh-commit` skill holds the types and the procedure, and no commit carries a `Co-authored-by` trailer. Two types the release reads specially:

- **`ci` is reserved.** `changelog.config.json` turns it off and `packages/scripts/src/release-version.ts` counts only enabled types, so a `ci:` commit earns no version and no changelog line. It belongs to the pipeline's own `ci(version)` and `ci(changelog)`; real CI work is `fix(ci)`, `feat(ci)` or `docs(ci)`.
- **A dependency refresh is `build(deps)`.** changelogen drops a non-breaking `chore(deps)`, so a window holding only one never releases.

## Common questions

**Why does the audit run on push and not on commit?**

It needs the network, and a new advisory in a dependency nobody touched would block every commit on `canary`, offline included, along with the build piped behind it. On push it still catches the advisory before the branch leaves your machine.

**Commitlint rejected a message that looks conventional.**

A capitalized subject (`feat: Add user page` fails `subject-case`), a trailing period, or a header or body line over 100 characters; a message with no type fails `type-empty`.

**How do I skip a hook, or get them back?**

`LEFTHOOK_EXCLUDE=build git commit` drops one command, `LEFTHOOK=0` drops every hook, and `git commit --no-verify` is git's own switch; the pull request re-checks it all. Hooks that never fire were skipped by an install with `--ignore-scripts`, and `bun run prepare` installs them.

## It's working if

- `git commit -m "add user page"` fails with `type may not be empty [type-empty]`.
- A file the formatter rewrote lands formatted in that same commit.
- Each push to a pull request runs the `Audit, Lint, and Build` check.
