Oxlint lints and `bun fmt` formats the whole monorepo, and [Lefthook](https://github.com/evilmartians/lefthook) runs them (plus a build and a commit-message check) at the moments a mistake would otherwise slip through. You rarely invoke any of it by hand.

## Oxlint and bun fmt, not ESLint + Prettier

[Oxlint](https://oxc.rs) replaces ESLint, and [`bun fmt`](https://bun.com/docs/format), the formatter built into Bun, replaces Prettier. Both are native code, so they finish in a fraction of the time, fast enough to run on every commit without you noticing. That speed is the whole reason to switch.

The config is deliberately small. `.oxlintrc.jsonc` is three lines, just a schema, every rule at its default:

```jsonc
{
  "$schema": "./node_modules/oxlint/configuration_schema.json",
}
```

`bun fmt` reads the `[fmt]` section of `bunfig.toml`, which formats like oxfmt, turns off semicolons, sorts imports, sorts Tailwind classes in the theme's order (in `className` and inside `cn()` and `cva()`), keeps every package.json's scripts A to Z, and skips the AI skill directory:

```toml
[fmt]
config = false
flavor = "oxfmt"
ignorePatterns = [".agents/**", ".claude/skills/**", ".github/skills/**"]
semi = false
sortImports = true
sortPackageJson = { sortScripts = true }

[fmt.sortTailwindcss]
functions = ["cn", "cva"]
stylesheet = "web/next/src/app/globals.css"
```

`config = false` keeps a Prettier or oxfmt config file, a parent folder's included, from applying, and `flavor = "oxfmt"` formats like oxfmt (100 columns) where bun fmt would otherwise format like Prettier.

Run either across the tree yourself:

```bash
bun run lint            # oxlint over everything (this is what CI runs)
bun run format          # bun fmt, writing fixes
bun run format:check    # bun fmt --check, report only (also what CI runs)
bun run format:changed  # the same check, only on the files that differ from canary
```

## bun check, not tsc

[`bun check`](https://bun.com/docs/runtime/check) is Bun's built-in type checker, and it reports the same errors as `tsc` from TypeScript 7. `bun run check-types` runs it where `tsc` ran before: `bun check` in every workspace, then over each `tests/` project. It needs no install of its own and runs wherever Bun runs.

Here it only checks. `typescript` stays installed where something needs the compiler itself: tsdown emits each package's `.d.ts` through it, `next build` type-checks the web app with it, and your editor runs it.

## The git hooks

`lefthook.yml` wires three hooks:

```yaml
pre-commit:
  piped: true
  commands:
    skills-manager:
      priority: 1
      glob:
        - ".agents/skills/**/*.md"
        - "packages/scripts/src/skills-manager.ts"
      run: bun packages/scripts/src/skills-manager.ts && git add AGENTS.md
    lint-staged:
      priority: 2
      run: bunx lint-staged --verbose
      stage_fixed: true
    build:
      run: bun run build
      use_stdin: true

commit-msg:
  commands:
    commitlint:
      run: bunx commitlint --edit {1}

pre-push:
  commands:
    audit:
      run: bun audit --audit-level high
      only:
        - ref: canary
    ensure-branches:
      run: bun packages/scripts/src/ensure-remote-branches.ts {1}
```

**pre-commit**: when a skill changed, `skills-manager` regenerates the AGENTS.md skills tables first. Then [lint-staged](https://github.com/lint-staged/lint-staged) formats your staged files with `bun fmt`, lints them with `oxlint` and stages the fixes again, so they ride along in the same commit. A file with both staged and unstaged changes is fine: lint-staged hides the unstaged part while it runs. Then a full `bun run build` has to pass. A commit that lands is formatted, linted, and building.

**commit-msg**: [Commitlint](https://commitlint.js.org) checks the message against Conventional Commits (below).

**pre-push**: `bun audit --audit-level high` runs, but only from `canary` (`only: ref: canary`), so a vulnerable dependency is caught before the branch leaves your machine without blocking your offline commits. `ensure-remote-branches.ts` seeds the release branches (default `main`) that drive the release PR (see [Releases](/docs/manage/release)).

**On a pull request**, the `auto-check-build` workflow re-runs the full gate on GitHub: `bun audit`, `bun run format:check`, `bun run lint`, `bun run check-types`, `bun run test`, and `bun run build`. A failing type error or test blocks the merge, so the checks that are cheap to skip locally (the pre-commit build tolerates type errors that `check-types` would reject) still cannot reach `canary`. It runs once per commit, on the pull-request events only: a review cannot change the result for a commit that is already built, and a second run on the same commit would cancel the first through the workflow's concurrency group, which shows on the pull request as a cancelled check.

<Callout type="warn" title="The local build sees your real .env">

Unlike CI (which sets `SKIP_ENV_VALIDATION=true`), the pre-commit build validates your actual `.env`. A missing or invalid required variable fails the commit locally even though the same build passes in CI.

</Callout>

## Commit messages

Messages follow [Conventional Commits](https://www.conventionalcommits.org): `<type>(<scope>): <subject>`. Common types are `feat`, `fix`, `docs`, `refactor`, `chore`, `test`, `perf`, and `style`; `build` and `revert` are also accepted.

```bash
feat(auth): add Google OAuth provider
fix(api): handle null user in session middleware
docs(readme): update setup steps
```

Two repo rules the hook and skills enforce:

- **Never add a `Co-authored-by` trailer.**
- **`ci` is reserved** for pipeline-generated commits (the changelog bot) and is filtered out of the changelog; use `fix(ci)` or `docs(ci)` for real CI work.

## Common fixes

- **A commit failed on formatting or lint**: run `bun run format` (and `bun run lint`), `git add` the result, and commit again.
- **Commitlint rejected the message**: rewrite it as `type: subject`; `add user page` becomes `feat: add user page`.
- **Hooks aren't running**: reinstall them with `bun run prepare`.
- **You need to bypass in an emergency**: `git commit --no-verify`, or `LEFTHOOK=0 git commit …` to drop every hook, or `LEFTHOOK_EXCLUDE=build git commit …` to drop just the build. CI re-checks all of it anyway.

Dependency advisories that can only be resolved with a `package.json` override are recorded in `.github/notes/dependencies.md`; the `audit` skill walks you through it.
