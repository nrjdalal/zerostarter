There is one `.env` at the repo root, and no app reads it through `process.env`: each imports a validated, typed slice of it from `@packages/env/<name>`, so a variable is set in one place and a wrong or missing one is caught once, at boot, instead of surfacing as `undefined` halfway through a request.

Each consumer validates its own slice at boot, and the client slice is `NEXT_PUBLIC_*` only: `POSTGRES_URL` has no such name, so it is in no client schema and the bundler has nothing to inline into a page. Exposing a value to the browser is a deliberate rename, never an accident. Outside the schema sit the variables the host injects (`PORT`, `VERCEL`, `VERCEL_ENV`, `VERCEL_GIT_COMMIT_REF`, `VERCEL_GIT_COMMIT_SHA`), the two [skip flags](#skipping-validation), and `GIT_SHA`, which you set off Vercel to suffix the build version; each is read at its point of use and absent from `.env.example`.

## When you need this

Reach for this page when you are adding a variable, setting one for a new stage or host, or reading a boot failure that names one. For pulling the `.env` from a shared vault instead of editing it by hand, see [Infisical](/docs/resources/infisical).

## The slices

Four slices, each a Zod schema in `packages/env/src/<slice>.ts`, imported as `@packages/env/<slice>` and named for the consumer that imports it, plus `NODE_ENV` in every one. A variable two slices declare (`HONO_APP_URL`, `HONO_TRUSTED_ORIGINS`) is validated by both and read through whichever slice its reader imports:

| Slice      | Holds                                                                                                                                                                |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `api-hono` | `AGENT_SIGNIN_ENABLED`, `HONO_APP_URL`, `HONO_PORT`, `HONO_RATE_LIMIT`, `HONO_RATE_LIMIT_WINDOW_MS`, `HONO_TRUSTED_ORIGINS`                                          |
| `auth`     | `BETTER_AUTH_SECRET`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `HONO_APP_URL`, `HONO_TRUSTED_ORIGINS`, `HONO_WEB_URL` |
| `db`       | `POSTGRES_URL`                                                                                                                                                       |
| `web-next` | `INTERNAL_API_URL` on the server, and the `NEXT_PUBLIC_*` variables the browser sees                                                                                 |

An app imports its slice (`import { env } from "@packages/env/api-hono"`) and reads typed values from it: `env.HONO_PORT` is a number, already defaulted. The three server slices import `packages/env/src/load-dotenv.ts`, which reads the root `.env` once and layers `.env.<stage>` over it; `web-next` does not, because client components import it (see the questions below), so a build-time consumer that reads `web-next` imports `@packages/env/load-dotenv` itself, above the slice import, since a slice validates the moment it evaluates. `web/next/next.config.ts` does, and so does `packages/scripts/src/generate-env.ts`, whose `web` target reads `web-next` and whose `auth` target reads `@packages/env/auth`.

`web-next` is the only slice split into `server` and `client`, and the split is the boundary: a server key read from a client component throws rather than returning `undefined`. The `db` slice carries the one Docker twist: when `INTERNAL_API_URL` is set, a `POSTGRES_URL` whose host is `localhost` is rewritten to `host.docker.internal` (`db.ts`, through `lib/postgres-url.ts`); only the host moves, never a `localhost` inside the credentials or the database name. That name reaches your machine under Docker Desktop but not on Linux as `docker-compose.yml` stands, and under `NODE_ENV=production` the database must also serve TLS: [Deploy with Docker](/docs/deployment/docker#prerequisites) has both.

## Every variable

`.env.example` holds the ones you are expected to set. `HONO_PORT`, `HONO_WEB_URL` and `INTERNAL_API_URL` are valid but left out of it on purpose: `HONO_PORT` has a default, Compose sets `INTERNAL_API_URL`, and `HONO_WEB_URL` has neither, because you set it by hand only on a public hosting suffix where inference from `HONO_TRUSTED_ORIGINS` fails. The Schema column says whether the slice file requires the variable; a default makes a variable optional, and the row names it first. Which slice declares each is in [the slices](#the-slices) table.

Under `bun run dev`, `.github/scripts/portless.ts` sets four of them in the process env before each app starts: `HONO_APP_URL` and `NEXT_PUBLIC_API_URL` to the api's `.localhost` URL, `NEXT_PUBLIC_APP_URL` to the web's, and `HONO_TRUSTED_ORIGINS` to the web's alone. The base `.env` never overrides a value the process already has, so `.env`'s values for those four apply only under `PORTLESS=0`, in Docker and on a deploy, and an extra origin you add to `HONO_TRUSTED_ORIGINS` is dropped in dev unless a `.env.<stage>` file sets it. That file loads with override and replaces the portless value whole, so list the dev web URL in it too, the one `bunx portless get <name>` prints (`<name>` the project's slug, `zerostarter` in the canonical starter); without it the dev web loses CORS, Better Auth's trust and the agent sign-in.

| Variable                            | Schema   | What it does                                                                                                                                                                                                                              |
| ----------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AGENT_SIGNIN_ENABLED`              | optional | Defaults to `false`. Mounts the local [agent sign-in](/docs/getting-started/working-with-agents), and only while `NODE_ENV` is `local` (`api/hono/src/lib/agent-signin.ts`); `init` and `reinit` write `true` over a blank or missing one |
| `BETTER_AUTH_SECRET`                | required | Signs sessions; `init` and `reinit` generate one when it is blank or missing. A [skip flag](#skipping-validation) leaves it unset rather than dummied, with the risk that section names                                                   |
| `GITHUB_CLIENT_ID` / `_SECRET`      | optional | GitHub sign-in registers only when both are set                                                                                                                                                                                           |
| `GOOGLE_CLIENT_ID` / `_SECRET`      | optional | Google sign-in registers only when both are set                                                                                                                                                                                           |
| `HONO_APP_URL`                      | required | The api's public origin; the cookie scope and Better Auth's `baseURL` derive from it in `packages/auth/src/index.ts`                                                                                                                      |
| `HONO_PORT`                         | optional | Defaults to `4000`. The port the api binds when the host injects no `PORT` (`api/hono/src/lib/server.ts`)                                                                                                                                 |
| `HONO_RATE_LIMIT`                   | optional | Defaults to `60`. Requests per address per window ([Rate Limiting](/docs/manage/rate-limiting))                                                                                                                                           |
| `HONO_RATE_LIMIT_WINDOW_MS`         | optional | Defaults to `60000`. The window, in milliseconds                                                                                                                                                                                          |
| `HONO_TRUSTED_ORIGINS`              | required | Comma-separated origins that the agent sign-in and Better Auth accept and that CORS names in `Access-Control-Allow-Origin`; CORS refuses no request on the server                                                                         |
| `HONO_WEB_URL`                      | optional | Names the web origin on a [public hosting suffix](/docs/deployment/vercel) when it cannot be inferred from `HONO_TRUSTED_ORIGINS`                                                                                                         |
| `INTERNAL_API_URL`                  | optional | Where the web server reaches the api inside [Docker](/docs/deployment/docker); Compose sets it to `http://api:4000`                                                                                                                       |
| `NEXT_PUBLIC_API_URL`               | required | The api origin. The browser calls it directly, except on a public hosting suffix; the web's `/api` rewrite and the web server's own calls target it when `INTERNAL_API_URL` is unset                                                      |
| `NEXT_PUBLIC_APP_URL`               | required | The web origin: the sitemap and robots, the `llms.txt` links, the sign-in callback, and on a public hosting suffix the origin the browser's API calls go to                                                                               |
| `NEXT_PUBLIC_POSTHOG_HOST`          | optional | [PostHog](/docs/manage/analytics) region or self-hosted URL; unset, `web/next/instrumentation-client.ts` uses the EU cloud                                                                                                                |
| `NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN` | optional | Turns PostHog on                                                                                                                                                                                                                          |
| `NEXT_PUBLIC_USERJOT_URL`           | optional | Shows the [feedback link](/docs/manage/analytics#user-feedback)                                                                                                                                                                           |
| `NODE_ENV`                          | required | The [stage](#stages). The browser never sees it: its `NEXT_PUBLIC_NODE_ENV`, which you never set, holds Next's build mode                                                                                                                 |
| `POSTGRES_URL`                      | required | The [database](/docs/manage/database); `init` fills it when it provisions one. A `localhost` host becomes `host.docker.internal` under `INTERNAL_API_URL`                                                                                 |

## Stages

`NODE_ENV` is a five-value enum in `packages/env/src/lib/constants.ts`, validated by every slice: `local`, `development`, `test`, `staging`, `production`. With a known stage set, `load-dotenv.ts` layers `.env.<stage>` over the base `.env` with override, so `.env.production` wins where both name a key. The api bundle reads the stage at runtime rather than at build (`bun build --env disable` in `api/hono/package.json`), so the process or container env decides it, never the shell that ran the build.

Deploy on `production` or `staging`, since the other three open things a deploy should not. `local` and `development` both keep the api's `/headers` route open, which echoes a request's headers, its session cookie included, to any script on a trusted origin. `local` also puts an unhandled error's raw message in every 500 (`api/hono/src/lib/error.ts`) and mounts the [agent sign-in](/docs/getting-started/working-with-agents#local-sign-in) while its flag is on, so setting the flag to `false` closes the sign-in and leaves `/headers` and the raw messages open. `test` turns off Better Auth's origin and callback-URL checks. `staging` keeps those closed but drops what only `production` turns on: [Better Auth's limiter](/docs/manage/rate-limiting#better-auths-limiter), Better Auth's refusal of its public default secret ([the callout below](#skipping-validation)), its redirect of `/api/auth/error` to `/` in place of the HTML page that names the error, and the database client's `tls` option, so TLS is whatever `POSTGRES_URL` asks for.

Better Auth reads the stage once, as it loads, and the built api (`api/hono/bundle/index.mjs`, which `bun run start` and the Docker image run) loads it before the `.env` loader runs. Its behaviours above therefore follow only a `NODE_ENV` already in the process env: Compose's `env_file` and Vercel's project variables put it there, but a bundle started by hand with `NODE_ENV=production` in `.env` alone runs the rest of the api as production while Better Auth's limiter, its default-secret refusal and its error-page redirect stay off. Export `NODE_ENV` in that shell.

To branch on the stage, `@packages/env` exports a checker per value (`isLocal`, `isProduction`, and the rest), so code reads `isProduction(env.NODE_ENV)` instead of comparing strings.

The stage stops at the server. The `web-next` slice fills `NEXT_PUBLIC_NODE_ENV` from `process.env.NODE_ENV`, which Next inlines into client code as its build mode, so the browser reads `development` under `next dev` and `production` from any `next build`, a `staging` build included; `local` and `test` never reach it either.

## Skipping validation

Two flags, both read in `packages/env/src/lib/polyfill.ts`, let a build pass without real values: a missing required variable falls back to a shape-valid dummy (`https://polyfill.url`, `postgres://polyfill.local:5432/db`). `NODE_ENV` has no dummy, since every slice reads it raw, so it must be set under either flag; the CI build sets `NODE_ENV: production` beside its flag. Validation otherwise still runs, so a present-but-invalid value fails either way.

- `SKIP_ENV_VALIDATION=true` covers every server and client variable but `NODE_ENV`: the CI escape hatch (`.github/workflows/auto-check-build.yml` sets it), for a build before any real secret exists. The Docker images do not use it: each mounts the real `.env` as a build secret and validates it in full.
- `SKIP_ENV_VALIDATION_SERVER=true` covers only the server variables; the `NEXT_PUBLIC_*` client variables stay required and validated, because the web build inlines and ships them. The web's Vercel build command sets it (`web/next/vercel.json`): it compiles the server packages for their types without their secrets.

`BETTER_AUTH_SECRET` is the exception to the dummy: under either flag `serverSecret` in `lib/polyfill.ts` turns its schema optional and leaves the value `undefined`, so the auth package still constructs for a build. Without a flag the schema stays required, so a missing secret fails at boot with `Invalid environment variables` rather than running.

<Callout type="warn" title="Never set a skip flag on a running app">

The server would start against dummy URLs, and without `BETTER_AUTH_SECRET` it signs sessions with a secret anyone can read: `packages/auth/src/index.ts` passes Better Auth no `secret`, so Better Auth reads the variable itself and, finding none, falls back to its own built-in default, a public constant. It refuses that default only when the `NODE_ENV` it reads is `production` ([Stages](#stages) says when that differs from `.env`); on `local`, `development`, `staging` and `test` it runs. The flags are for a build, and the error they silence is the one you want at boot.

</Callout>

## Adding a variable

A variable lives on more surfaces than the schema, and a surface left out fails quietly rather than loudly. `HONO_RATE_LIMIT` is the full set, in the order you add a variable to them, from the schema to the docs:

| Surface                            | For `HONO_RATE_LIMIT`                                                                       | Because                                                                                                                                                                |
| ---------------------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The slice: schema and `runtimeEnv` | `packages/env/src/api-hono.ts`                                                              | the schema types and validates it; the `runtimeEnv` entry is what reads `process.env`                                                                                  |
| The root `.env`                    | `.env`                                                                                      | your value                                                                                                                                                             |
| `.env.example`                     | `.env.example`                                                                              | what a fresh checkout and `init` start from, defaults included, `HONO_RATE_LIMIT` among them; only the variables the [table's lead-in](#every-variable) names stay out |
| `globalEnv` in `turbo.json`        | `turbo.json`                                                                                | Turbo hashes it, so a changed value misses the cache instead of replaying a stale build                                                                                |
| The consumer                       | `api/hono/src/middlewares/rate-limiter.ts` and `auth.ts`                                    | where the typed value is read                                                                                                                                          |
| The docs and skills that name it   | the table on this page, and whatever `rg -n HONO_RATE_LIMIT web/next/content .agents` finds | so the table a reader scans still matches the schema                                                                                                                   |

<Callout type="warn" title="runtimeEnv is mandatory">

Nothing type-checks a slice's `runtimeEnv` map against its schema, so a variable declared in the schema but missing from the map reads as unset whatever `.env` says: a required one fails at boot, an optional one is silently `undefined`, and a defaulted one such as `HONO_RATE_LIMIT` silently keeps its default. Always add both.

</Callout>

## Common questions

**What reads `HONO_APP_URL`?**

Not the api's routers, which is why it looks removable: the `api-hono` slice declares it, but nothing under `api/hono/src` reads it. `packages/auth/src/index.ts` does, through `@packages/env/auth`, three times. The cookie scope derives from its host (parsed at build by `generate-env.ts`, overridden at runtime for a `.localhost` dev host so web and api share the cookie), its origin is what separates the api from the web entries in `HONO_TRUSTED_ORIGINS`, and Better Auth's `baseURL` falls back to it off a public hosting suffix. So it stays required.

**Why does the `web-next` slice not load `.env` itself?**

Because client components import it. The loader needs `dotenv` and `node:path`, and a module shared with `web-next` would drag the browserified node graph behind `dotenv` into every page that imports the slice, so the load lives in `load-dotenv.ts`, which only the server slices import. A fork adding a slice of its own (a `mail` target, say) adds `import "@/load-dotenv"` to it, then gives it the `entry` and `exports` lines the `add-package` skill ([AI Skills](/docs/resources/ai-skills)) describes for a library with several entries.

Keep such a slice out of the web's server code, along with the other server slices, `@packages/db` and the main `@packages/auth` entry, and have the web read server data through the api. A module the web server runs (a page, layout, route handler or server action under `web/next/src`, or anything it imports) that reaches the loader lets Next's file tracer follow its `path.resolve(process.cwd(), "../../.env")` to the root `.env`, so a standalone build (every build but Vercel's) copies that file into `.next/standalone`, and the web image ships that output whole, secrets included. `next.config.ts` is the exception and keeps its import: Next runs the config at build and writes its values into the standalone `server.js` rather than tracing its imports. After a build, `web/next/.next/standalone/.env` should not exist.

**Is `INTERNAL_API_URL` how two Vercel projects talk?**

No, it is the Docker variable, and Compose sets it on both services. It does three jobs there: the web's `/api` rewrite and its server-side fetches target it instead of the public api URL, and its presence flips `POSTGRES_URL` to `host.docker.internal`. Two projects on a public suffix such as `*.vercel.app` need none of that: the web build detects the suffix (`NEXT_PUBLIC_IS_PRIVATE`, derived by `generate-env.ts`) and proxies the browser's `/api` calls to `NEXT_PUBLIC_API_URL` itself, for the reason [sessions and cookies](/docs/manage/authentication#sessions-and-cookies) gives. Setting `NEXT_PUBLIC_API_URL` to the web origin by hand is the trap: without `INTERNAL_API_URL` the rewrite's destination is the web itself, and every `/api/*` call ends in `508 Loop Detected`. [Deploy to Vercel](/docs/deployment/vercel) has the matrix that works.

## It's working if

- `bun run dev` with `POSTGRES_URL` blank stops at the `@packages/db` build, before either app starts, with `❌ Invalid environment variables:` and an issue whose `path` is `POSTGRES_URL`, then throws `Invalid environment variables`; nothing starts against a half-read config.
- Started as `NODE_ENV=local bun run dev`, `next dev` prints `@web/next:getSafeEnv:` with the slice's values and `NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN` shown as `******** REDACTED ********`. With the stage in `.env` alone it prints nothing: `next dev` sets `NODE_ENV=development` before `next.config.ts` loads `.env`, which never overrides a value the process already has.
- Reading `env.INTERNAL_API_URL` from a client component throws `❌ Attempted to access a server-side environment variable on the client`.
