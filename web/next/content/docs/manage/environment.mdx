There is one `.env` at the repo root, and no app reads it through `process.env`: each imports a validated, typed slice of it from `@packages/env/<name>`, so a variable is set in one place and a wrong or missing one is caught once, at boot, instead of surfacing as `undefined` halfway through a request.

Each consumer validates its own slice at boot, and the client slice is `NEXT_PUBLIC_*` only: `POSTGRES_URL` has no such name, so it is in no client schema and the bundler has nothing to inline into a page. Exposing a value to the browser is a deliberate rename, never an accident. The one thing outside the schema is a variable the host injects rather than you setting (`PORT`, `VERCEL`, `VERCEL_GIT_COMMIT_SHA`), read at its point of use and absent from `.env.example`.

## When you need this

Reach for this page when you are adding a variable, setting one for a new stage or host, or reading a boot failure that names one. For pulling the `.env` from a shared vault instead of editing it by hand, see [Infisical](/docs/resources/infisical).

## The slices

Four slices under `packages/env/src/`, each a Zod schema named for the consumer that imports it, plus `NODE_ENV` in every one. A variable two slices declare (`HONO_APP_URL`, `HONO_TRUSTED_ORIGINS`) is validated by both and read through whichever slice its reader imports:

| Slice                    | File          | Loads `.env` | Holds                                                                                            |
| ------------------------ | ------------- | ------------ | ------------------------------------------------------------------------------------------------ |
| `@packages/env/api-hono` | `api-hono.ts` | yes          | `AGENT_SIGNIN_ENABLED`, `HONO_APP_URL`, `HONO_PORT`, the rate-limit pair, `HONO_TRUSTED_ORIGINS` |
| `@packages/env/auth`     | `auth.ts`     | yes          | `BETTER_AUTH_SECRET`, the OAuth pairs, `HONO_APP_URL`, `HONO_TRUSTED_ORIGINS`, `HONO_WEB_URL`    |
| `@packages/env/db`       | `db.ts`       | yes          | `POSTGRES_URL`                                                                                   |
| `@packages/env/web-next` | `web-next.ts` | no           | `INTERNAL_API_URL` on the server, and the `NEXT_PUBLIC_*` variables the browser sees             |

An app imports its slice (`import { env } from "@packages/env/api-hono"`) and reads typed values from it: `env.HONO_PORT` is a number, already defaulted. The three server slices import `packages/env/src/load-dotenv.ts`, which reads the root `.env` once and layers `.env.<stage>` over it; `web-next` does not, because client components import it (see the questions below), so a build-time consumer that reads `web-next` imports `@packages/env/load-dotenv` itself, above the slice import, since a slice validates the moment it evaluates. `web/next/next.config.ts` does, and so does `packages/scripts/src/generate-env.ts`, whose `web` target reads `web-next` and whose `auth` target reads `@packages/env/auth`.

`web-next` is the only slice split into `server` and `client`, and the split is the boundary: a server key read from a client component throws rather than returning `undefined`. The `db` slice carries the one Docker twist: when `INTERNAL_API_URL` is set, a `POSTGRES_URL` whose host is `localhost` is rewritten to `host.docker.internal` (`db.ts`, through `lib/postgres-url.ts`), so a container reaches a database on your machine; only the host moves, never a `localhost` inside the credentials or the database name.

## Every variable

`.env.example` holds the ones you are expected to set. `HONO_PORT`, `HONO_WEB_URL` and `INTERNAL_API_URL` are valid but left out of it on purpose: each has a default or is wired for you. The Schema column is the slice file's own word for it, and a default makes a variable optional.

| Variable                            | Slice                    | Schema                    | What it does                                                                                                                                                                                     |
| ----------------------------------- | ------------------------ | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `AGENT_SIGNIN_ENABLED`              | `api-hono.ts`            | optional, default `false` | Mounts the local [agent sign-in](/docs/getting-started/working-with-agents), and only while `NODE_ENV` is `local` (`api/hono/src/lib/agent-signin.ts`)                                           |
| `BETTER_AUTH_SECRET`                | `auth.ts`                | required                  | Signs sessions; `init` generates one. Never dummied under a [skip flag](#skipping-validation)                                                                                                    |
| `GITHUB_CLIENT_ID` / `_SECRET`      | `auth.ts`                | optional                  | GitHub sign-in registers only when both are set                                                                                                                                                  |
| `GOOGLE_CLIENT_ID` / `_SECRET`      | `auth.ts`                | optional                  | Google sign-in registers only when both are set                                                                                                                                                  |
| `HONO_APP_URL`                      | `api-hono.ts`, `auth.ts` | required                  | The api's public origin; the cookie scope and Better Auth's `baseURL` derive from it in `packages/auth/src/index.ts`                                                                             |
| `HONO_PORT`                         | `api-hono.ts`            | optional, default `4000`  | The port the api binds when the host injects no `PORT` (`api/hono/src/lib/server.ts`)                                                                                                            |
| `HONO_RATE_LIMIT`                   | `api-hono.ts`            | optional, default `60`    | Requests per address per window; a signed-in request also counts against a per-user budget of twice this, so from one address this one binds first ([Rate Limiting](/docs/manage/rate-limiting)) |
| `HONO_RATE_LIMIT_WINDOW_MS`         | `api-hono.ts`            | optional, default `60000` | The window, in milliseconds                                                                                                                                                                      |
| `HONO_TRUSTED_ORIGINS`              | `api-hono.ts`, `auth.ts` | required                  | Comma-separated origins that CORS, Better Auth and the agent sign-in accept                                                                                                                      |
| `HONO_WEB_URL`                      | `auth.ts`                | optional                  | Names the web origin on a [public hosting suffix](/docs/deployment/vercel) when it cannot be inferred from `HONO_TRUSTED_ORIGINS`                                                                |
| `INTERNAL_API_URL`                  | `web-next.ts` (server)   | optional                  | Where the web server reaches the api inside [Docker](/docs/deployment/docker); Compose sets it to `http://api:4000`                                                                              |
| `NEXT_PUBLIC_API_URL`               | `web-next.ts` (client)   | required                  | The api origin the browser calls                                                                                                                                                                 |
| `NEXT_PUBLIC_APP_URL`               | `web-next.ts` (client)   | required                  | The web origin: the sitemap and robots, the `llms.txt` links, and the sign-in callback                                                                                                           |
| `NEXT_PUBLIC_POSTHOG_HOST`          | `web-next.ts` (client)   | optional                  | [PostHog](/docs/manage/analytics) region or self-hosted URL; unset, `web/next/instrumentation-client.ts` uses the EU cloud                                                                       |
| `NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN` | `web-next.ts` (client)   | optional                  | Turns PostHog on                                                                                                                                                                                 |
| `NEXT_PUBLIC_USERJOT_URL`           | `web-next.ts` (client)   | optional                  | Shows the [feedback link](/docs/manage/analytics#user-feedback)                                                                                                                                  |
| `NODE_ENV`                          | every slice              | required                  | The [stage](#stages); the web slice mirrors it to the browser as `NEXT_PUBLIC_NODE_ENV`, which you never set                                                                                     |
| `POSTGRES_URL`                      | `db.ts`                  | required                  | The [database](/docs/manage/database); `init` fills it when it provisions one. A `localhost` host becomes `host.docker.internal` under `INTERNAL_API_URL`                                        |

## Stages

`NODE_ENV` is a five-value enum in `packages/env/src/lib/constants.ts`, validated by every slice: `local`, `development`, `test`, `staging`, `production`. With a known stage set, `load-dotenv.ts` layers `.env.<stage>` over the base `.env` with override, so `.env.production` wins where both name a key. The api bundle reads the stage at runtime rather than at build (`bun build --env disable` in `api/hono/package.json`), so the process or container env decides it, never the shell that ran the build.

To branch on the stage, `@packages/env` exports a checker per value (`isLocal`, `isProduction`, and the rest), so code reads `isProduction(env.NODE_ENV)` instead of comparing strings.

## Skipping validation

Two flags, both read in `packages/env/src/lib/polyfill.ts`, let a build pass without real values: a missing required variable falls back to a shape-valid dummy (`https://polyfill.url`, `postgres://polyfill.local:5432/db`). Validation otherwise still runs, so a present-but-invalid value fails either way.

- `SKIP_ENV_VALIDATION=true` covers every variable, server and client: the CI escape hatch (`.github/workflows/auto-check-build.yml` sets it), for a build before any real secret exists. The Docker images do not use it: each mounts the real `.env` as a build secret and validates it in full.
- `SKIP_ENV_VALIDATION_SERVER=true` covers only the server variables; the `NEXT_PUBLIC_*` client variables stay required and validated, because the web build inlines and ships them. The web's Vercel build command sets it (`web/next/vercel.json`): it compiles the server packages for their types without their secrets.

`BETTER_AUTH_SECRET` is the exception to the dummy: under either flag `serverSecret` in `lib/polyfill.ts` turns its schema optional and leaves the value `undefined`, because a secret that resolved to a constant would be a secret everyone knows; the auth package still constructs for a build. Without a flag the schema stays required, so a missing secret fails at boot with `Invalid environment variables` rather than running.

<Callout type="warn" title="Never set a skip flag on a running app">

The server would start against dummy URLs and an undefined `BETTER_AUTH_SECRET`. The flags are for a build, and the error they silence is the one you want at boot.

</Callout>

## Adding a variable

A variable lives on more surfaces than the schema, and a surface left out fails quietly rather than loudly. `HONO_RATE_LIMIT` is the full set:

| Surface                            | For `HONO_RATE_LIMIT`                                                                       | Because                                                                                                                                                                |
| ---------------------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The slice: schema and `runtimeEnv` | `packages/env/src/api-hono.ts`                                                              | the schema types and validates it; the `runtimeEnv` entry is what reads `process.env`                                                                                  |
| The root `.env`                    | `.env`                                                                                      | your value                                                                                                                                                             |
| `.env.example`                     | `.env.example`                                                                              | what a fresh checkout and `init` start from, defaults included, `HONO_RATE_LIMIT` among them; only the variables the [table's lead-in](#every-variable) names stay out |
| `globalEnv` in `turbo.json`        | `turbo.json`                                                                                | Turbo hashes it, so a changed value misses the cache instead of replaying a stale build                                                                                |
| The consumer                       | `api/hono/src/middlewares/rate-limiter.ts` and `auth.ts`                                    | where the typed value is read                                                                                                                                          |
| The docs and skills that name it   | the table on this page, and whatever `rg -n HONO_RATE_LIMIT web/next/content .agents` finds | so the table a reader scans still matches the schema                                                                                                                   |

<Callout type="warn" title="runtimeEnv is mandatory">

A variable declared in the schema but missing from the slice's `runtimeEnv` map is silently `undefined` at runtime. Always add both.

</Callout>

## Common questions

**What reads `HONO_APP_URL`?**

Not the api's routers, which is why it looks removable: the `api-hono` slice declares it, but nothing under `api/hono/src` reads it. `packages/auth/src/index.ts` does, through `@packages/env/auth`, three times. The cookie scope derives from its host (parsed at build by `generate-env.ts`, overridden at runtime for a `.localhost` dev host so web and api share the cookie), its origin is what separates the api from the web entries in `HONO_TRUSTED_ORIGINS`, and Better Auth's `baseURL` falls back to it off a public hosting suffix. So it stays required.

**Why does the `web-next` slice not load `.env` itself?**

Because client components import it. The loader needs `dotenv` and `node:path`, and a module shared with `web-next` would drag the browserified node graph behind `dotenv` into every page that imports the slice, so the load lives in `load-dotenv.ts`, which only the server slices import. A fork adding a slice of its own (a `mail` target, say) adds `import "@/load-dotenv"` to it, then gives it the `entry` and `exports` lines the `add-package` skill ([AI Skills](/docs/resources/ai-skills)) describes for a library with several entries.

**Is `INTERNAL_API_URL` how two Vercel projects talk?**

No, it is the Docker variable, and Compose sets it on both services. It does three jobs there: the web's `/api` rewrite and its server-side fetches target it instead of the public api URL, and its presence flips `POSTGRES_URL` to `host.docker.internal`. Two projects on a public suffix such as `*.vercel.app` need none of that: the web build detects the suffix (`NEXT_PUBLIC_IS_PRIVATE`, derived by `generate-env.ts`) and proxies the browser's `/api` calls to `NEXT_PUBLIC_API_URL` itself, for the reason [sessions and cookies](/docs/manage/authentication#sessions-and-cookies) gives. Setting `NEXT_PUBLIC_API_URL` to the web origin by hand is the trap: without `INTERNAL_API_URL` the rewrite's destination is the web itself, and every `/api/*` call ends in `508 Loop Detected`. [Deploy to Vercel](/docs/deployment/vercel) has the matrix that works.

## It's working if

- `bun run dev` with `POSTGRES_URL` blank stops the api at boot with `❌ Invalid environment variables:` and an issue whose `path` is `POSTGRES_URL`, then throws `Invalid environment variables`; nothing starts against a half-read config.
- With `NODE_ENV=local`, `next dev` prints `@web/next:getSafeEnv:` with the slice's values and `NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN` shown as `******** REDACTED ********`.
- Reading `env.INTERNAL_API_URL` from a client component throws `❌ Attempted to access a server-side environment variable on the client`.
