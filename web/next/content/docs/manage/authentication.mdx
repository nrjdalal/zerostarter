[Better Auth](https://better-auth.com) owns sign-in, sessions and roles as one config in `packages/auth`: `src/schema.ts` declares the plugins and the columns they add, and the Drizzle auth schema is generated from it; `src/index.ts` adds the providers, the cookie scope and the sign-in hook. It runs in-process against your own Postgres, so no user record leaves your database and there is no separate auth service to keep in sync.

`user.role` is the only truth for the console, and every gate re-reads it past the five-minute cookie cache. There is no env allow-list and no second list to keep in step: a rung granted or revoked, by the console, the CLI or an allowlist rule, is the whole decision, and it lands on the next request.

## When you need this

Reach for this page when you are configuring how people sign in, or deciding who reaches the console and what each rung may do there. For granting console access by rule rather than one account at a time, see [Allowlist](/docs/manage/allowlist); for the per-tenant roles inside an organization, which share three words with the ladder here and govern nothing on it, see [Organizations & Teams](/docs/manage/organizations).

## Prerequisites

An OAuth app registered with GitHub or Google, or a magic-link sender, before a deploy exposes a login. A fresh clone needs neither: the local agent sign-in covers development, and it cannot exist in a deploy.

## Sign-in methods

The sign-in dialog draws itself from `GET /api/auth/providers` (`api/hono/src/routers/auth.ts`), which lists the methods the api has enabled, so turning one on or off is an env or plugin change, never a UI change.

| Method                    | What turns it on                                                                                                                                                 |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GitHub                    | `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET`, both; one half alone registers nothing                                                                            |
| Google                    | `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, both                                                                                                              |
| Magic link                | `magicLink({ sendMagicLink })` in the `plugins` array of `packages/auth/src/schema.ts`; the client plugin is already registered, so the email field then appears |
| Agent sign-in (local dev) | `NODE_ENV=local` and `AGENT_SIGNIN_ENABLED=true`, plus a trusted `Origin` on each request                                                                        |

A fork ships with GitHub, Google, both or neither: `packages/auth/src/index.ts` builds `socialProviders` from the complete pairs and exports `enabledProviders`. A new provider is registered there the same way, then given a button in `web/next/src/components/common/access.tsx`.

Magic link is off until its server plugin is registered, and the comment above `magicLinkEnabled` in `packages/auth/src/index.ts` names the line. The sender is yours (Resend, Postmark, SES), imported inside the `sendMagicLink` callback rather than at the top of `schema.ts`; that file's header says why: the Better Auth CLI loads it under Node to generate the tables, so nothing at its top may reach the database.

Agent sign-in mints a real session as `LocalAgent`, an `owner` on the sign-in that creates the account and left at its rung after that (`api/hono/src/routers/agents.ts`). `AGENT_SIGNIN_ENABLED` is blank in `.env.example`, so a deployed default env exposes nothing; [Working with Agents](/docs/getting-started/working-with-agents) has the curl form.

### Callback URLs

Each OAuth app takes your app's origin (GitHub's "Homepage URL", Google's "Authorized JavaScript origins") and the callback Better Auth listens on at `/api/auth/callback/<provider>` (GitHub's "Authorization callback URL", Google's "Authorized redirect URIs"):

| Where you run                                                        | Origin                        | Callback                                                                                                          |
| -------------------------------------------------------------------- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Production on your own domain                                        | `https://example.com`         | `https://api.example.com/api/auth/callback/github` and `https://api.example.com/api/auth/callback/google`         |
| Local, `PORTLESS=0 bun run dev` (web `:3000`, api `:4000`)           | `http://localhost:3000`       | `http://localhost:4000/api/auth/callback/github` and `http://localhost:4000/api/auth/callback/google`             |
| Two deployments on a public hosting suffix (two `*.vercel.app` apps) | `https://your-web.vercel.app` | `https://your-web.vercel.app/api/auth/callback/github` and `https://your-web.vercel.app/api/auth/callback/google` |

The last row is the web for both: on a public suffix sign-in completes on the web origin, for the reason the [sessions and cookies](#sessions-and-cookies) table gives, and a callback registered on the api there ends every sign-in in `state_mismatch`. Under the default `bun run dev`, providers refuse the `.localhost` redirect URI, so OAuth round-trips only on the fixed ports; the question below has the detail.

## The console role ladder

`/console` is the privileged area, gated by the `role` column the Better Auth [Admin plugin](https://www.better-auth.com/docs/plugins/admin) adds to the `user` table.

| Rung     | Reaches                                                       | May change                                          |
| -------- | ------------------------------------------------------------- | --------------------------------------------------- |
| `owner`  | the whole console                                             | anyone, including another owner, but not themselves |
| `admin`  | the whole console                                             | anyone below admin: not a peer, not an owner        |
| `member` | the console shell and Console > Docs, when that feature is on | nothing                                             |
| `user`   | nothing                                                       | n/a                                                 |

Access, Waitlist and History are admin and above, so a member's console is the shell and the internal docs: the rung the [allowlist](/docs/manage/allowlist) grants, the one a fork builds its read-only surfaces on, and never sight of who your users are. Every gate asks `roleAtLeast` in `@packages/auth/access`, the only place the order is written, and anything unrecognized (a null, a legacy value, a crafted string) reads as `user`, so an unknown role can never grant access.

Two gates enforce it. `web/next/src/lib/auth/console.ts` admits `member` and above and answers `notFound()` to everyone else, so the console is never advertised; the Access, Waitlist and History pages each assert `admin` themselves. The api's console router under `/api/v1/admin/*` requires `admin` throughout (`api/hono/src/middlewares/console.ts`; the envelope is in [API Conventions](/docs/manage/api-conventions)). Both re-read the session past the cookie cache, so a grant, a demotion or a ban lands on the next request, and both refuse a banned user, which covers a ban written straight to the database.

The plugin's own endpoints are switched off rather than gated: `/api/auth/admin/*` authorizes on access-control statements alone, with no notion of rank or of the last owner, so at the stock `adminAc` one `set-role` request promoted an admin to owner. Every rung is declared with no statements; `set-role`, `ban-user` and `unban-user` come back as the console's own routes with the rank rule attached, and the rest, impersonation included, stay off. The comment above `adminPlugin` in `packages/auth/src/schema.ts` records this and what a fork accepts by widening a statement with `defaultAc.newRole`.

### Changing a role, banning an account

Both live at **Console > Access > Users**, on a row or across a selection. The guard is one pure function per decision in `@packages/auth/access` (`refuseRoleChange`, `refuseBan`), asked by the menu so it never offers what the server would refuse, and again by the api on every request: your own account is refused, so is anyone at or above your rank, granting owner is owner-only, and the last owner cannot be demoted. A ban also ends the person's sessions, so they are signed out everywhere at once; an unban clears the flag, the reason and the expiry and nothing else, so it restores exactly the access they had. The guard runs per account, so a selection is partly refusable by design and every id comes back with its own outcome. Every write leaves a line in [Console > History > Activity](/docs/manage/activity) inside the same transaction, because `user.role` is overwritten in place and nothing else would record what it used to say.

The first owner comes from the CLI, which is also how a fresh install gets its first way in:

```bash
bun run console:roles grant you@example.com owner
```

Its header (`.github/scripts/console-roles.ts`) lists `grant`, `revoke` and `list`: `grant` defaults to `owner` while the install has none and to `admin` after, `revoke` sets `user`, and both write the same activity line as the console. This ladder lives on `user.role` and governs the install; an organization's `owner`, `admin` and `member` live on `member.role` and govern one organization, and neither reads the other.

## Sessions and cookies

Sessions live in the `session` table and travel as a secure cookie; the active `organizationId` and `teamId` ride along on the row. The cookie's scope is derived at build time from `HONO_APP_URL`'s public-suffix breakdown (`packages/auth/src/lib/utils.ts`), so it follows where you deploy rather than a setting you keep in step:

| Where the api runs                                           | Cookie scope                                                                                                                                                                   |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A subdomain of a parent you own (`api.example.com`)          | A cross-subdomain `Domain` cookie, shared by web and api                                                                                                                       |
| A public hosting suffix (`*.vercel.app` and the like)        | Host-only and first-party to the web: siblings cannot share there, so the client routes sign-in same-origin through the web's `/api` proxy ([Vercel](/docs/deployment/vercel)) |
| A bare or apex host, or a bare `localhost` (as under Docker) | Host-only; on `localhost` it holds across ports                                                                                                                                |
| Local portless dev (`*.localhost`)                           | One `Domain` cookie shared by the web and api hosts. The exception to the build-time rule: the api re-derives the scope at runtime from the subdomain portless injects         |

Better Auth caches the session in the cookie for `maxAge: 300`, so a plain read can trail a role change by five minutes. Three reads skip the cache: the console page gate, the api's console middleware, and the dashboard layout (`web/next/src/app/(protected)/layout.tsx`). The first two are correctness. The third draws the Console link in the dashboard's user menu, and the direction that matters is promotion: on a cached read someone you just lifted to `member` could not find the console they already have. It costs one session lookup per dashboard render, on the api side of a round trip that happens anyway.

Reading the session is one call on either side, both in `web/next/src/lib/auth/`: `index.ts` on the server (`auth.api.getSession`, with `disableCookieCache` for a gate), `client.ts` in a client component (`authClient.useSession`). The `(protected)` layout redirects anyone without a session to `/`; api routes behind `authMiddleware` (`api/hono/src/middlewares/auth.ts`) answer `401 UNAUTHORIZED`.

## Common questions

**Sign-in between two `*.vercel.app` projects ends in `state_mismatch`.**

`vercel.app` is on the Public Suffix List, so web and api projects there are different sites: a `Domain=.vercel.app` cookie is refused, and a host-only cookie the api sets during a sign-in started from the web is cross-site, which the browser will not store either. The app detects the shape at build and routes sign-in same-origin through the web's `/api` rewrite, so the cookie lands first-party on the web; register the callback at the web origin (the last row of the [callback table](#callback-urls)) and set `HONO_WEB_URL` on the api when it cannot infer the web origin from `HONO_TRUSTED_ORIGINS`. A custom domain switches back to the shared `Domain` cookie on its own.

**Is `HONO_APP_URL` still read?**

Yes, three times in `packages/auth/src/index.ts`: as the api origin the web-origin inference excludes, as the host whose public-suffix breakdown sets the cookie scope at build, and as Better Auth's `baseURL` everywhere the api is not on a public suffix. On a public suffix the `baseURL` becomes the web origin instead, which is what a request to remove the variable mistook for it being unused.

**The dialog says "No sign-in options are configured yet."**

The api reported no provider: neither OAuth pair is complete, the magic-link server plugin is not registered, and in a dev build `AGENT_SIGNIN_ENABLED` is unset, which the message says there. A deploy with nothing configured shows this to every visitor. "Could not load sign-in options" is different: the web could not reach `/api/auth/providers` at all.

**OAuth does not round-trip under `bun run dev`.**

Portless serves `api.<name>.localhost`, and a provider refuses that redirect URI: Google requires a top-level domain on the public suffix list, which `localhost` is not, and allows plain `localhost` only for testing. Run `PORTLESS=0 bun run dev` for the fixed ports the local row expects, or use **Login (agents)**, which needs no provider.

**`authClient.admin.*` returns 403 for an owner.**

By design: every endpoint the Admin plugin mounts refuses every rung, because the plugin cannot see rank. The console's routes under `/api/v1/admin/` are the replacements; a fork that ships UI on the plugin's client widens the statement it needs in `packages/auth/src/schema.ts`.

**Nobody can grant owner any more.**

An admin cannot grant owner, act on a peer, or unban another admin, so an install with no owner is recoverable only from the CLI: `bun run console:roles grant <email> owner`. The console refuses to demote the last owner or to ban the last unbanned one, so the state comes from the script, which warns when a `revoke` takes the last owner, or from a write straight to the database.

## It's working if

- `GET /api/auth/providers` answers `{"data":{"providers":["github"]}}` with your provider in the list, and the sign-in dialog draws that button and no other.
- `bun run console:roles list` prints you as `- owner  you@example.com (Your Name)`.
- After `bun run console:roles revoke you@example.com`, your next request to `/console` is a 404 rather than a redirect, and the Console entry is gone from the dashboard's user menu, with no sign-out in between.
